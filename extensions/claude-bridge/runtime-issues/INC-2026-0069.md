## Symptom and evidence limits

On the production Bridge server (6.3.15x), the owner's own agent session disconnected. At the same time, the server console was flooded with two repeating line shapes for the same few dozen subagent transcript files:

- `[subagent] watcher start: <agent> (<agent-file>.jsonl)`, repeated for the same file many times;
- `[subagent] send <agent>: N entries`, repeated with the identical N per agent — 200 (one replay chunk) or the full size of a small transcript.

The server is shared by up to 20 users with 5–10 sessions each. The excerpt does not show which client was disconnected, and no memory or socket metrics were captured. The disconnect is therefore attributed by mechanism, not by measurement.

## Confirmed source defect

At `origin/main` `350beae` (Bridge server 6.3.153), `JsonlWatcher.scanSubagents()` runs every 4 s for every open session (`server/src/core/pty/jsonl-watcher.ts`):

1. A subagent watcher whose file has not grown for `SUBAGENT_RETIRE_MS` (5 min) is stopped and deleted from `subagentWatchers`. This retirement was added so that finished subagents stop holding timers and inotify handles.
2. The same scan then lists `subagents/`. The retired file is no longer in the map, so a new `SubagentJsonlWatcher` is created for it.
3. `SubagentJsonlWatcher.startTailing()` reads the file from byte 0 and sends every entry to the client in 200-entry chunks (`subagent-jsonl-watcher.ts`).
4. Five minutes later the idle watcher is retired again, and the cycle repeats for as long as the session is open.

The code comment assumes the client deduplicates by uuid. That limits duplicates in the UI, but not the cost: every finished subagent's whole transcript is re-read from disk, re-parsed and re-sent every ~5 minutes. Multiplied by sessions and users, this fills each connection's outbound buffer.

The 16 MB limit is the per-connection outbound-buffer cap (`WS_SEND_MAX_BUFFER`, `session-io.ts`). Past it, frames are dropped so that one slow client cannot run the server out of memory. Raising it would only move the cliff: an endless replay fills any buffer.

## Expected result

A retired subagent watcher keeps a small record (path, consumed byte offset, file identity/size). A later scan:

- skips the file while its size equals the recorded offset;
- resumes tailing from the recorded offset when the file grew, without a replay from 0;
- replays from 0 only when the file shrank or was replaced.

Re-checking retired files must be cheap at server scale (hundreds of sessions): no `stat` of every retired file on every 4 s scan. Use a bounded re-check interval or directory-level change detection. Records are dropped with the session. Live (non-retired) subagent behaviour, backpressure retries and the first replay of a newly discovered subagent stay unchanged.
