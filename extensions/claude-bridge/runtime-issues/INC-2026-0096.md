## Symptom

A session runs a bridge Bash tool call (`mcp__user-tools__Bash`) with
`sleep 90 && echo <marker>`. The client interrupts the turn a few seconds after
the process started. The chat stops at once and the session accepts the next
prompt, but the `sleep 90` process on the client host is not stopped. It runs
its full 90 seconds.

## Confirmed facts

- Setup: the embedding example host (headless workspace host built from the
  source of #724, `8ea084b0` in `main`) with `@kaminide/bridge-browser-client`, against
  Bridge server 6.3.164 with CLI 2.1.312. The client host was a Linux container.
- 10 repeats in one session, then one more in a fresh session. Each repeat:
  submit the prompt, wait until `sleep 90` exists on the client host, wait 5
  seconds, call `interrupt(tab)`.
- In all 11 repeats `session:activity` reported `isWorking: false` 116 to 188 ms
  after the interrupt, and a follow-up prompt was answered. The transcript shows
  the tool call as not completed. The marker never reached the transcript.
- In all 11 repeats the `sleep 90` process was still present 3 seconds after the
  interrupt. Up to 5 such processes from consecutive repeats ran at the same
  time. In the last repeat the process was followed by its PID: it exited 88 to
  93 seconds after its start, which is its natural end.
- No permission prompt appeared for these calls in this setup.
- Server source: `session:interrupt` (`server/src/core/pty/session-ws.ts`)
  aborts the in-flight upstream request and interrupts the CLI. It sends nothing
  about the running tool call to the client.
- Server source: the MCP endpoint answers `notifications/cancelled` with 202
  and does nothing else (`server/src/core/pty/mcp-http-handler.ts`).
- Client source: `interruptSession` (`extension/src/main/ws/connection-manager.ts`)
  only sends `session:interrupt` to the server.

## Hypotheses

- The CLI may send `notifications/cancelled` for the tool call, or only close
  the HTTP request. Either way the server does not turn it into a cancellation
  of the client tool call.
- The same may hold for other long client tools (monitors started by a tool,
  long file searches) and for an interrupt sent from KaminIDE. Only bridge Bash
  through the embedding host was measured.
- On Windows client hosts the surviving process may differ in form (a shell
  with children). Not measured.

## Expected outcome

After an interrupt the command started by the interrupted tool call is stopped
on the client host together with its child processes, and the session stays
usable. A command that the user moved to the background on purpose is not
affected.

## Research result and fix (2026-11-11)

The first hypothesis is confirmed by the code. Three places lost the
cancellation, all on the server:

- `session:interrupt` told only the CLI.
- `notifications/cancelled` was acknowledged and ignored.
- On the task path (`Bash` / `PowerShell` with the tasks extension) an aborted
  foreground wait turned the command into a background task.

The client needed no change: on `mcp:cancel` it already stops the process tree
of that call (process group on Linux and macOS, `taskkill /T /F` on its own
child PID on Windows).

#727 makes the server track the tool calls a request still waits on. On
`session:interrupt` and on `notifications/cancelled` it sends `mcp:cancel` for
them and answers the call as interrupted. Explicit background tasks and other
sessions are not affected.

Automated acceptance (in `main`, run by `Bridge server checks` on Linux):
`server/src/core/pty/mcp-interrupt.integration.test.ts` drives the real MCP
handler and the client's real `runForegroundCommand`. For the legacy, modern
and task call paths the command and its child process exit within 1 second of
the interrupt, the result is the interrupted error and the next command works.
Ten interrupts in a row leave no process.

Which of the call paths CLI 2.1.312 uses was not read from a live server, so
all of them are covered.

## Verification on the released image (2026-11-11)

Run by studiohost on the acceptance Bridge server from image
`dykamino/open-claude-bridge:6.3.169` (CLI 2.1.322). The CLI used the
`mcp__user-tools__Bash` call path.

### Gate 1, Linux client host: passed

Client: a Linux container with the embedding example host and the 6.3.169
packages downloaded from the GitHub Release. Ten repeats in one session of
`sleep 90 && echo <marker>`: wait until the process exists, wait 5 seconds,
call `interrupt(tab)`.

- The shell and `sleep` were gone 16 to 27 ms after the interrupt (median
  22 ms) in 10 of 10 repeats.
- `session:activity` reported `isWorking: false` after 118 to 191 ms.
- The follow-up prompt was answered every time (2.5 to 4.3 seconds).
- No `sleep` was left after the series, the marker never reached the
  transcript, and the tool result is the "did not complete" error.

### Gate 2, KaminIDE 1.0.92 on Windows: failed

Client: KaminIDE 1.0.92 installed from the release installer on Windows 11,
started on a copy of a profile and driven through the CEF debugging port
(the release binary has no probe). The stop button of the chat was pressed
3 seconds after the command's processes appeared. Process exit was polled every
5 ms. Eleven repeats with three commands: a native child (`ping -n 600`), an
MSYS child (`sleep`), and both at once.

- The cancellation reaches the client in every repeat. The top shell process
  exits 1038 to 1068 ms after the click. That is the client's 1 second
  force-kill timer, not `taskkill`.
- The rest of the tree that `taskkill /T /F` can see (inner shells, `conhost`,
  `ping`) exits 1379 to 1647 ms after the click (median 1425 ms). The 1 second
  bound of gate 1 was not met in any repeat.
- The follow-up prompt was answered in 11 of 11 repeats (2.9 to 3.4 seconds).
  The marker never reached the chat. No `Session destroyed`.
- With a native child only, nothing was left (3 of 3).
- With `sleep`, `sleep.exe` was still running after the interrupt in 8 of 8
  repeats. Two of them were found still running several minutes later. Cause:
  Git Bash starts an MSYS program through an intermediate process that exits
  at once, so the Windows parent PID of `sleep.exe` belongs to a dead process
  and `taskkill /T` does not find it from the shell's PID. `ping.exe`, a native
  program, keeps a live parent and is stopped.

The expected outcome of this card is therefore not met on Windows for commands
that run MSYS programs (`sleep`, and by the same mechanism other Git Bash
utilities). The defect is in the client's Windows tree stop
(`extension/src/main/mcp/tools/shell-foreground.ts`), not in #727.

### Time bound on Windows

Measured: 1.38 to 1.65 seconds, on a machine that was running other builds.
About 1.0 second of it passes before `taskkill` has done anything, and the
tree is gone 0.3 to 0.6 seconds later. A 1 second bound cannot hold while the
stop goes through `taskkill`. Proposed bound for the current mechanism:
3 seconds from the interrupt until every process of the command has exited,
which is about twice the slowest measured run. If the tree stop is replaced by
a Job Object, measure again and set the bound from that data; 1 second is then
a reasonable target. The Linux bound stays 1 second.

## Windows client change #738 (2026-11-11)

[#738](https://github.com/dykamino-coder/gpui-kamin-ide/pull/738) (`2c5ea735`) starts Bash and PowerShell foreground commands
through `kamin-jobrun.exe`, a runner that holds a kill-on-close Job Object
without breakaway, and cancels by ending the runner. Gate 2 on the candidate
commit `fabab20e` (runner and extension of that commit inside a private copy
of the installed 1.0.92 application, real CLI, Stop pressed through CDP):
13 interrupts in 4 variants (MSYS `sleep`, native `ping` from Bash, both,
`ping` from the PowerShell tool); the whole tree, including MSYS children
with a dead parent, was gone 40 to 90 ms after the click, nothing was left and
the next prompt was answered in every run. Limits: only foreground commands
are covered; a host without the runner keeps the `taskkill` path; the gate
did not use an installer built from the commit. The proposed 3 second bound
above belongs to the `taskkill` path; with the runner the measured time is
under 0.1 second.

## Verification on the released build 1.0.94 (2026-11-11)

Run by studiohost. Client: KaminIDE 1.0.94 installed from the installer of the
GitHub Release (its SHA-256 equals the release provenance) on Windows 11,
started on a copy of a profile and driven through the debugging port. Server:
the acceptance Bridge server from image
`dykamino/open-claude-bridge:6.3.171`. The method is the one of gate 2
above: Stop is pressed 3 seconds after the command's processes appear and
process exit is polled every 5 ms.

| Variant | Runs | Whole tree gone after Stop | Left after Stop | Follow-up answered |
| --- | --- | --- | --- | --- |
| native child (`ping` from the Bash tool) | 2 | 37 and 43 ms | nothing | yes |
| MSYS child (`sleep`) | 2 | 36 and 57 ms | nothing | yes |
| both at once | 2 | 49 and 36 ms | nothing | yes |
| `ping` from the PowerShell tool | 2 | 50 and 37 ms | nothing | yes |

- In 8 of 8 runs the command ran under `kamin-jobrun.exe`, the chat was idle
  163 to 397 ms after Stop, the follow-up prompt was answered in 2.9 to
  4.4 seconds, the marker of the stopped command never reached the chat and the
  host process survived.
- Baseline on the same day with the installed KaminIDE 1.0.93 / server
  6.3.170: no runner in the tree, and a process of the command was still
  running after Stop in both runs made (MSYS child, both at once).

Limits of this run: 8 interrupts, foreground commands only. Background shells,
hooks and plugin monitors keep the earlier cleanup and were not run. The
application was not updated through the Bridge self-update; the installer was
run directly.
