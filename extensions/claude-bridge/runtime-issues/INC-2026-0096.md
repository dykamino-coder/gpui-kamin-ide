# INC-2026-0096 — Interrupt ends the turn, but a running bridge Bash command keeps running on the client host

- **Status:** reported
- **Registration author:** studiohost, lead-assigned check (10 repeats of an interrupt during a bridge Bash `sleep 90`).
- **Completion target:** a research result: where a cancellation of an in-flight client tool call is lost between the CLI, the Bridge server and the client host, and a bounded change plan that stops the command's process tree on interrupt. Implementation is a later task.
- **Diagnostic PR:** this registration.
- **Fix PR:** none
- **Next step:** research. Trace what the CLI sends to the Bridge MCP endpoint when a turn is interrupted during a tool call, what the server forwards to the client, and how the client's Bash executor can be told to stop the process. Owner: next maintainer run.
- **Private evidence:** not required. The facts below reproduce from public source and a synthetic prompt. The run logs stay outside the repository.
- **Dependencies:** none.
- **Acceptance:** automated: a test that drives the real server MCP handler and the real client Bash executor, interrupts a running command and observes that its process has exited. A live repeat of the scenario below is a supporting check, not a merge gate.
- **Acceptance rationale:** the defect is a missing message and a process that is not stopped. Both are observable in handler and executor tests without a UI.
- **Deployment observation owner:** KaminIDE owner, after an implementation ships.

## Symptom

A session runs a bridge Bash tool call (`mcp__user-tools__Bash`) with
`sleep 90 && echo <marker>`. The client interrupts the turn a few seconds after
the process started. The chat stops at once and the session accepts the next
prompt, but the `sleep 90` process on the client host is not stopped. It runs
its full 90 seconds.

## Confirmed facts

- Setup: the embedding example host (headless workspace host built from the
  source of #724, `8ea084b0` in `main`) with `@kaminide/bridge-browser-client`, against
  Bridge server 6.3.164 with CLI 2.1.312. The client host was a Linux container.
- 10 repeats in one session, then one more in a fresh session. Each repeat:
  submit the prompt, wait until `sleep 90` exists on the client host, wait 5
  seconds, call `interrupt(tab)`.
- In all 11 repeats `session:activity` reported `isWorking: false` 116 to 188 ms
  after the interrupt, and a follow-up prompt was answered. The transcript shows
  the tool call as not completed. The marker never reached the transcript.
- In all 11 repeats the `sleep 90` process was still present 3 seconds after the
  interrupt. Up to 5 such processes from consecutive repeats ran at the same
  time. In the last repeat the process was followed by its PID: it exited 88 to
  93 seconds after its start, which is its natural end.
- No permission prompt appeared for these calls in this setup.
- Server source: `session:interrupt` (`server/src/core/pty/session-ws.ts`)
  aborts the in-flight upstream request and interrupts the CLI. It sends nothing
  about the running tool call to the client.
- Server source: the MCP endpoint answers `notifications/cancelled` with 202
  and does nothing else (`server/src/core/pty/mcp-http-handler.ts`).
- Client source: `interruptSession` (`extension/src/main/ws/connection-manager.ts`)
  only sends `session:interrupt` to the server.

## Hypotheses

- The CLI may send `notifications/cancelled` for the tool call, or only close
  the HTTP request. Either way the server does not turn it into a cancellation
  of the client tool call.
- The same may hold for other long client tools (monitors started by a tool,
  long file searches) and for an interrupt sent from KaminIDE. Only bridge Bash
  through the embedding host was measured.
- On Windows client hosts the surviving process may differ in form (a shell
  with children). Not measured.

## Expected outcome

After an interrupt the command started by the interrupted tool call is stopped
on the client host together with its child processes, and the session stays
usable. A command that the user moved to the background on purpose is not
affected.

## Missing evidence and blockers

None for the research step. The Windows client host was not measured.
