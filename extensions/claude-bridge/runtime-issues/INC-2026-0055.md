## Symptom

On Windows, KaminIDE 1.0.55 showed `Extension crashed — Contained — extensions stayed alive: write UNKNOWN` while an active session and subagents were running. Afterward the Cloud Bridge chat and Console stopped visibly advancing. The application did not close normally and the owner eventually forced it closed through Task Manager. A later server-side report says the Claude Code session continued producing output during part of the client freeze; this is second-hand evidence, not proof that the client WebSocket or UI delivery remained healthy.

## Confirmed facts

- The owner-supplied Windows log archive contains five `exthost-child: uncaughtException Error: write UNKNOWN` stacks. The stack reaches Node `child_process` send, `src/kamin-host/port.ts` (`process.send`), `RpcEndpoint.emit`, and `WebviewPostQueue` broadcast from a scheduled flush. This is a child-to-parent IPC write failure, distinct from BR-19's `shell client disconnected` rejection.
- At the current source baseline, `openChildPort().post` calls `process.send` without a local failure result. `WebviewPostQueue.sendOneFrame` removes posts before broadcast and settles them only afterward. If broadcast throws, that batch has no normal settle path. The source shows a risk of lost/unsettled delivery; it does not prove the exact state of each post in the field capture.
- The extension-host crash handler classifies these exceptions as contained and reports the toast. The supplied host incident log does not record a process exit for this capture. The current native crash log records only startup; older native-log generations include earlier renderer terminations and must not be assigned to this event.
- Bridge diagnostic samples in the supplied archive stop around the time of the reported toast. The capture does not timestamp the exact client disconnect or establish why the Node IPC write failed. The separate server agent's transcript and database observations were not independently verified from raw server files here.

## Hypotheses

- The IPC receiver may have closed, become unavailable, or rejected a pending write; transport state and process lifetimes need correlation before choosing a recovery policy.
- An exception during queued webview broadcast may leave the UI with undelivered posts or promises that never settle. The user-visible freeze may also involve a separate native/UI stall; the existing logs cannot exclude it.
- Server transcript maintenance reported later by the server agent is a separate observation and should not be treated as the cause of the earlier local IPC failure without a correlated trace.

## Expected outcome

The maintainer identifies the failure boundary, records a reproducible trigger or a bounded instrumentation result, and addresses child-to-parent send failure without reporting a healthy extension host while chat and Console delivery are stalled. Pending posts must have an explicit delivered/failed outcome, and reconnect or respawn must restore a coherent view. A Change/Fix PR links this incident; the card remains open until the applicable Windows acceptance is recorded.
