## Close-out audit — 2026-09-06

Source checked at `main` `686cc92`: `web::deliver()` still sets `PULL_PENDING`
without waking the pump. Diagnostic #33 and the implemented partition/replay
changes do not close this incident. Their later Windows gates used forced chat
repaint as a BR-31 workaround. BR-25 completion must repeat after BR-31 without
that workaround and cover the original hide/show, tab switch and reap cases.
The stalled invoke evidence also informs BR-24; it does not prove that every
lost-reply/generation case has the same cause. No new runtime fix was made in
this audit. The facts below describe the original pre-fix diagnostic run.

## Symptom

KaminIDE 1.0.54 dev build from `origin/main` `8a1e6f9`, Windows 11, disposable
gate server 6.3.131, Claude Code 2.1.236, one Sonnet 5 session with Agent Teams
(team `br25`, teammates `alpha` and `beta`). The Agents panel, revealed after
the shell reaped its hidden renderer, shows the empty placeholder for 16 s and
longer although the chat view already received the same replay. A single
repaint of any webview (in the gate: a forced style toggle in the chat page; in
the field: pointer movement) delivers the pending frames within 200 ms and the
panel populates. No pointer, toggle or reap wait is otherwise involved.

## Confirmed facts

- The shell keeps host→webview frames in a per-view outbox
  (`crates/shell/src/web/outbox.rs`) and makes the page pull them with
  `window.__kaminPull()` only from `flush_pending_pulls()` inside the repaint
  pump (`crates/shell/src/web/pump.rs`). The pump wakes exclusively through
  `repaint_requested()` (CEF paint/resize callbacks); `web::deliver()` marks
  `PULL_PENDING` but never wakes the pump.
- Run R4 (fresh app, reveal after reap): the recreated Agents view received
  only 7 `invoke-reply` frames after `load`. A direct read of its outbox 60 s
  later returned 103 pending frames (275 KB) including `tab:switched`,
  `jsonl-status`, `jsonl-entries` (51 rows) and `jsonl-subagent-entries` for
  the active tab; the chat outbox held another 274 KB.
- Run R6: reveal → empty panel for 16 s without any input → one forced repaint
  in the chat page → 13 pending frames delivered 200 ms later → panel shows
  team `br25` with both rows.
- Run R5: same procedure, the burst landed 10 ms after `load` because the
  creation paint woke the pump → panel populated at once. Whether the panel
  is empty is a race between the resync burst and the last paint of the new
  view.
- Before the app restart the same starvation looked like a host outage:
  the exthost kept processing inbound messages (it logged unimplemented-channel
  warnings for probe invokes) while no outbound frame reached any view for
  more than 15 minutes; invoke replies from every view timed out.
- Visibility lifecycle from PR #21 works: every hide/show produced
  `visibilitychange` plus a resync burst (`jsonl-status replayComplete:false`
  → entries → `replayComplete:true`) and the shell reaped the hidden renderer
  after 20 s.
- Rows for finished teammates stay `RUNNING` (badge `Active 2`, `Completed 0`)
  both live (session finished at 15:41:28 UTC, rows unchanged at 15:43:21) and
  after replay 27 minutes later (R5, R6). The wire entries for the team tab
  carried two lifecycle `tool_use` rows (`Agent`) and no teammate completion
  signal (no `idle_notification`, no `toolUseResult`), which matches the
  contract inconsistency recorded in BR-27.

## Hypotheses

- `jsonl:request-replay` sent from a webview produced no frames in three
  attempts (chat and tools roles, before and after restart); this needs a
  source audit but is not required for the fix.
- Tools-role views accumulate `mcp:test-log` and `logs:entry` frames in their
  outbox (dozens per minute); cost only, not a correctness issue.

## Expected outcome

BR-31 Change/Fix PR: wake the pump (or an equivalent event-driven pull) when
`web::deliver()` enqueues a frame, with an automated test for the wake and the
R6 procedure as the Windows gate. BR-25 completion gate repeats after BR-31,
BR-27 and BR-26.
