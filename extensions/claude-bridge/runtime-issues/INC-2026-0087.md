## Symptom

The Bridge server can own Claude CLI sessions in a container, but the client
still needs KaminIDE to execute tools and display the conversation. A browser
user needs the same client capabilities with the container acting as the local
machine, including persistent project files, shell, plugins and editor context.

## Confirmed facts

- `extension/src/bridge-host.ts` composes the vendored client handlers and sends
  the same invoke replies and events to attached webviews.
- File/shell tool dispatch is already shared through
  `extension/src/main/mcp/tool-registry.ts`. Plugin hooks, external MCP, LSP and
  monitors are client-host responsibilities, not browser JavaScript processes.
- `webview/src/bridge-shim.ts` builds `window.kaminBridge` from channel tables;
  its transport uses a single `acquireVsCodeApi` handle.
- `webview/src/App.tsx` retains the combined sidebar/chat/settings composition.
  Shipped desktop entry points are chat, tools and customize.
- The API also exposes file viewer/tree and local PTY channels. These channels
  have no handlers in the current extension source; desktop files/editor/terminal
  are native host features. They need container environment services.
- The existing compose file is `server/docker-compose.yml`; there is no compose
  file at the repository root at this source revision.

## Hypotheses

The remaining desktop environment dependencies can be isolated behind a small
adapter without forking business logic. The parity gate must verify this with
actual registrations and fixtures, rather than accepting a successful null
reply as support. Runtime resource and lifecycle behavior need measurement in
the isolated deployment.

## Expected outcome

One headless client host per workspace serves the existing UI over authenticated
HTTP/WebSocket, connects to the Bridge server, and executes local operations in
the container rooted at `/workspace`. Project files and client settings survive
workspace replacement; CLI auth persists solely in the server. Both separate-server and combined packaging
are documented for Podman with loopback publication by default.

Every `KaminBridgeApi` member, mapped channel, dynamic channel and registered
client tool has a supported implementation and a named executable test. Missing
rows, missing handlers, silent no-ops and unsupported capability claims fail the
parity gate. Browser-specific adaptations are explicit and tested.

## Missing evidence and blockers

No implementation or browser/Podman acceptance has run at registration time.
Authenticated CLI availability is a prerequisite for the real chat gate; a
synthetic server is useful for deterministic protocol tests but cannot satisfy
that gate. The agent owns preparing fixtures, performing acceptance, recording
exact candidate evidence and reporting any concrete blocker to the Claude lead.

## Implementation progress

Merged PR #639 provides the authenticated HTTP/WebSocket boundary library.
PR #640 composes the actual shared BridgeHost and tool registry; its deterministic
file-handler tests use a synthetic upstream and await lead review. That code is
not a dependency of the independent browser increment, which adds a cookie-authenticated
socket entry for the existing full App and private reply delivery. Production-bundle
headless Chromium checks cover sign-in/out, UI composition, reconnect, unknown-outcome
rejection, forged window replies and mutation non-replay with an enumerated synthetic
backend. They do not prove real shared-handler, model or container acceptance.
The terminal increment reuses native shell discovery and PTY execution for all
seven terminal channels, including owned teardown and bounded input/resources.
Actual shell and authenticated socket tests cover cwd, TTY dimensions, data,
natural exit and child termination on kill/disconnect/logout/shutdown/backpressure.
This does not prove browser terminal integration or Podman behavior.
Remaining environment services, executable composition, exhaustive parity, dashboard-admin
login and all Podman/live acceptance remain open. See [the package README](../workspace/README.md)
for exact limits; these increments do not close the task.
