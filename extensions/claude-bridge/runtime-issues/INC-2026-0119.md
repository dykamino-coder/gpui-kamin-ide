## Symptom and confirmed facts

During the published 1.0.101 / server 6.3.178 restart replay, the CLI described
receiving two requests together, with the first cut off. The chat was open
through the server restart. This is an observation, not a measured product
delay or proof of its cause.

The old gate driver sampled the entry-count baseline before the page replayed
history. Its completion check could therefore time out despite a visible answer,
or accept an idle gap before the current response. That driver defect is
independent: the corrected driver requires the current uniquely identified
prompt and its subsequent answer, and stops instead of sending another request
when completion cannot be proved.

Source inspection of server 6.3.178 establishes a separate startup risk:
`submitTextToSession` waits for prompt readiness only when attaching engine-switch
context. Ordinary native submissions reach `submitCoordinatedText`, whose
clear/paste/Enter transaction can begin before the new CLI has shown a prompt.
Its two-second Enter ceiling is an echo timeout, not startup readiness.
An early paste can therefore encounter an input consumer that is still starting.
This path has not yet been proved to cause the historical truncated message.

Two isolated single-send checks on the published server, one immediately after
restart and one after a new authenticated backend session, produced no new
visible answer within their bounded observation windows. Neither sent a second
prompt. A subsequent read-only terminal replay of the second check showed its
unique SECOND, THIRD and END data lines in the CLI editor, without the START
line or request prefix. Thus clipping is reproducible independently of a
follow-up gate prompt; successful delivery and concatenation were not observed.
Backend authentication and replayed client idle state did not establish CLI
input readiness. The current private captures stay with the worker; the public
source trace and a subsequent synthetic regression suffice to review the
bounded startup contract without publishing raw profiles or transcripts.

## Bounded proposed change and acceptance

Hold native semantic messages until the CLI's first positive prompt-readiness
notification. Preserve FIFO order, cancellation and teardown; once startup is
complete, preserve existing native mid-turn queuing. Do not turn a startup
timeout into an unconditional paste. Agent-input engines and direct CLI-module
delivery retain their own contracts.

Automated acceptance exercises the real `submitTextToSession` boundary with a
fake PTY: no native writes before readiness, complete multiline paste after
readiness, separate subsequent transactions, cancellation before readiness,
and no delivery after teardown. Tests must fail on the old implementation.

For Windows acceptance, keep a chat open across a restart, send exactly one
uniquely marked multiline request at startup, verify its complete text reaches
the CLI and receives the matching answer, then verify a separately sent second
request. Repeat with delayed readiness. Use only `kamin-acc-302`; do not inspect
or alter its authentication volume or CLI authentication directory. Record the
exact candidate and immutable sanitized evidence before merge. A passing
startup guard alone does not close the historical symptom without correlation.
