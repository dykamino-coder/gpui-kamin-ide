## Symptom

На машине без видеокарты (облачная VM в RDP, окно растеризует WARP) KaminIDE
занимает несколько ядер и интерфейс подвисает, особенно пока идёт ход Claude.
На машинах с видеокартой то же поведение видно как высокая загрузка GPU.
Первоначальная public diagnostic branch содержала raw private data и поэтому
не была смержена.

## Confirmed facts

Capture 2026-09-01 (1.0.53): bounded CPU, thread, module, environment, crash,
CEF и host snapshots одного наблюдения; авторский анализ software-render
throttling и hidden webview state. Functional fix в том diagnostic PR не
выполнялся.

Capture 2026-10-07 (1.0.56, сборщик `collect_cpu_diag.ps1`, два прогона):

Private evidence PR #59 merged at `4ea81f89`; the immutable link above points
to that merged package. All 52 evidence checksums and the backlink to #178
were rechecked. The capture uses an earlier collector copy, not the corrected
candidate in [#179](https://github.com/dykamino-coder/gpui-kamin-ide/pull/179).
Its `diag-window` has 39/36 rows for approximately 30-second windows, so those
rows cannot supply exact per-second averages or acceptance thresholds.
Version 1.0.56 is reported by the capture; an installed binary source SHA is
not established by a provenance sidecar. Source baseline `a0a21dc` below is
the baseline of the source audit, not a verified SHA of that installed binary.
Loaded `d3d10warp.dll` is a module observation; it alone does not establish the
active renderer or its CPU cost.

- RDP-сессия, в главном процессе загружен `d3d10warp.dll`; системные
  «эффекты анимации» выключены, и страницы CEF сообщают
  `prefers-reduced-motion: reduce`. Блок глушения PR #19
  (`#__kaminReducedMotion`) в страницах присутствует.
- Во время хода Claude главный процесс занимал **4,55 из 8 ядер** (девять
  потоков примерно по 0,5 ядра, renderer- и GPU-процессы CEF ≤ 0,1); Chromium
  присылал до **64–68 кадров/с**, сцена gpui стоила до ~385 мс/с. Время
  растеризации WARP в счётчики `diag.log` не входит.
- Второй прогон после перезапуска с `KAMIN_REDUCE_MOTION=1` (0,47 ядра, 0
  кадров Chromium) не является A/B: Claude простаивал, Console ждала
  «Connecting to session…», а под RDP нативный `reduce_motion()` и так
  включён.
- Source, `origin/main` `a0a21dc`: `web/gpu_mode.rs::reduced_motion_block`
  глушит повторы селектором `*,*::before,*::after` (специфичность 0,0,0), а
  правила webview, активные именно при `prefers-reduced-motion: reduce`,
  форсируют `infinite !important` с большей специфичностью:
  `extensions/claude-bridge/webview/src/theme/global.css:48-52`
  (`.fa-spin.fa-spin`) и `theme/legacy-global.css:2869-2879`
  (`.fa-spin`, `[class*="spin"]`, `[class*="pulse"]`, `[class*="ndicator"]`,
  `[class*="loading"]`). На таких машинах глушение PR #19 для этих элементов
  не действует.
- Source: повторяющиеся нативные анимации (`with_animation(..).repeat()`)
  заказывают кадр окна через `request_animation_frame` в обход
  software-интервала насоса; кадр gpui собирается целиком. Покрытие
  `reduce_motion()` неполное — INC-2026-0017.
- `diag.log` не содержит решений `software_render`/`reduce_motion` (они
  уходят только в stdout), не разделяет кадры по вью и источникам и не
  содержит CPU процесса — по нему нельзя назвать, что именно гонит кадры.

## Hypotheses

- Кадры во время хода Claude даёт индикатор активности или другой
  спиннер страницы чата под правилами выше. Не подтверждено: страница чата
  зонду не ответила, по-вью счётчика нет.
- Основная цена — растеризация всего окна WARP на каждый кадр; девять равных
  потоков похожи на пул WARP. Не подтверждено.
- «Висит, пока не кликнешь и не поводишь мышью» после перезапуска — симптом
  BR-06/BR-31; исправления #147/#148/#152 вошли в 1.0.60–1.0.61, а на машине
  стоит 1.0.56. Перепроверить на актуальной сборке.
- Ранее записанные направления остаются открытыми: replay cache в
  наблюдаемом сценарии, полная копия буфера при малом dirty,
  `TS_PROCESS_CRASHED` / `STATUS_BREAKPOINT` (в capture 2026-10-07 —
  дважды для Chat и второго вью).

Ни один пункт пока не считается доказанной единственной причиной.

## Next step — Change PR 1: diagnostic logging

Цель — чтобы следующий полевой `diag.log` сам назвал источник кадров. Только
`crates/shell`; без патчей `vendor/gpui`, без пересборки webview.

1. **Boot-строки в `diag.log`** (сейчас `println!`, в packaged-сборке
   теряются): решение `software_render()` с перечнем адаптеров из
   `gpu_mode::detect`; `reduce_motion()` и его источник (env/RDP) с записью
   каждой смены (функция не кэширует RDP); системный
   `SPI_GETCLIENTAREAANIMATION`; `windowless_frame_rate`; заданные
   `KAMIN_*` overrides (без значений токенов).
2. **Посекундная строка `[why]`**, только если что-то ненулевое:
   - CPU процесса за секунду (`GetProcessTimes`, kernel + user);
   - кадры CEF по вью, топ-5 (`render_handler.rs` уже знает `self.id` в
     `on_paint`/`on_accelerated_paint`);
   - тики нативных анимаций по статическому имени: счётчик в animator-
     замыкании каждого повторяющегося `with_animation`
     (`ui/chat_switch_skeleton.rs` ×3, `ui/icon.rs` ×2, `ui/toasts.rs:278`,
     `ui/sessions/status_dot.rs`, `ui/tabs/chip_leading.rs`,
     `state/term_grid.rs`) и в собственных `request_animation_frame`
     (`ui/toast_card.rs`, `state/metrics.rs`);
   - события ввода окна (move/down/key на корне, `state/handlers_mouse.rs`),
     чтобы «кадры только при движении мыши» были видны в логе;
   - разбудки насоса по причине (кадр CEF / пост хоста / pull) и число
     разосланных `__kaminPull`.
3. **Строка `[views]` раз в 10 с или при смене:** для каждого вью — visible
   или усыплено, `webviews_alive`, `has_html`, попытки resolve, секунды с
   последнего кадра и с последней доставки поста.
4. Ограничения: новый `crates/shell/src/web/diag_why.rs` с `//!` (≤ 250
   строк; `diag.rs` уже 234), не больше одной `[why]` в секунду, ротация
   как у `diag.log`. Unit tests: агрегация top-N, подавление нулевой строки,
   смена `reduce_motion`. Нужные фичи `windows` уже подключены.

## Next step — Change PR 2: mute that wins under reduced motion

`gpu_mode::reduced_motion_block` должен перебивать правила webview при
`prefers-reduced-motion: reduce`. Например, специфичность уровня id —
`:not(#__kaminNoMotion)` для `*`, `::before`, `::after` с той же политикой
`animation-iteration-count: 1 !important`, что приняла PR #19 (разовые
появления доигрывают, повторы гаснут). Вне software-режима блок по-прежнему
пуст. Unit test проверяет селектор и пустой блок при аппаратном рендере.
Webview CSS не менять: страница не знает о software-режиме.

## Verify

После выпуска обоих PR владелец снимает `collect_cpu_diag.ps1` на актуальной
сборке в двух состояниях — простой и ход Claude — без перезапуска с
`KAMIN_REDUCE_MOTION` как «A/B». Приёмка: новые строки присутствуют, источник
кадров назван, CPU главного процесса во время хода Claude заметно ниже
baseline 4,55 ядра. Если зависание после перезапуска воспроизводится на
сборке ≥ 1.0.60, оно регистрируется отдельно или связывается с BR-06/BR-31.
