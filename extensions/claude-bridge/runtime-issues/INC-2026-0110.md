## Symptom

The installed KaminIDE 1.0.94 shows its window, but the main thread does not
answer (Windows marks it "Not Responding") and no webview exists for 20 s or
longer after start. Three starts on 2026-11-13 were stopped after 40–60 s
without a first frame; a fourth drew its first frame after 22.1 s. The same
profile started on 2026-11-12 drew its first frame after 5.8 s.

## Environment and versions

- KaminIDE 1.0.94 (installed), Windows 11, Intel Iris Xe (minimum-power
  policy), Bridge server container from `main` 584b5616, a copy of a working
  profile with five chat tabs and several MCP servers, one of which restarts
  in a loop (its circuit breaker trips every few seconds).
- Started with `--do-not-de-elevate`, `KAMIN_CEF_CDP=1`, a separate probe port.

## Confirmed facts

- `diag.log` of the 22.1 s start: `adapter selected` at 186 ms, the next line
  (first view created) at 22 141 ms. The first metrics line after the stall
  counts 3 907 `wake/host-post` wakes.
- Shell stderr of that start: 16 `resolveWebviewView` calls in the extension
  host, 47 `webview html arrived` lines, each 1.6–2.0 MB, and 149 incoming
  WebSocket frames totalling about 133 MB.
- Source at `origin/main` `04f67209`:
  - `crates/shell/src/host/ws_events/views.rs` sends
    `kamin:webviewView:resolve` for every known view not yet in
    `resolved_views()` on each `kamin:registry:update` and
    `kamin:extensions:changed`. A view enters `resolved_views()` only when its
    HTML arrives, so every registry update that comes before that sends the
    resolve again.
  - `src/exthost/api/webview.ts` `resolveView()` answers a repeated resolve by
    broadcasting the cached HTML again, so each extra resolve becomes another
    full HTML delivery.
  - The HTML branch forwards every payload as `TermEvent::WebviewHtml`, also
    when the view already has the same HTML.

## Hypotheses

- Each repeated HTML reloads the page, and each reload triggers a new resync
  burst from the extension host. This would explain the 3 907 wakes and the
  stall, but the shares of HTML reloads, resync bursts and the looping MCP
  server's log traffic are not separated.
- The longer stalls (40 s and more) may come from the same repeats with more
  registry updates, for example from the looping MCP server. Not measured.

## Expected outcome

- One resolve and one HTML delivery per view per extension-host generation;
  a respawn still re-resolves every view (BR-04).
- First frame on a profile copy faster than 5.8 s.

## Root cause of the stall (2026-11-13, main-thread dumps)

Two later starts of 1.0.94 on a profile copy got no first frame at all (7 and
more than 2 minutes, then stopped). Three mini-dumps of the main process, taken
with procdump, show the same main-thread stack:

- `ntdll!NtWaitForMultipleObjects` ← `KERNELBASE!WaitForMultipleObjects` ← a
  function in `kaminide_gpui` ← the gpui render path under
  `user32!DispatchMessageWorker`. The window is "Not Responding" at about 1 %
  CPU, so the thread waits; it does not compute.
- The waiting function references the strings `terminal-bash`,
  `\System32\wsl.exe`, `wsl-` and `terminal-linux`. Those strings belong to
  `crates/shell/src/term/profiles.rs` `discover()`.
- `discover()` runs `wsl.exe -l -q` through `Command::output()`, with no
  timeout, the first time `profiles()` is called. `state/frame/panels.rs`
  `frame_panels()` calls `profile_by_id()` inside `render` when the terminal tool
  is visible in a panel slot and no terminal exists yet. The tested profile has
  a Terminal tab in the bottom dock.
- On the same machine, at the same time, `wsl.exe -l -q` started from a plain
  shell did not finish in 25 s, both with the normal and with a changed
  `USERPROFILE`. So when WSL does not answer, the first frame waits on it with no
  limit. When WSL answers slowly (a cold service start), the first frame is late
  by that time.

So the stall is `wsl.exe` on the main thread. The repeated HTML deliveries
above are real and still need their own fix (#820), but they do not explain a
main thread blocked at 1 % CPU.

Fix direction for the stall: run shell discovery off the main thread. Start it
in the background at shell start, show the terminal with the profiles found so
far, and limit `wsl.exe -l -q` with a timeout that kills the child, so a hung
WSL costs only its WSL profiles. The first-frame acceptance is unchanged.

## Missing evidence and blockers

- No matching PDB ships with 1.0.94. Frames were identified by module offsets
  and the referenced strings, not by symbols.
- Why WSL stopped answering on this machine is outside KaminIDE and is not
  investigated here.
## Fix candidate

- A shared shell guard claims each view before the resolve RPC, including
  startup retries, registry updates and contributed-view discovery. Request
  errors allow retry; respawn resets the generation. A late error from an old
  generation cannot clear the new request.
- Identical HTML for the same view is dropped before the UI event is queued.
  Changed HTML still reaches the view; respawn permits the same HTML again.
- Resolving before provider registration now reports an error instead of a
  successful no-op, so the shell can retry after extension activation.
- Automated coverage includes a 16-update pre-HTML burst, in-flight dedup,
  request errors, respawn, changed/identical HTML and late provider registration.
  Live first-frame timing and neighboring UI interactions: see Live gates.
