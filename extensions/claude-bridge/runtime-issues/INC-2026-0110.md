# INC-2026-0110 — KaminIDE draws its first frame 20 s or more after start while every webview receives its HTML several times

- **Status:** confirmed (repeated HTML delivery and the start stall are measured; the share of the stall caused by the repeats is not measured)
- **Registration author:** @dykamino-coder, lead-directed registration by Claude Code maintainer `kmaint` (2026-11-13), found while preparing the BR-31 R6 run of batch `RC-2026-11-13-KAMIN-BRIDGE`.
- **Completion target:** accepted and published fix: each webview receives its HTML once per extension-host generation, and the installed KaminIDE draws its first frame on a copy of a working profile faster than 5.8 s, the start time of the same profile on 2026-11-12.
- **Diagnostic PR:** [#816](https://github.com/dykamino-coder/gpui-kamin-ide/pull/816)
- **Fix PR:** none
- **Next step:** change — in the shell, mark a view as "resolve requested" when `kamin:webviewView:resolve` is sent (not only when its HTML arrives), clear the mark on `kamin:exthost:respawned` and on a failed request, and ignore an HTML payload equal to the one the view already has. Then measure the first frame again. Owner of the step: the executor the lead assigns.
- **Private evidence:** not published; the local run logs contain user paths and stay in the maintainer's private folder. The numbers below are counts and times only.
- **Dependencies:** none. Related: BR-04 (respawn reseed uses the same resolve path) and BR-31 (the pump that delivers the resulting frames).
- **Acceptance:** automated test that a burst of `kamin:registry:update` events before the first HTML sends one resolve per view, plus a live start on a profile copy with the first-frame time from `diag.log` and the number of `webview html arrived` lines (one per view).
- **Acceptance rationale:** the stall is a property of the real start of the shell with CEF and the extension host; the duplicate count is provable in a unit test, the start time only in a live run.
- **Deployment observation owner:** none

## Symptom

The installed KaminIDE 1.0.94 shows its window, but the main thread does not
answer (Windows marks it "Not Responding") and no webview exists for 20 s or
longer after start. Three starts on 2026-11-13 were stopped after 40–60 s
without a first frame; a fourth drew its first frame after 22.1 s. The same
profile started on 2026-11-12 drew its first frame after 5.8 s.

## Environment and versions

- KaminIDE 1.0.94 (installed), Windows 11, Intel Iris Xe (minimum-power
  policy), Bridge server container from `main` 584b5616, a copy of a working
  profile with five chat tabs and several MCP servers, one of which restarts
  in a loop (its circuit breaker trips every few seconds).
- Started with `--do-not-de-elevate`, `KAMIN_CEF_CDP=1`, a separate probe port.

## Confirmed facts

- `diag.log` of the 22.1 s start: `adapter selected` at 186 ms, the next line
  (first view created) at 22 141 ms. The first metrics line after the stall
  counts 3 907 `wake/host-post` wakes.
- Shell stderr of that start: 16 `resolveWebviewView` calls in the extension
  host, 47 `webview html arrived` lines, each 1.6–2.0 MB, and 149 incoming
  WebSocket frames totalling about 133 MB.
- Source at `origin/main` `04f67209`:
  - `crates/shell/src/host/ws_events/views.rs` sends
    `kamin:webviewView:resolve` for every known view not yet in
    `resolved_views()` on each `kamin:registry:update` and
    `kamin:extensions:changed`. A view enters `resolved_views()` only when its
    HTML arrives, so every registry update that comes before that sends the
    resolve again.
  - `src/exthost/api/webview.ts` `resolveView()` answers a repeated resolve by
    broadcasting the cached HTML again, so each extra resolve becomes another
    full HTML delivery.
  - The HTML branch forwards every payload as `TermEvent::WebviewHtml`, also
    when the view already has the same HTML.

## Hypotheses

- Each repeated HTML reloads the page, and each reload triggers a new resync
  burst from the extension host. This would explain the 3 907 wakes and the
  stall, but the shares of HTML reloads, resync bursts and the looping MCP
  server's log traffic are not separated.
- The longer stalls (40 s and more) may come from the same repeats with more
  registry updates, for example from the looping MCP server. Not measured.

## Expected outcome

- One resolve and one HTML delivery per view per extension-host generation;
  a respawn still re-resolves every view (BR-04).
- First frame on a profile copy faster than 5.8 s.

## Missing evidence and blockers

- A main-thread stack during the stall was not captured; it is the next
  diagnostic step if the change does not bring the first frame under 5.8 s.
