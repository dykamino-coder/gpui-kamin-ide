## Symptom

Right after `/clear` the footer of the chat shows "High / Auto" although the
session was at "Extra high / Bypass permissions" a moment before. The values
come back after the session is resumed or, for the permission mode, after the
next turn.

## Environment and versions

- KaminIDE 1.0.92 on Windows 11 (a copy of the owner profile), Bridge server
  image 6.3.169 in the acceptance container, Claude Code CLI 2.1.322, model
  `claude-opus-5-5`. Not re-run on 1.0.93 / 6.3.170.
- The chat was driven through CDP (`KAMIN_CEF_CDP`) without taking over the
  screen. The release exe has no `kamin-probe`; whether release acceptance
  should have such a tool is an open acceptance-tooling question, not a defect.
## Reproduction steps

1. Open a Claude Bridge chat session. Set effort "Extra high" and permission
   mode "Bypass permissions" in the footer. The footer shows
   "Extra high / Bypass permissions / Opus 5.5".
2. Send a prompt that uses a tool and wait for the answer.
3. Send `/clear`.
4. Read the footer without sending anything else.

Observed: the footer shows "High / Auto / Opus 5.5". The CLI has started a new
session id; its transcript has rows with `mode: "normal"` and no
`permission-mode` rows, and its assistant rows have `effort: "high"`.

5. Send `/resume <id of the session before /clear>` and then a prompt that
   uses a tool.

Observed: after the prompt the footer shows "High / Bypass permissions"; the
tool call runs without a permission prompt.

## Confirmed facts

- Seen twice in one run (two `/clear` commands), same footer text both times.
- The effort part overlaps with INC-2026-0099: in this run the CLI had already
  been restarted with `--effort high`, so "High" after `/clear` matches
  what the CLI really used; "Extra high" before it was the stale label. The
  permission part is independent of that.

## Hypotheses

- The footer takes the permission mode from transcript rows, and the new
  transcript after `/clear` has none until the first turn. Not checked in
  source.
- Whether the CLI really runs in a different permission mode between
  `/clear` and the next turn was not tested (no tool call was made in that
  state without a resume).

## Expected outcome

`/clear` keeps the effort and permission mode of the session, and the footer
shows the values in use at every moment.

## Missing evidence and blockers

- A tool call directly after `/clear` (no resume) to see which permission
  mode the CLI applies.
- Source check of how the footer derives the two labels.
