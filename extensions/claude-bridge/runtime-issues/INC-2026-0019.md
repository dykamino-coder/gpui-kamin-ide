# INC-2026-0019 — Chat JSONL export bypasses WebSocket backpressure

- **Status:** confirmed (source-level and synthetic handler proof; not fixed)
- **Priority:** P2
- **Diagnostic PR:** this incident's enclosing Diagnostic PR (indexed in the research report)
- **Fix PR:** none
- **Private evidence:** [INC-2026-0019](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/1ff37e64b1626b301ac667561c886001572866e7/incidents/INC-2026-0019)
- **Dependencies:** none; coordinate export policy with INC-2026-0018
- **Acceptance:** automated slow-socket tests + disposable Linux WS/client gate; Windows save/progress gate
- **Corporate observation owner:** none

## Symptom

A normal Chat transcript download can enqueue every JSONL chunk on a connection
already above the server's intended outbound-buffer limit. Individual messages
are small, but the exporter has no lossless backpressure or yielding between
chunks. Slow connections therefore retain export work in addition to ordinary
session traffic.

## Confirmed facts

Source revision: `a34ab4892058bcacc00de8d97ae951fb60551780`. Paths below are
relative to `extensions/claude-bridge/`.

- The shipping Chat download action is at
  `webview/src/components/chat-header/ChatHeaderStrip.tsx:62`. The handler in
  `extension/src/main/ipc/sessions.ts:257–285` asks for a save location first and
  then calls `requestJsonlDownload`; this single-file action has no mirror fast
  path. Cancellation avoids the transfer.
- `extension/src/main/ws/connection-manager.ts:899–916` sends
  `jsonl:download-request`. Server `server/src/core/pty/session-ws.ts:751–793` authenticates,
  resolves the active watcher/file, then reads the entire UTF-8 transcript using
  `fsp.readFile`.
- The loop at server lines 782–790 sends begin, all chunks and end through raw
  `ws.send`. It has no await/drain, bufferedAmount check or per-chunk disconnect
  cancellation. The ordinary guarded send helper refuses work above 16 MiB
  (`server/src/core/pty/session-io.ts:88–105`); this loop bypasses it.
- An executed proof extracted the actual download switch case from TypeScript.
  With an inert socket starting at 17 MiB bufferedAmount and synthetic
  2,000,001-character content, it made five sends containing 2,000,366 JSON bytes.
  All sends occurred before a microtask scheduled by the first send: no yield.
- The client retains chunks and joins them at completion
  (`extension/src/main/ws/connection-manager.ts:994–1016`), then writes the whole
  result. Frame-size limits do not bound the retained complete transcript.

Existing mitigations matter: async filesystem read avoids synchronous disk
blocking; chunks avoid a single huge frame; the button has a busy state; the
client reports a 30-second timeout. None supplies server-side backpressure or
cancels an already running export. This is not an unauthenticated attack finding.

## Hypotheses

Compression and slow links can increase queued work. No actual socket benchmark,
measured heap/RSS, CPU percentage or production OOM cause was established. The
synthetic proof establishes control flow and buffer-policy bypass only.

## Expected outcome

Use a bounded, lossless export stream with yielding, disconnect cancellation and
scoped request identity; write chunks incrementally on the client where possible.
Do not simply replace raw sends with the existing drop-on-cap helper: dropped
export chunks would silently corrupt the downloaded file.

Automated/disposable Linux tests cover an already over-cap slow socket,
disconnect, exact output/progress, concurrent PTY/MCP traffic, growing files and
multiple export attempts. Windows acceptance verifies native save, cancellation,
progress and failure UX before claiming the Chat action fixed. The separate MCP
delivered-state defect remains independently actionable; reducing export pressure
does not correct its delivery bookkeeping.
