## Symptom

In KaminIDE, the session row of a ChatGPT (codex) chat kept its "working" dot
and its running "time working" label while the chat was idle. Its session
metadata had `bridgeStatus=connected` and `bridgeWorking=true`. The label also
keeps the window redrawing once per second.

## Confirmed facts

- On the stand (KaminIDE 1.0.111, Bridge 6.3.188): the codex `app-server`
  process of that session used one CPU tick in 30 seconds and had no child
  processes, so no turn was running.
- Source: `CodexSessionBinding.activity()` sends `session:activity` only on
  `turn.started` / `turn.completed` (and on interrupt or restart), to the
  current `session.ws`. A frame sent while no client is attached is lost.
- `reattachSession()` replays the turn state only through
  `sessionCliControl(session)?.replay()`, which exists for Claude CLI sessions.
  A codex session had no equivalent, so a client that reattached after the
  turn ended kept the last `working=true`. The extension publishes
  `bridgeWorking` only on a change, so nothing corrected it.
- A WebSocket test (fake app-server: one turn, then a second client resumes the
  live chat) received no `session:activity` frame before the fix.

## Hypotheses

- That the stand's session took exactly this path (turn end while detached) is
  inferred from the code; the stand's earlier server log was not kept.

## Expected outcome

A client attaching to a live codex session receives `session:activity` with
the session's current turn state: idle after an ended turn, working during an
open one.
