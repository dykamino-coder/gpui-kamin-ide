## Symptom

During the 1.0.78 installer smoke test (`/S /update` over an installed 1.0.75), a
debug build of `kaminide-gpui.exe` was running from a separate source checkout.
The update closed that debug build together with the installed copy. The
install log says `taskkill done (processes gone: false)`: one process of the
other build was still exiting when the wait finished.

## Confirmed facts

Source audited at `origin/main` `9f07472`.

1. `crates/installer/src/steps.rs` runs
   `taskkill /F /IM <image>` for every name in `unlock::IMAGES`
   (`kaminide-gpui.exe`, `kaminhost.exe`, `kaminide-web.exe`). The kill matches
   by image name only, so every process with that name is killed, wherever it
   was started from.
2. `unlock::wait_processes_gone` uses
   `tasklist /FI "IMAGENAME eq <image>"` and also waits for all processes with
   that name. A long-lived instance in another directory makes the wait time
   out (`processes gone: false`). The install then continues by moving locked
   files aside.
3. The uninstall path in `steps.rs` uses the same image-name `taskkill`.
4. The relaunch after the update starts only the installed executable. The
   closed foreign instance is not restarted.

## Hypotheses

- A second per-user install, or a portable copy, would be closed the same way.
  This was not tested.

## Expected outcome

- Kill and wait select processes by full executable path inside the install
  directory, including `runtime\kaminhost.exe` and the `web` helper copies.
- Processes of the same name in other directories are left alone and do not
  extend the wait.
- The behaviour of the installed copy is unchanged: it is closed, files are
  unlocked, and it is relaunched.
