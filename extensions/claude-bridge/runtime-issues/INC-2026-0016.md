## Symptom

The authenticated request-history API ignores requested pages and filters,
reports error events as success, and deletes from a different dataset than it
reads. Filtering deletion by user and error status clears all that user's OTel
history and metrics rather than only matching errors.

## Confirmed facts

Audited source: `a34ab4892058bcacc00de8d97ae951fb60551780`.
Paths below are relative to `extensions/claude-bridge/server/src/`.

- `core/dashboard/controllers/stats.ts:140–143` forwards only limit to
  `getRecentEvents`. `core/telemetry/store.ts:190–195` queries OTel events with
  no offset/user/status/endpoint predicates. Offset and filters are ignored.
- `controllers/stats.ts:159–161,218–220` returns status=success and code=200
  even when the returned event includes an error.
- GET detail at line 202 reads `otel_events`; DELETE at line 232 calls legacy
  `deleteRequest` (`core/stats/database/crud.ts:215–221`, table `requests`).
  The same identifier therefore does not designate the same record in both APIs.
- Filter DELETE at lines 184–192 filters the legacy table, then calls
  `clearOtelDataForUser(userName)` without status/endpoint. That function
  (`core/telemetry/store.ts:244–254`) deletes all user metrics and events.
- An actual-route VM fixture demonstrated an ignored offset/filter, a synthetic
  error mapped to success, GET=200 followed by DELETE=404 for an OTel-only ID,
  and whole-user OTel deletion dispatch for a user+error filter. Independent
  SQL/source review confirmed the mocked boundaries. Real data was not deleted.

## Hypotheses

This is an API contract finding. The current UI has no caller of `openRequestList`,
so ordinary modal pagination or filtered-delete reproduction is **not** claimed.
The active dashboard does fetch initial request history, and user-wide deletion
has a current sidebar caller. An unrelated legacy ID collision is a conditional
additional risk, not an observed deletion. Authorization guards remain present;
this is not a demonstrated cross-user authorization bypass.

## Expected outcome

Decide whether these routes remain supported or are explicitly retired. For a
supported API, use a coherent record identity/dataset for GET and DELETE, honor
or reject unsupported pagination/filters, and preserve actual error semantics.
Deletion counts and scope must describe the records actually affected.

Use an isolated database with two users, successes/errors, both storage formats
and colliding IDs. Verify disjoint pages, filter predicates, GET/DELETE identity,
and preservation of nonmatching events **and metrics**. Keep the existing auth
matrix and test current user-wide deletion separately. No production mutation
is needed. Link BR-21's legacy-route decision, without duplicating its aggregation
tasks or treating the dormant modal as a measured UI regression.

## Решение контракта (2026-09-29)

Маршруты **сохранены** и работают ТОЛЬКО с набором OTel — тем же, который они
читают. То, что этот набор честно исполнить не может, отвергается с внятной
причиной, а не исполняется наполовину: молча проигнорированный фильтр в запросе
на УДАЛЕНИЕ и есть потеря данных.

* Список честно принимает `limit` и `offset` и сужение по `userName`; страницы
  не пересекаются. Мусор в числах отвергается.
* `status` набор отдельным полем не хранит (он выводится из содержимого
  события), конечная точка у всех одна. Такой фильтр отвергается с кодом 400 —
  и на чтении, и на удалении. Именно сочетание «пользователь + ошибки» стирало
  всё.
* Удаление по фильтру требует имени пользователя: фильтр, который ничего не
  сужает, — это «удали всё» под видом выборочного удаления. Ответ содержит
  реальные числа по каждому набору (события, метрики, устаревшая таблица), а не
  голое `ok`.
* Удаление по идентификатору идёт в ТОТ ЖЕ набор, что и подробность. Раньше GET
  отвечал 200, а DELETE — 404, потому что один идентификатор обозначал в двух
  API разные записи.
* Статус и код ответа восстанавливаются из самого события; список и подробность
  отвечают одним и тем же отображением, а не двумя разошедшимися копиями.

## Проверки

18 тестов. Контракт разбора и статуса — 13 без базы. Область удаления — 5 на
ИЗОЛИРОВАННОЙ базе DuckDB во временном каталоге (подменён только источник

даёт непересекающиеся страницы, удаление по идентификатору убирает ровно одну
запись. На прежнем коде падают все пять. Боевые данные не затрагивались.
