# INC-2026-0125 — A Claude message sent while the tab reattaches after a server restart is dropped silently

- **Status:** confirmed. **Priority: high** — user input is lost without any sign.
- **Registration author:** `kacc22`, Bridge executor, lead-directed (2026-11-19). Found during the live candidate check of the 1.0.117 release ([#1055](https://github.com/dykamino-coder/gpui-kamin-ide/pull/1055)).
- **Completion target:** a message sent before the tab is ready either reaches the CLI once the tab is ready, or stays in the input with a visible error. It is never lost silently.
- **Diagnostic PR:** this registration.
- **Fix PR:** none
- **Next step:** change. Sketch: queue the send in the tab until `promptReady` (the queue already exists for messages sent during a turn), or reject it with an explicit error and keep the text in the input. Owner: next Bridge executor.
- **Private evidence:** not required — the card states only state fields and counts.
- **Dependencies:** none.
- **Acceptance:** an automated test of the send path while the tab is not ready, plus a live check: server restart, send within seconds, the turn starts once (or the input shows the error and keeps the text), 3 of 3.
- **Acceptance rationale:** the reattach timing is real only against a restarted server; the decision itself is testable in the webview.
- **Deployment observation owner:** the executor of the fix (stand check after release).

## Symptom

Every Bridge release restarts the server. Right after a restart, while a Claude tab is still reattaching, a message sent from that tab starts no turn. It does not appear in the chat, no error is shown and nothing is queued.

## Confirmed facts

- Path: `bridgeCmd.send`, which is the same path as the Send button (`sendMessageToTab`).
- At the moment of sending the tab reports `promptReady: false`, `busy: true`, `queued: 0`. About 45 s later: no new user entry, no assistant entry, `queued: 0`, `promptReady: true`, the text is not in the chat.
- A/B, 3 attempts each, a fresh Claude chat with one finished turn, send right after `/health` answers again:
  - candidate 1.0.117 / 6.3.194: dropped 3 of 3;
  - published 1.0.116 / 6.3.193: dropped 3 of 3.
  So it predates 1.0.117 and is not caused by #1048.
- Sending the same text again once the tab is ready works.

## Unknown

- Whether the visible input keeps the text when the user presses Enter (the probe path does not read the textarea draft) and whether the Send button is disabled while `promptReady` is false.
- Whether GPT (Codex) tabs behave the same.
