## Symptom

Two different error lines appear in the Bridge console of a Claude session.
The tool calls themselves work; the user's local hooks do not run.

1. On every hooked event, twice per `mcp__user-tools__PowerShell` call
   (KaminIDE 1.0.93, Bridge 6.3.170):
   `PreToolUse:mcp__user-tools__PowerShell hook error — Failed with
   non-blocking status code: spawn error: spawn C:\Program
   Files\Git\bin\bash.exe ENOENT`, and the same for `PostToolUse`. The same
   line was seen for `SessionStart` on 1.0.84 / 6.3.161.
2. In a long session, during a turn of about 36 minutes, twice in a row:
   `PreToolUse:mcp__user-tools__Write hook error — Failed with non-blocking
   status code: Bridge hook dispatch
   {"event":"PreToolUse","type":"command","host":"local"}: Client-host WS is
   not open — local hook unavailable`. The `Write` call itself was executed.

## Environment and versions

- KaminIDE 1.0.93 on Windows 11, Bridge server image 6.3.170; first seen on
  1.0.84 / 6.3.161.
- User hooks: command hooks for all events without a matcher and without an
  explicit shell, plus one `PostToolUse` hook with `shell: bash`. Git Bash is
  installed at the path named in the message.

## Confirmed facts

Symptom 1 — `ENOENT`:

- The hook is started on the client, not in the container. The server sends
  `hook:execute` over the client WebSocket
  (`server/src/core/hooks/dispatcher.ts`), and the client starts the shell
  (`extension/src/main/hooks/executor.ts`). The Windows path in the message
  comes from the client.
- The client starts the shell in the directory the server sends:
  `cwd = req.cwd || os.homedir()`. The server replaces the CLI's directory
  with the client project directory only when the session has one
  (`server/src/core/hooks/routes.ts`: `if (session.cwd) payload.cwd =
  session.cwd`). `session.cwd` is the folder of the client tab. A tab without
  a folder leaves it empty, so the hook request carries the CLI's own
  directory inside the container.
- On Windows, starting a process in a directory that does not exist fails
  with `ENOENT` and Node names the program, not the directory. A direct check
  on the affected machine: starting the same `bash.exe` with a container-style
  directory gives exactly `spawn C:\Program Files\Git\bin\bash.exe ENOENT`;
  with the home directory it runs.
- Server hook audit log of the acceptance server, 2026-11-11: 159 local hook
  executions ended with this `ENOENT` (104 user hooks, 55 plugin hooks) in
  four sessions, and these sessions have no successful local hook at all. One
  of them is a session started for this research from a tab without a folder;
  it fails on every hook event. Sessions with a folder had 11 successful local
  hooks the same day.
- The same failure follows from any project directory that no longer exists
  on the client (not reproduced separately).

Symptom 2 — `Client-host WS is not open`:

- The server fails a local hook at once when the client socket of the session
  is not open at that moment (`dispatchLocal`: `ws.readyState !== 1`). It
  does not wait for the client to come back.
- Tool calls are treated differently: an MCP call for a detached session
  stays pending and is sent again when the client reattaches
  (`server/src/core/pty/session-mcp-call.ts`). This explains the owner's
  observation: the `PreToolUse` hook failed while the socket was closed, and
  the `Write` call ran after the client reconnected. `user-tools` calls run
  only on the client, so the executed call shows that the client did come
  back.
- The client reconnects by itself, first after 1 s, then with a doubling
  delay up to 30 s (`extension/src/main/ws/connection-manager.ts`). The
  server keeps a detached session for 10 minutes.
- Audit log of the acceptance server, 2026-10-30 to 2026-11-11: 14 local
  hooks ended with this message. In all of them the client was gone for good
  (session detached and destroyed after the grace period, or the hook was the
  session's own `SessionEnd`); none of them is the owner's `PreToolUse` case,
  which is not in this log.

## Hypotheses

- The owner's sessions with symptom 1 were started from a tab without a
  folder. Not checked on the owner's sessions; the fix must not depend on it.
- In the owner's case of symptom 2 the socket was closed for a short time.
  The duration is not known: the lifecycle journal of the acceptance server
  has no reattach near such a hook failure.

## Expected outcome

- A local hook never starts in a directory that does not exist on the client.
  The client uses the session's project directory when it exists, otherwise
  the user's home directory, and the hook's stdin `cwd` and
  `CLAUDE_PROJECT_DIR` name the directory actually used.
- When the client socket is closed at hook time, the server waits a short
  bounded time for the client to reattach and then runs the hook once. A hook
  that was already sent is never sent again.
- When the client does not come back, the console gets one restrained line
  for that disconnect, not a line for every hook call.
- Gate on the exact candidate, on a copy of the owner's profile with a test
  hook that leaves a checkable side effect: no hook error on `SessionStart`,
  `PreToolUse` and `PostToolUse` in a tab without a folder and in a tab with
  one, the side effect is present, and a client WebSocket break in the middle
  of a session followed by recovery leaves no hook error.

## Fix #743 (2026-11-11)

[#743](https://github.com/dykamino-coder/gpui-kamin-ide/pull/743) (`83053f75`): the client starts a hook in the tab's folder
when it exists on the client and in the home directory otherwise; the server
waits a bounded time for the client to reattach before a local hook and
reports an absent client once per disconnect. Live gate on the candidate
(Windows, profile copy, test hooks that record each run): a tab without a
folder, a tab whose folder was removed, a tab with a folder and a resumed
session ran every hook with no error. A 2.5 second socket cut while a hook
was in flight reported that one hook once (it ran, its answer was lost, it was
not sent again); a 20 second cut during a client tool call produced no hook
error; with the client away for 30 seconds the transcript holds exactly one
hook error for the disconnect and the following hooks were skipped quietly.
Details are in the PR. Not run live: plugin monitors and external MCP servers
in a tab without a folder. Known limit: an external stdio MCP server without a
configured directory still inherits the host process directory. Found during
the gate and registered separately: hook matchers for native tool names
([INC-2026-0106](INC-2026-0106.md)).

## Verification on the released build (2026-11-11)

Run by studiohost. Client: KaminIDE 1.0.94 installed from the installer of the
GitHub Release on Windows 11, started on a copy of a profile whose test hooks
record each run with the process directory and the hook input. Server: the
acceptance Bridge server from image `dykamino/open-claude-bridge:6.3.171`.
One turn with seven tool calls in each of three tabs.

| Tab | Hook process directory and input `cwd` | Relative `Write` and `Glob` | Hook errors |
| --- | --- | --- | --- |
| with a folder | the tab folder | work in the tab folder | none |
| without a folder | the home directory of the test profile | work in the home directory | none |
| folder that does not exist | the home directory; the missing folder is not created | work in the home directory | none |

- The hooks without a matcher ran once for the prompt, for every tool call
  (before and after it) and for Stop in all three tabs. The chat shows no hook
  error, `ENOENT` or `Client-host WS is not open` line, and the server log
  of the run has no such line.
- Baseline on the same day with KaminIDE 1.0.93 / server 6.3.170: a relative
  `Glob` in the tab with a folder found nothing.

Limits of this run: the socket cuts and the resumed session of the candidate
gate were not repeated on the released build; the reconnect wait is covered by
that gate and by the unit tests. The text of the Bridge Console view could not
be read by the driver; the absence of error lines was established from the
chat and the server log. The owner's own profile and hooks were not used.
Plugin monitors and external MCP servers in a tab without a folder were not
run.
