## Symptom and available evidence

Two September 4 screenshots accompany the report. The stronger example shows /rename and its acknowledgment in Console and a matching local-command record in Chat, while the selected Projects row still displays a fallback Session N label. The other example shows a fallback label for a meaningful conversation, but does not prove a separate title already existed in metadata.

## Limits and source entry points

Acknowledgment does not prove persisted metadata or a broken broadcast. Native display label, CLI custom title and automatic topic may have distinct precedence. At the intake baseline, server/src/core/pty/session-io.ts sends session:title, extension/src/main/ws/handle-server-message.ts handles it, and tab-manager.ts/tree-enrichment.ts carry sessionTitle. These are investigation entry points, not a located failure. BR-29 concerns hover-to-rename/focus, not the full CLI title propagation contract.

## Maintainer research deliverable

Map each title field, its authority and persistence. Trace /rename/custom-title, server notification, extension tab update/tree enrichment, host snapshot and native Projects label, including invalidation of cached values. Distinguish user-assigned labels from generated fallback and automatic titles before deciding whether all views should share one value.

Use a synthetic session to compare immediate state, tab switch, reconnect, app restart and archived-session reopen. Check explicit native rename versus CLI rename precedence, repeated renames and stale title events. Keep the first screenshot's automatic-title expectation separate unless it reproduces the same contract violation.

## Acceptance and next handoff

Return a field/flow map and a minimal stale-label reproduction or a documented product decision on separate names. A later fix must persist and display the agreed label without overwriting a newer/manual name and pass automated event-order tests plus Windows Projects/Chat verification.
