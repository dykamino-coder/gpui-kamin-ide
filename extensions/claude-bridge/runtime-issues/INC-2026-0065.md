## Accepted outcome — 2026-10-19 reconciliation

The accepted #347 instrumentation identified `host-received → handler-resolved
→ reply-false`, with `hidden=true` and no `renderer-received`: the extension
host refused replies to the hidden Console view, and `BridgeHost` dropped them.
It now defers refused replies per view (cap 256), flushes on reveal in order,
and drops the queue on dispose. Startup read requests use bounded retries;
mutating requests are not retried. This identifies the actual reply refusal;
it does not prove every hypothetical loss point in the original report below.

Accepted Windows candidate: `202277558d96866013ba252eab91d968d4c6e06a`.
On that exact head, **8/8 GPU and 8/8 WARP** fresh starts with host and isolated
profiles left the loader; all deferred replies flushed on reveal. The pre-fix
control hung in 3/4 starts. Extension tests (171), webview tests (285), typechecks
and regenerated runtime artifacts were accepted in #347. This reconciliation
records that existing gate and immutable evidence; it does not claim another
live run. The published 1.0.75 tag contains the merged fix.

The remaining sections preserve the original report and pre-fix hypotheses;
their request for instrumentation has been satisfied by #347.

## Symptom

On a fresh profile the Bridge console page sometimes never leaves the
"Restoring your session…" loader. The window is alive and the host answers
manual requests; only the console page stays in its initial state.

## Confirmed facts (main `b03ffd5`, Windows, 2026-10-16)

- Reproduced in 3 of 4 fresh starts on a GPU machine; the same symptom was seen
  on `main` before the recent performance PRs, so it is not a regression of
  them.
- The loader (`LoadingCue` in `EmptyState.tsx`) is shown while `initializing`
  is true in `webview/src/hooks/useInit.ts`. `init()` awaits its start-up
  requests (config, tabs, restored tab state, …) one after another and has
  neither a timeout nor a retry, so a single lost reply keeps `initializing`
  true for good.
- In hung runs the console page posts only about 20–23 messages instead of the
  49–57 of a healthy start, i.e. it is stuck waiting for one reply and never
  sends the later requests.
- In hung runs the shell's per-view delivery queue is empty and the host
  answers manually issued requests in 19–32 ms, so the host and the queue are
  responsive after the hang.
- The console CEF view is created hidden (`visible = false`) at start-up and
  loads for about 20 s before it is shown.
- A previous incident of the same family (chat stuck on the same loader because
  replies were discarded) was fixed in `web/outbox.rs`; this is a different
  loss point.

## Hypotheses

1. A host reply is dropped between the host and the page: `web::deliver`
   returns silently when the view is not registered yet, or a pull dispatched by
   `execute_script` reaches a page that has not defined `__kaminPull`, or the
   `/__pull` response is lost after the outbox was emptied (`take_all`).
2. A page request is dropped on the way to the host: the page's fire-and-forget
   `fetch('/__ipc')` fails silently, `post_body` cannot decode the request body,
   or the shell has no host client yet and `handle_inbound` discards the message.
3. A reply reaches the page before its React listener is subscribed (the shim
   queues only until `DOMContentLoaded`).

## Expected outcome

The first lost message is identified with logs from an instrumented build, the
cause is fixed at its source, and `init()` recovers from a lost reply instead of
waiting forever. Windows runtime acceptance on WARP and on a GPU shows no hang in
at least 8 fresh starts on the exact head.

## Missing evidence and blockers

At registration the exact lost reply and layer were unknown. The accepted
instrumented captures and #347 identified and fixed the hidden-view refusal
above. No blocker remains for this bounded incident. General transport-policy
work continues under BR-24, with its own prerequisites and acceptance.
