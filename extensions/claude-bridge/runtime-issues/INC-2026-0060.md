## Symptom

During live Windows acceptance, a 9-line TypeScript file that fits in the
editor viewport was open with the caret on line 1. A single click on line 8
moved the whole content up, so line 1 was partly or fully hidden under the
editor path bar. No scroll wheel or keyboard input was used. The same result
was observed on the integration line and on `main` at `a0a21dc`.

## Confirmed facts

- Screenshot measurement: the line pitch is one editor line (20 logical px).
  The content shift was about 24 logical px in one layout and about 14 logical
  px in another, i.e. it is not a whole number of lines and depends on the
  editor height.
- Source checked at `259925d`: the code editor `InputState` allows vertical
  scrolling beyond the last line. `TextElement::prepaint`
  (`vendor/gpui-component/src/input/element.rs`) sets the scroll size to
  `lines * line_height + max(viewport / 2, 3 lines)`, and
  `InputState::update_scroll_offset` clamps the offset to
  `scroll_size - viewport`. For a 9-line file this leaves
  `180 - viewport / 2` px of possible scroll, which matches the measured,
  layout-dependent shift. So some path requests a downward scroll for a caret
  that is already visible, and the clamp limits its amount.
- A mouse click goes through `InputState::on_mouse_down` → `move_to` →
  `scroll_to(offset, None)`; `prepaint` additionally nudges the offset when the
  caret is within `top_bottom_margin` of the viewport bottom.

## Hypotheses

- Which of `scroll_to` (uses `last_bounds`, the previous frame's text bounds)
  and the `prepaint` nudge (uses the current bounds and margin) produces the
  request is not yet proven. A bounds value that does not match the visible
  viewport, or the shell's surrounding layout (path bar, sticky-scroll overlay),
  are candidates. The fix must be chosen after a deterministic reproduction.

## Research result (2026-10-10)

- A click on a visible line does **not** scroll. Reproduced neither in the live
  app (isolated dev build with temporary scroll logging: clicks on lines 8, 9,
  the gutter, line ends and the empty area below the text all kept offset 0)
  nor in gpui `VisualTestContext` tests with the real `Input` element.
- A mouse wheel over the same 9-line file scrolls it by 28 px in that layout:
  the code editor's scroll size is `text + max(viewport/2, 3 lines)`, so the
  overscroll limit is `text + max(H/2, 60) − H`, which matches both measured
  shifts. The acceptance after-shot shows no caret on line 8 and the line-1
  highlight under the path bar, i.e. overscrolled content rather than a caret
  move; the "click" in the report did not move the caret.
- The original Electron editor ran Monaco with `scrollBeyondLastLine: false`.
  The GPUI port inherited the upstream `gpui-component` overscroll instead.
- Fix: a vendored `InputState::scroll_beyond_last_line(bool)` option (upstream
  default kept) disabled for editor tabs; regression tests cover the wheel on a
  short file, a long file still reaching its last line, and clicks.

## Expected outcome

A file that fits the viewport cannot be scrolled (wheel or click); a long file
scrolls until its last line reaches the bottom, without an empty tail.
Scrolling to reveal a caret that is actually outside the viewport keeps working.
