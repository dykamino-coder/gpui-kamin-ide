## Verified webview source

Audited fresh `origin/main`: `f441fdc2a9218dce5da4bb1922db82f9ea3b3960`,
2026-10-20. Source links resolve inside this repository; line numbers refer to
that audited revision.

- [JsonlViewer.tsx](../webview/src/components/jsonl-viewer/JsonlViewer.tsx#L422-L475)
  computes `hiddenCount = max(0, visibleMerged.length - renderCap)` and takes
  the tail slice `shown`. It renders the exact
  [earlier-messages pill](../webview/src/components/jsonl-viewer/JsonlViewer.tsx#L553-L562)
  when hiddenCount is positive. N counts projected rows outside the render cap,
  not the transcript total, and does not prove an empty resident store.
- The viewer has an initial render cap of **150**, grows it by **400** on near-top
  scroll and can shrink it at the bottom after a delay. This is bounded tail
  rendering with scroll-up loading; a counted row need not be a mounted drawable
  message. See [caps](../webview/src/components/jsonl-viewer/JsonlViewer.tsx#L27-L32)
  and [window transitions](../webview/src/components/jsonl-viewer/JsonlViewer.tsx#L87-L175).
- [derived-cache.ts](../webview/src/components/jsonl-viewer/derived-cache.ts#L80-L145)
  selects the segment, merges/chains records and filters the visible projection.
  `JsonlEntry` runs **after** the cap slice; null results are skipped. A positive
  pill can therefore coexist with no prepared rows if all selected rows are
  non-drawable. This is a possible mechanism, not evidence about the owner's
  actual rows. BR-22 tracks predicate/recent-tip/renderer divergence and possible
  stale derived/vnode state.
- [signals/jsonl.ts](../webview/src/signals/jsonl.ts#L43-L50) defines resident
  window **4,000**, trim slack **500**, scroll-up ceiling **16,000** entries.
  [Clear and trim](../webview/src/signals/jsonl.ts#L560-L644) track refill debt
  and enforce caps. Entry retention differs from the 150-row render cap and
  pill count; 1,049 is not a configured retention threshold.
- [useBridgeListeners.ts](../webview/src/hooks/useBridgeListeners.ts#L400-L474)
  starts replay state only on explicit `replayComplete === false`, completes it
  asynchronously, and clears Chat entries on `status.compacted` before refill.
  A compact-refill watchdog exists. Ordinary replay start does **not** itself
  clear Chat entries. Agent replay staging is separate; index-only updates do
  not restart replay on the audited main.

## Candidate mechanisms — all hypotheses for this report

1. **Counted but non-drawable tail or stale render state.** More than 150
   projected structural/recent-tip records could displace drawable history,
   or cached projection/vnodes could diverge from retained entries. Compare
   predicate acceptance, null-render reasons, prepared count and actual DOM rows.
2. **Reset followed by interrupted/chunked replay.** Compact/reset clears the
   store; successive chunks, superseding generations, delayed completion or
   incomplete refill might temporarily expose a misleading tail. A correlated
   trace is needed. A completely empty store alone does not explain a positive
   pill: some projected rows must exist when it renders. Trace replay generation,
   chunk ordering, clear reason and refill watchdog. Same-path rewrite now also
   signals reset in [replayRewrittenFile](../server/src/core/pty/jsonl-watcher.ts#L1072-L1080)
   following the INC-0068 fix.
3. **Retention/segment/window transition.** Trim, segment selection or cap shrink
   might leave a tail without drawable rows or require delayed refill. Record
   resident count, dropped range, refill debt, selected segment and cap. A cap's
   existence does not prove loss. Distinguish background retention from active-tab
   trimming; do not blame an unrelated tab eviction without evidence.
4. **Replay pressure around reconnect.** INC-0069's retired-subagent replays may
   amplify delivery/render load; their relation to this disappearance is
   unmeasured. INC-0067/0068 own distinct compact/replay defects. Fixes
   [#377](https://github.com/dykamino-coder/gpui-kamin-ide/pull/377) and
   [#378](https://github.com/dykamino-coder/gpui-kamin-ide/pull/378) are merged on
   the audited main with source acceptance recorded; this does not prove this
   Chat symptom fixed. Preserve their publication/field-observation distinctions.

## Classification and fix candidate (2026-10-20)

Source/synthetic classification on fresh `origin/main`
`4d72a247f371a5ce9e2f48d44e95e7a982a5cd20`, following BR-22's 2026-10-12 handoff
(a controlled case may justify a bounded fix with the original Windows gate;
it does not explain the historical episode).

**Boundary.** The pill needs `visibleMerged.length > renderCap`, so at least
151 projected rows existed while it showed (about 1,199 for N ≈ 1,049). A
cleared or refilling store shows the loading cover or the empty placeholder,
never the pill, so reset/replay alone cannot produce this state. The first
divergence is **projection → prepared rows**: the window took the last 150
*projected* rows, and only then did the renderer decide whether each draws.

Two concrete mechanisms, reproduced deterministically with the real render
model and the real `JsonlEntry`:

1. **Recent-tip bypass.** In
   [derived-cache.ts](../webview/src/components/jsonl-viewer/derived-cache.ts)
   every row after the last `assistant` (except the bookkeeping types list)
   skipped `entryIsVisible` entirely. 300 turns followed by 200 invisible
   `task_reminder` attachments gave 800 projected rows, the pill
   "650 earlier messages" and **zero** drawn rows — the reported picture. It
   recovers as soon as a new assistant row moves the tip, which matches
   "comes back later". Any long run of housekeeping rows after the lead's last
   answer (hooks, reminders, merged tool results, idle periods with Agent
   Teams) qualifies. Whether the owner's session had such a run is unverified.
2. **Mounted-but-empty rows.** `JsonlEntry` returned a vnode for rows whose
   component then renders nothing (`SystemEntry` for empty `away_summary`,
   `turn_duration`, empty `init`; `AssistantEntry` with only empty
   text/thinking; empty compact summary; empty tool group). Such rows took a
   slot as an empty wrapper of almost no height, so 150 of them left only the
   pill in the viewport.

Checked and not found to produce the pill: retention trim and older-page
prepend both bump the structure version, so the segment slice and the render
model recompute together; compact/reset clears go through the cover or the
empty placeholder; INC-0067/0068 staging changes replay start and reset
signalling, and a reset still passes through that cover/placeholder path. The DOM/viewport boundary (content-visibility, anchoring)
was not exercised; it needs the Windows run.

**Fix in the Fix PR.** The window now counts only rows that draw
([render-window.ts](../webview/src/components/jsonl-viewer/render-window.ts)):
walk back from the end and stop after `renderCap` drawn rows. A non-drawable
row can never take a slot, so a projection with any drawable row always mounts
its last drawable rows. `JsonlEntry` returns null exactly when the component
would draw nothing; the components share one set of checks
([entry-draws.ts](../webview/src/components/jsonl-viewer/entry-draws.ts)). The recent tip now
bypasses only the chain-membership walk, its original purpose. A store whose
projection draws nothing shows the empty placeholder instead of a blank panel.
Instrumentation:
[chat-window-diag.ts](../webview/src/components/jsonl-viewer/chat-window-diag.ts)
counts empty-window-with-rows episodes, renders and counted-but-empty rows
(numbers only), warns once per episode in the console, and is included in the
stethoscope `DiagnosticButton` dump as `chatWindow` and in
`window.__chatWindowDiag`. It is not yet forwarded to the extension-host
`incident.log`; that would need a separate extension allowlist change.

BR-16 stays dependent on this classification and is not changed. BR-22 and
this incident stay open until the Windows gate passes and the fix is accepted.
