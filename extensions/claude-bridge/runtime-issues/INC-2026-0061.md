# INC-2026-0061 — Quick Pick with few items keeps a tall empty panel

- **Status:** confirmed
- **Registration author:** @dykamino-coder (owner-directed live acceptance follow-up)
- **Priority:** P3
- **Diagnostic PR:** pending
- **Fix PR:** none
- **Next step:** change — size the Quick Pick panel by its content up to the existing limit `min(60vh, 100vh − 84px)` and keep the list scrollable and the multi-select actions row visible when the limit is reached; Change/Fix PR by the implementer, acceptance by the maintainer.
- **Private evidence:** pending
- **Dependencies:** none
- **Acceptance:** **Windows runtime merge gate:** required — in an isolated KaminIDE instance show a Quick Pick with three items (one separator) and one with more items than fit; the first panel ends just below its last item, the second is capped and scrolls; filter input focus, hover/click on items and scrim click still work.
- **Deployment observation owner:** none

## Symptom

During live Windows acceptance, an extension `showQuickPick` with three items
(one under a separator) opened a panel about 60 % of the window high. The
items occupied the top fifth of it; the rest was empty. The same result was
observed on the integration line and on `main` at `a0a21dc`.

## Confirmed facts

- Source checked at `259925d`: `crates/shell/src/ui/quick_pick.rs` gives the
  panel a fixed height `h(min(0.6 * vh, vh − 84))`, and the list wrapper uses
  `flex_1`, so the panel never shrinks to its content.
- The code comment attributes this to the original Electron renderer: its
  `.overlay` is a flex row without `align-items`, so the `.panel` (with
  `max-height: 60vh`) is stretched. The fixed height was therefore an
  intentional parity choice, not an accidental regression.
- The owner accepted the tall empty panel as a defect in live acceptance; the
  expected behaviour (also VS Code's) is a panel sized by its content up to the
  same limit. The fix is an intentional deviation from that original CSS
  stretch and keeps all other `.panel`/`.list` metrics.

## Hypotheses

none. Whether the vendored layout sizes a `flex_1` list inside an auto-height,
max-height-capped column correctly must be verified at runtime.

## Expected outcome

Short pickers end below their last row (plus the list padding); long pickers
stop at `min(60vh, 100vh − 84px)` and scroll inside the list; the
`canPickMany` Cancel/OK row stays pinned under the list.
