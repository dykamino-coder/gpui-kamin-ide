# INC-2026-0020 — Windows sleep/RDP crash requires graphics recovery diagnosis

- **Status:** investigation (field cause unknown; unsafe GPUI error paths confirmed in source)
- **Priority:** P1
- **Diagnostic PR:** enclosing Diagnostic PR for this incident
- **Fix PR:** none
- **Private evidence:** [INC-2026-0020](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/e80333d1ac16d1ec70d8a055a5db421d83afd30c/incidents/INC-2026-0020)
- **Dependencies:** none; related source findings INC-2026-0021/0022/0023
- **Acceptance:** automated failure-state coverage + disposable Windows sleep/RDP/device-loss gate
- **Corporate observation owner:** none

## Symptom

After Windows sleep or an RDP disconnect lasting approximately 5–10 minutes,
reconnect reportedly shows “KaminIDE has stopped working”. The exact build,
faulting PID/process role, exception, dump and graphics recovery timeline have
not been obtained. Process-group CPU, memory and GPU counters cannot identify
which process failed or establish a memory leak, OOM or graphics reset.

## Confirmed facts

Source revision: `a34ab4892058bcacc00de8d97ae951fb60551780`. The following are
independent source defects, not a reproduced explanation of that field crash.
Paths below are relative to `vendor/gpui/src/platform/windows/`.

- `directx_renderer.rs:880–913` updates cached dimensions, manually releases its
  render target and removes the target view before fallible ResizeBuffers and
  resource recreation. An error leaves the released target slot and absent
  view reusable. The callback at `events.rs:224` only logs the error.
- A same-size resize then returns success without repair; another size change
  releases the target again and unwraps the absent view. Draw can unwrap the
  view at renderer line 411 if its earlier buffer update succeeds. Ordinary
  resource destruction also releases that target at lines 1935–1939.
- Device recovery releases existing resources and devices at renderer lines
  463–474 before fallible construction at 477–494. Replacement occurs only at
  500–504. The five-attempt helper in `directx_devices.rs:23–40` therefore retries
  using already destroyed ownership after an intermediate error.
- `platform.rs:1056–1081` logs success and dispatches device recovery even when
  platform device creation exhausted its attempts. This makes the existing
  success message insufficient diagnostic evidence.

Successful first-attempt recovery avoids the retry failure path. Present errors
are logged rather than directly unwrapped. Device-removed polling and a VSync
sleep fallback exist; this is not an absence of all recovery handling. Atlas
resources are reset. Separate blur/blend cache generation is tracked in INC-2026-0023.

A source-anchored deterministic model confirms these transition orders without
executing Rust, COM, an unsafe destructor or Windows graphics. No native crash
was reproduced. [Microsoft device-loss guidance](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios)
recognizes fallible Present/ResizeBuffers and requires device-resource recovery.

## Hypotheses

A sleep/RDP display transition could trigger resize/device loss, followed by a
failed allocation and unsafe recovery state. Neither that transition chain nor
a driver fault has been established in the reported event. CEF software startup
under RDP does not disable GPUI Direct3D; the affected process remains unknown.

## Expected outcome

First establish build/PID role, WER exception/module/stack, ordered resize and
GetDeviceRemovedReason HRESULTs, recovery attempt stages, adapter, CEF mode,
resolution/DPI and actual sleep versus RDP disconnect. Preserve private dumps
and screenshots outside the public card.

Make failed/unavailable renderer ownership explicit and retry-safe; clean partial
attempts and accurately report terminal failure. Automated gates cover failure at
each allocation stage, same/different-size retry, draw and destruction. Disposable
Windows gates separately exercise sleep and 5–10 minute RDP disconnect, fixed and
changed dimensions, CEF software/accelerated modes and repeated recovery cycles.
Successful source checks alone cannot close the reported field incident.
