# INC-2026-0020 — CEF renderer crash after Windows sleep/RDP return

- **Status:** investigation (renderer termination confirmed; underlying cause unknown)
- **Priority:** P1
- **Diagnostic PR:** #66
- **Fix PR:** none
- **Private evidence:** [INC-2026-0020](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/700220821be69a51da2faef16b9baf26a856c8e7/incidents/INC-2026-0020)
- **Dependencies:** none; related INC-2026-0021/0022/0023/0024/0025/0026
- **Acceptance:** attributed renderer failure + Windows sleep/RDP and panel-recovery gate
- **Corporate observation owner:** deployment owner supplied logs; further observation pending

## Symptom

After reported Windows sleep or an RDP disconnect lasting about 5–10 minutes,
a Windows stopped-working dialog appears. The owner clarified that closing the
dialog restored the Claude Bridge and Console panels without restarting the IDE.
New logs narrow this incident to CEF renderer termination while the shell survives.

## Confirmed facts

- Supplied `crash.log` identifies KaminIDE 1.0.55. It contains a main startup and
  two `renderer-terminated` callbacks about 1.5 seconds apart, both `crashed`
  with error code `-2147483645` / `0x80000003`. Microsoft identifies this as
  [STATUS_BREAKPOINT](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55).
  It does not name the faulting CHECK, module, GPU error or memory condition.
- The unchanged PID is the observing main process: `crates/crash/src/lib.rs`
  writes its own PID, and `note_renderer_termination` does not receive the
  child's PID. Two view callbacks do not establish two distinct crashed OS
  processes. The second opaque view class does not independently identify Console.
- `crates/shell/src/web/browsers.rs:137–157` records termination and navigates
  the affected main frame to its current URL. This explains the reported panel
  reload. That callback does not restart the shell or Node host.
- `diag.log` contains two termination markers and continuing frame reports
  afterwards, with no subsequent boot marker. Nearby software-frame reports
  establish software-copy activity. Metrics lack timestamp/PID, so row order
  cannot establish precise crash-time resource use or complete per-view mode.
- The source files governing this callback and crash logging are identical in
  documented installer source `c599cae23afb8393ed1377a67f91b13082902115` and audited
  main `a34ab4892058bcacc00de8d97ae951fb60551780`. The version label alone does
  not certify the exact installed executable or libcef DLL.

- The newly supplied host `data/incident.log` contains one `host-log-start` from
  September 4. `src/kamin-host/incident-log.ts:54–91` writes host startup and
  extension-host exit events, not periodic Bridge samples. A startup-only file
  is expected while the child stays alive; it does not show telemetry stopped.
- `host.log` contains four untimed rejected RPCs with `shell client disconnected`.
  `src/kamin-host/ws-server.ts:93` fails all pending calls on one shell socket
  close: these are not four proven disconnects or evidence of a remote Bridge
  server failure. Subsequent child watchdog output does not establish an exthost
  restart. Two timers in the same child produce the paired lag messages.

The files still contain no faulting module/stack or extension Bridge resource
trail. They remain useful after panel reload; a full IDE restart is not required
to obtain existing records. Main restart rotates `crash.log` and may truncate
an oversized `diag.log`; submitted originals have been preserved privately.

## Hypotheses and reclassification

The previous main-process GPUI fatal hypothesis is secondary for this episode:
it does not explain the surviving main observer and automatic panel reload.
The independently confirmed unsafe GPUI recovery paths are preserved in
INC-2026-0025, rather than treated as the renderer crash's root cause. The effect
cache and accelerated CEF defects in INC-2026-0021/0022/0023 remain separate.

A Chromium fatal trap, memory pressure or a graphics transition remains possible,
but the exception code does not distinguish them. Missing web-hook records do
not prove missing helper packaging. Retaining `error_string` alone may merely
repeat an exception label; it is not guaranteed to supply a fatal CHECK message.

## Expected outcome

Correlate actual renderer PID/image and generation, exception module/address/stack
or bounded CEF fatal diagnostic, installed CEF build, and sleep/RDP/display events.
Read `%LOCALAPPDATA%\kaminide-gpui-dev\data\globalStorage\dykamino-studio.claude-bridge\incident.log`
and its `.1`–`.3` generations for retained renderer samples and Bridge transitions.
`bridge-host.ts:180` installs diagnostics under `context.globalStorageUri`;
`src/kamin-host/services/storage.ts:152–153` derives this directory from dataRoot.
The separate `data/incident.log` records host startup/exthost exits. This corrects
the earlier request to use that host file as the pre-crash resource trail.
INC-2026-0026 tracks a confirmed extension-emitter rotation gap; corruption of
the actual field Bridge generations has not been demonstrated. Keep raw logs/dumps
private. Correct the misleading implication that an observer PID is the victim.
Existing Windows Application/WER records around the two callbacks can supply the
missing executable/module/PID; saved session state cannot substitute for them.

After attribution, use a disposable Windows gate for sleep and 5–10 minute RDP
disconnect, long-running and fresh sessions, and relevant rendering modes.
Check shell survival, successful panel load, Bridge handshake/subscriptions,
Console state, pending input and absence of reload loops or growing resources.
Reported visual recovery alone does not prove every panel contract recovered.
No functional fix or native reproduction is included; the incident stays open.
