## Correction (2026-11-13, kmaint2)

The finding was a measurement error. The toast detector checked the toast
background at one fixed row of the capture and the progress bar at another. A
single-line `Session finished` notice is drawn lower, so both checks missed it.
Counting pixels of the toast background colour over the whole capture shows:

- candidate of #834 (`94ebd71c`), real turn end in a background session: the
  notice appears, its countdown runs, and it closes by itself after about 8 s;
- `main` without #834: the notice appears and stays (sticky, the old BR-23
  behaviour);
- candidate of #854: the same as #834.

The app's diagnostics log of these runs records the toast animation for each
completion. The record below is kept as history; its symptom was not real.
## Symptom (original report, invalid)

In a KaminIDE window, a message is sent in session A and session B is then made
the active tab. The turn in A completes (the reply is shown when A is opened
again), but no `Session finished` notice appears in the main window during the
following 20–25 seconds.

The same window shows the notice for the built-in test trigger
(`notifications:test`), which calls the same `spawnToast` `finished` path.

## Environment and versions

- Candidate of PR #834 (`94ebd71c`) and `main` `84f9f198` without #834; same result on both.
- Windows 11, isolated profile copy, authenticated acceptance stand server.
- Notice presence was measured on app-rendered captures of the main window.

## Source facts (still true; they do not show a defect)

- `core-ipc.ts` `ConnectionManager.onSessionIdle` suppresses the notice only when the tab is both the active and the displayed tab. In the runs, the finishing tab was neither.
- `configureToastGate` is not called in production, so `notificationsEnabled()` keeps its default `true`.
- The test trigger reaches the main-window notice on the same build, so rendering and the host API are not the failing part.
- `onSessionIdle` is called only from `SessionIdleTracker`, which fires on a debounced `working → idle` transition after a recent working spell, outside the reconnect settle window.

## Not checked

- Whether the server sent `isWorking` states for the background tab during the run, and whether they were hook-driven or from the OSC title heuristic.
- Whether the settle window (held until `replayComplete`, capped at 60 s) was still active after the tab switch.
- Behaviour on the installed 1.0.94 release and with a session that was not restored at start.
