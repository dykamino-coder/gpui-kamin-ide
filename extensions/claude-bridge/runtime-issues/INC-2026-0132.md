## Confirmed source cause

At `2212d6e14d701b3184a200cd742413667175ad08`, `VirtualPty.pid` is 0 and
Dashboard passes it to `getProcessTreeStats`. That function builds parent-to-child
edges and follows them even when the requested root is absent. Linux PID 1
has parent 0, so a traversal from the sentinel 0 reaches the container's
process tree and sums its RSS as if it belonged to the Codex session.

The same traversal can attribute orphaned children to an absent PTY root,
contradicting the function's documented null-for-missing-PID contract.

## Fix and evidence boundary

Reject nonpositive, noninteger and absent root PIDs before traversing. Keep the
existing positive-root aggregation, CPU calculation and sibling isolation.
Regression tests populate the real sampler from synthetic `/proc` rows and
use the real VirtualPty for the sentinel case; the zero-PID and absent-parent
cases fail on the original source.

This establishes a counter-accounting defect, not an actual Codex memory leak
and not why the operator's first turn failed. The exact large number reported
by the operator is not retrospectively attributed without the original field
and process capture. No sessions are killed and no CODEX_HOME protection is
changed. Docker and corporate deployment observations have not run locally.

## Independent check 2026-11-26 (merged source, before publication)

Two containers of their own on the published 6.3.205 image, without network,
account or model: one unchanged, one with the server source of `main`
`6ca4ccfb5` copied over it. A client opened `/ws/terminal` inside each
container and recorded frame order and visible text (no environment values).

- On the real Linux `/proc` of the container, `getProcessTreeStats(0)`
  returned the whole container tree (487 MB) on 6.3.205 and `null` with the
  merged source; PID 1 and the server's own PID keep their tree totals, an
  absent PID stays `null`.
