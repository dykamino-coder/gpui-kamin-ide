## Symptom

In the Claude Bridge chat webview, some assistant messages that the Bridge
Console (the CLI terminal view) prints between tool calls — short progress
narration of the form "Understood: … first I will fix the build error" or
"Build succeeded … now doing X" — never appear in the chat. User messages,
other assistant prose and the tool-call groups render normally. Reported by the
owner on 2026-10-15 with a screenshot, a chat diagnostic dump and the CLI
session transcript of the same session.

## Environment and versions

- KaminIDE chat webview (`extensions/claude-bridge/webview`) at the owner's
  current build; Bridge server in a container, CLI session transcript tailed by
  the server.
- Claude Code CLI `2.1.296` for the affected turns (`thinkingDisplay: "updates"`);
  earlier turns of the same session were written by `2.1.284` (no
  `thinkingDisplay` field) and `2.1.236`.

## Confirmed facts

- Every missing text is **not** a `text` block: it is a non-empty `thinking`
  block. The CLI persists each such turn as separate JSONL rows sharing one
  `message.id`: `thinking` (empty text, signature only, `apiBlockIndex: 0`),
  `thinking` (the narration text, `apiBlockIndex: 1`), then one or more
  `tool_use` rows (`stop_reason: "tool_use"`), followed by the user
  `tool_result` row. Under CLI `2.1.296` both thinking rows carry the top-level
  field `thinkingDisplay: "updates"`; the TUI prints that text as narration.
- In the transcript, all 151 messages with non-empty thinking have this shape
  (66 under `2.1.296` with `thinkingDisplay: "updates"`, 85 under `2.1.284`
  without the field). None contains a `text` block.
- The chat store has all of them: the chat diagnostic dump holds one merged
  store entry per such `message.id` (rows are merged by `message.id`; the
  server projection strips only the thinking `signature`). Its `preview` is
  empty because previews read `text` blocks only.
- The render model hides them: in the dump's `render.visibleTail`, the store
  entry of the second screenshot message is rendered only as
  `tool-group-<its uuid>`, i.e. folded into the tool-call group.
- Source cause (`webview/src/components/jsonl-viewer/utils.ts`):
  `isToolOnlyAssistantEntry` treats thinking blocks as invisible ("Thinking
  blocks are invisible in the current viewer"), and `splitProseFromTools`
  splits prose from tools only for `text` blocks. After
  `mergeAssistantEntriesByMessageId`, the entry `[thinking(empty),
  thinking(narration), tool_use]` therefore counts as tool-only, and
  `groupConsecutiveToolCalls` folds the whole entry into a `tool_group`, whose
  collapsed summary shows only tool counts. `isInvisibleAssistantEntry` already
  treats non-empty thinking as visible, so the two predicates disagree.
- Not involved: `uuid-dup` drops (the dump's 400 drops are re-deliveries of
  rows already in the store), compaction segments, streaming delta handling.

## Hypotheses

- None for the mechanism above. Whether CLI `2.1.284` displayed its untagged
  thinking text in the TUI is unverified; the fix keeps such text visible as the
  existing collapsed thinking block rather than hiding it.

## Expected outcome

- Narration thinking (`thinkingDisplay: "updates"`) renders as an assistant
  prose bubble at its position, before the tool-call group of the same turn,
  matching the Bridge Console.
- Other non-empty thinking that precedes a tool call stays visible as the
  collapsed thinking block instead of disappearing into the group.
- Empty (signature-only) thinking + tool_use entries keep folding into tool
  groups; committed store entries are not mutated.
- Gates: automated merge gate above; owner observation after release.
