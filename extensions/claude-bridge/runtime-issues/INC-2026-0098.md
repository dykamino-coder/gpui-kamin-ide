## Symptom

In the Claude Bridge chat, the thinking marker (the lightbulb with the
collapsed thinking text) does not appear for real model output, although the
model does think: the turn has a thinking phase and the transcript has a
`thinking` block. A synthetic transcript row with thinking text renders the
marker correctly on 1.0.92 and 1.0.93, so the renderer itself works.

## Environment and versions

- Bridge server image 6.3.169 and 6.3.170 (acceptance container), Claude Code
  CLI 2.1.296, 2.1.312 and 2.1.322, models `claude-opus-5-5` and
  `claude-haiku-5-5`, effort `high` and `xhigh`.
- KaminIDE 1.0.92 and 1.0.93 chat webview.

## Confirmed facts

- The chat draws the marker only for a `thinking` block with non-blank text
  (`webview/src/components/jsonl-viewer/ThinkingBlock.tsx`). A block with empty
  text and a signature draws nothing; this is intended, an empty marker never
  stands alone.
- In 246 CLI transcripts of the acceptance server there are 297 assistant
  `thinking` blocks with empty text and a signature, and 22 with text. Every
  one of the 22 is short (108 to 244 characters), has a thinking duration of
  1 to 8 ms, and is the second thinking block of a message whose first
  thinking block is empty. These are the progress notes of INC-2026-0063, which
  the chat shows as assistant prose, not as thinking. No transcript holds the
  model's actual reasoning text.
- Empty and non-empty blocks do not differ by model, CLI version, effort or
  day: on the day with most data the same model, CLI 2.1.312, effort `high`
  and `thinkingDisplay: "updates"` produced 168 empty blocks and all 15
  non-empty ones of that day. Empty blocks occur under every CLI version, both
  models and both effort levels seen.
- The request explains it. Every recorded request shape in these transcripts
  has `"thinking":{"type":"adaptive","display":"updates"}`, and every affected
  row carries `thinkingDisplay: "updates"`. In this mode the API returns the
  reasoning as a signature without text and, sometimes, a short progress note.
- The CLI chooses the mode. The 2.1.322 bundle sends the beta
  `thinking-display-updates-2026-08-18` by default, has a hidden option
  `--thinking-display <summarized|omitted|highlights>` and a setting
  `showThinkingSummaries` ("Request API-side thinking summaries and show them
  in the conversation and in the transcript view").
- Reproduction in print mode, CLI 2.1.322, `claude-opus-5-5`, `--effort high`,
  the same prompt, `--output-format stream-json --verbose
  --include-partial-messages`:
  - no display option: two `thinking` blocks, text length 0 and 0, signatures
    present, 4 `thinking_delta` events; the transcript rows have
    `thinkingDisplay: "updates"`;
  - `--thinking-display summarized`: two `thinking` blocks, text length 227
    and 254, 42 `thinking_delta` events; the transcript rows have
    `thinkingDisplay: "summarized"`;
  - `--settings '{"showThinkingSummaries":true}'`: text length 0 and 0. The
    bundle forces the display to `omitted` for a non-interactive session
    unless the display was given explicitly, so this run says nothing about
    the setting in an interactive session.
- In a Bridge-started interactive session on KaminIDE 1.0.92 (CLI 2.1.322,
  `claude-opus-5-5`, effort `xhigh`), `showThinkingSummaries: true` written to
  the session's project-local CLI settings, followed by a CLI restart, did not
  bring thinking text: the block stayed signature-only and its row had no
  `thinkingDisplay` field. The setting was removed after the run.
- Bridge passes neither control: `server/src/core/pty/session-env.ts` and
  `session-plugin-args.ts` build the CLI arguments without a display option,
  and no Bridge source mentions `showThinkingSummaries`.

## Hypotheses

- `--thinking-display summarized` gives thinking text in a Bridge-started
  interactive session too, as it does in print mode. Not verified: two
  interactive runs in a pseudo-terminal outside Bridge did not get past
  start-up in an untrusted directory and wrote no transcript. The
  `showThinkingSummaries` setting alone did not work in the one session tried
  (see above); why is not known.
- Summaries change output token use. One pair of runs (463 and 520 output
  tokens) is not a measurement.
- With `summarized` the short progress notes of INC-2026-0063 may stop
  arriving; the two displays were not compared in one long session.

## Expected outcome

The cause is the display mode the CLI requests, not the chat renderer and not
a model, version or effort setting. The owner decides what the chat shows:

1. Keep the current behaviour: no marker when the API returned no thinking
   text. Nothing to change.
2. Show a marker without text for a signature-only thinking block (for
   example with the thinking duration the CLI records). Render-only change;
   the reasoning itself stays unavailable.
3. Ask the CLI for summaries with `--thinking-display summarized`, possibly
   as a Bridge session setting. The option is hidden in the CLI help.
   The chat then shows real summarized reasoning under the existing marker.
   Needs the interactive check and a look at the effect on progress notes and
   token use first.

Gates follow the chosen option: vitest replay of the render model for 2; a
live session on the candidate for 3.

## Missing evidence and blockers

- Interactive effect of `--thinking-display summarized` inside a Bridge session; owner of
  the step: the executor of the Change PR, if option 3 is chosen.
- The owner's choice between the options above.

## Source-trace follow-up — 2026-11-13 (cxstats)

Source baseline: `32109f31cd9a4940726d216e5deae03aef1220d5`, compared with
`origin/main` `848ac4618d81dad519958060fccb7200489bc5d9`. No new model request
or CLI display-mode experiment was made.

The current renderer has two visibility boundaries:
`webview/src/components/jsonl-viewer/entry-draws.ts::assistantHasVisibleContent`
rejects an assistant row consisting only of blank thinking/text, and
`ThinkingBlock.tsx` independently rejects blank thinking. Nonempty thinking
currently renders as ordinary Markdown with a lightbulb, without an expandable
control; the collapsed-marker wording above describes the historical client.

The server's `pty/jsonl-projection.ts::leanEntries` strips `signature` from the
wire DTO while preserving the thinking block and its text. A presentation
decision specifically requiring proof that a signature was present cannot
inspect that signature in the current client DTO. Decide what an empty block
means for the UI and, if necessary, carry a small explicit presentation fact;
do not restore the opaque signature payload merely to draw a marker. Keep
streaming empty placeholders and `redacted_thinking` distinct.

**Next artifact:** product owner chooses the intended empty-block presentation;
webview executor then covers row visibility and block rendering together,
including streaming-to-final state and narration conversion. This does not
establish lost thinking text or request a different paid CLI display mode.
