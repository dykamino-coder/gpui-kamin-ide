- **Completion target:** accepted and published fix: an external MCP server started over stdio by the client gets a working directory by the same rule as tools and hooks — its configured directory, otherwise the folder of the project that declares it, otherwise the user's home directory — and never the application directory.
- **Diagnostic PR:** [#751](https://github.com/dykamino-coder/gpui-kamin-ide/pull/751)
- **Fix PR:** none
- **Next step:** change — one Fix PR in the client (`extension/src/main/mcp/transports/stdio.ts` and discovery): choose the directory by the rule above with the helper added in #743 (`extension/src/main/utils/working-directory.ts`), with a test that starts a real stdio process and reads its directory. Owner of the step: the executor of the Fix PR.
- **Private evidence:** not required.
- **Dependencies:** none. Follow-up of INC-2026-0103 (#743), which fixed tools and hooks and listed this as a limitation.
- **Acceptance:** automated: a test that starts a stdio MCP process through the real transport and observes its working directory, for a server with a configured directory, a project-level server and a user-level server.

- **Deployment observation owner:** none

## Symptom

An MCP server that the client starts over stdio and that has no
`workingDirectory` in its configuration runs in the directory of the host
process, which for the installed KaminIDE is the application directory. A
server that writes or reads relative paths works in the wrong place. Not
observed in a user session; found by reading the code during INC-2026-0103.

## Environment and versions

- Source at `origin/main` `4ecb8cbb` (after #743 and #747).

## Confirmed facts

- `extension/src/main/mcp/transports/stdio.ts` passes `cwd` to the process
  start only when `state.config.workingDirectory` is set; otherwise the
  process inherits the directory of the extension host.
- `extension/src/main/mcp/discovery.ts` sets `workingDirectory` only from an
  explicit entry of the server configuration. A server declared in a
  project's `.mcp.json` gets no directory from the project root.
- #743 made tools and hooks use the tab's folder or the home directory
  (`resolveWorkingDirectory`); the MCP transport does not use that rule.

## Hypotheses

- Plain Claude Code starts a stdio MCP server in the directory of the CLI,
  which is the project folder; servers that rely on it (relative paths in
  arguments, files beside the project) behave differently under Bridge. Not
  checked on a real server.

## Expected outcome

- A stdio MCP server never starts in the application directory. The order is:
  configured directory, then the root of the project that declares the
  server, then the user's home directory. A directory that does not exist is
  skipped.
- A server with a configured directory behaves as now.

## Missing evidence and blockers

- No live observation with a real MCP server; not needed for the change,
  which is provable by a transport test.
