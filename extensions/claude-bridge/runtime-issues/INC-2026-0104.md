## Symptom

KaminIDE 1.0.93, Bridge server 6.3.170. A session has several conversation
segments in the strip above the chat (after `/clear` or compaction). The user
selects a past segment whose badge shows 270 records. The chat shows only a
few last rows of that segment (collapsed tool-call groups and a couple of
replies) with a large empty area below them. The rest of the segment cannot be
reached by scrolling up. A turn was running in the session at that moment and
a submitted message was shown as queued.

## Confirmed facts

- A past segment is opened as an archived view: the webview asks the server
  for the segment by its boundary timestamps and replaces its window with the
  answer (`webview/src/lib/open-segment.ts`, `replaceWindowWithSegment` in
  `webview/src/signals/jsonl.ts`).
- The server answers with one page — the newest records of the segment, at
  most 200 records or 512 KiB of the file (`server/src/core/pty/jsonl-page.ts`,
  the `jsonl:segment-request` handler in `server/src/core/pty/session-ws.ts`).
  A segment with 270 records never arrives whole.
- The remaining records are meant to arrive through the scroll-up path:
  the viewer asks for the page before its oldest row and passes the answer to
  `prependJsonlEntries`. That function ends in `appendJsonlEntries`, and
  `appendJsonlEntries` treats every row that arrives during an archived view
  as a live row of the current conversation: it puts the page into the
  held-back buffer and returns without touching the window. The page is never
  shown, and it is later appended to the current conversation when the user
  returns to it.
- A unit test reproduces both effects on `origin/main` at `2c5ea735`: after
  the first page of 200 records and an older page of 70, the window still
  holds 200 rows, and after returning to the current conversation the 70 old
  rows are in it.
- The scroll-up path starts only from a scroll event that moves up and ends
  near the top (`useChatScrollPin.ts`). When the first page draws fewer rows
  than the viewport holds — 200 file records fold into a handful of tool
  groups — the container does not overflow, no scroll event can occur, and no
  older page is requested at all. This matches the empty area in the report.
- An older page that arrives while the reader is at the bottom is discarded
  as stale (`JsonlViewer.tsx`). A window that does not overflow is always "at
  the bottom".

## Hypotheses

- Whether the tab had a working folder does not appear to matter: none of the
  code above depends on it. Not checked on a live session.
- The badge counts file records of the segment, while the chat draws merged
  rows; the two numbers are not expected to be equal. To be confirmed on a
  live session.

## Expected outcome

- An older page requested during an archived view is merged into the archived
  window in file order and is not added to the held-back live rows.
- A window that does not fill the viewport requests older pages by itself
  until it overflows or the segment start is reached.
- Live rows of a running turn stay out of the archived view and return, in
  order and without archived rows, when the user goes back to the current
  conversation.
- Unit tests cover the three statements. Unchanged: the current conversation
  following new messages at the bottom, switching between segments, and the
  Bridge Console.

## Result of the fix (2026-11-11)

[#752](https://github.com/dykamino-coder/gpui-kamin-ide/pull/752), merged as
`5a8752ea`, webview only:

- rows of the window on screen bypass the archived-view gate, so an older page
  of a past segment lands in that window and no longer in the held-back live
  rows;
- while the drawn rows do not fill the viewport the viewer asks for older
  pages by itself, and such a page is not discarded as stale;
- opening another segment of the same tab re-arms the bottom pin. This was
  found in the live check: a past segment that can now be scrolled to its
  start released the pin, and the current conversation then stopped following
  new messages.

Live check by the executor, KaminIDE 1.0.93 binaries with the webview of the
candidate, Bridge server 6.3.170, a session without a working folder, a past
segment of 335 file records:

- `origin/main` before the fix reproduces the report: the last 30 tool calls,
  no overflow, the wheel does nothing;
- the candidate shows the segment up to its first prompt; the wheel, End,
  PageUp, Home and the scrollbar thumb reach the first record, also while a
  turn is running with a queued message; switching between the segments keeps
  both intact, nothing of the past segment appears in the current
  conversation, and the current conversation opens at its end and follows a
  streamed reply.

Both hypotheses above are settled for this session: a tab without a working
folder behaves the same, and the badge (335 file records) is not the number of
drawn rows (1 prompt, 141 tool calls, 1 reply).

Not checked: a tab with a working folder, the scrollbar thumb on the final
head (checked one commit earlier), scrolling of the Bridge Console (its code
is not touched; the terminal of the test profile had no scrollback), and an
installer built from this commit.
