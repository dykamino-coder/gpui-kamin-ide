## Symptom

A failed swap-chain resize or intermediate device-recovery allocation can leave
the native renderer with already released resources still represented as live
fields. Retry, draw or destruction can then use or release those fields again.
This source finding was initially recorded in INC-2026-0020. New field logs
identify a surviving shell and CEF renderer termination, so this independent
GPUI hazard is tracked here and is not attributed to that observed crash.

## Confirmed facts

Source `a34ab4892058bcacc00de8d97ae951fb60551780`; paths below are relative to
`vendor/gpui/src/platform/windows/`.

- `directx_renderer.rs:880–913` changes cached dimensions, manually drops the
  render target and takes its view before fallible ResizeBuffers/recreation.
  An error leaves the dropped slot and absent view in the renderer. The caller
  at `events.rs:224` logs the failure without making that state unavailable.
- A same-size retry returns success without repair. A changed-size retry drops
  the target again and unwraps the absent view. Draw can unwrap it at line 411
  if its earlier buffer update succeeds. `DirectXResources::drop` at 1935–1939
  also releases the manually dropped target slot.
- Recovery drops existing resources/devices at renderer lines 463–474 before
  fallible replacements at 477–494 and assignments at 500–504. The five-attempt
  helper in `directx_devices.rs:23–40` repeats the operation on destroyed state
  after an intermediate failure. Exhaustion only logs and returns.
- `platform.rs:1056–1081` logs success and dispatches recovery even when new
  platform device construction exhausted its attempts, passing the old device.

Two source reviews and a source-anchored deterministic model confirm the order.
The model does not execute Rust/COM/destructors or reproduce a Windows crash.
The renderer source is also identical in documented 1.0.55 installer source
`c599cae23afb8393ed1377a67f91b13082902115`.

## Counterchecks and limits

First-attempt successful recovery avoids the retry hazard. Releasing back-buffer
references before ResizeBuffers is required; retaining unsafe ownership after
failure is the defect. Draw's earlier Map may fail before its unwrap. Present
errors are logged; device-loss polling, recovery and a VSync sleep fallback exist.
The atlas is reset; separate successful-recovery effect caches are INC-2026-0023.
Microsoft's [device-loss guidance](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios)
documents fallible resize/present recovery. No driver fault, field root cause or
measured memory impact is claimed here.

## Expected outcome

Make failed/unavailable renderer ownership explicit and retry-safe. Clean partial
allocations and report terminal recovery failure accurately. Test failure at
ResizeBuffers and each replacement stage, then exercise same/different-size
resize, retry, draw and teardown without repeated release or use of dead slots.
A disposable Windows gate covers controlled device loss and allocation failure,
sleep/RDP transitions, dimensions/DPI changes and repeated successful/failed
recovery. Coordinate overlapping renderer edits with INC-2026-0023. This source
task does not close INC-2026-0020 or prove that its CEF crash is fixed.

## Windows recovery acceptance (2026-10-11, partial)

Run on main `22fb1ad` (debug build with the #216 fix and the #232
application-level seams) on a Windows 11 console session (Intel Iris Xe):
GPUI's device was an application-owned D3D11On12 device and
`nativeAcceptance deviceLoss` called `ID3D12Device5::RemoveDevice`, a genuine
device removal without any system setting. Five removals in a row on the
native UI (no CEF view): before each, a toast with `paint_backdrop_blur`
populated the effect caches; removals 1–2 kept the window size, 3–5 resized
it between recoveries. Result: 5/5 `device_changed=true` recoveries; blurred
toast, animated loaders and layout drawn on every new device at the same and
at changed sizes; input works; no panic, crash record or D3D11 debug-layer
error ([evidence](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/22367a54678b2759385b8d7a31e970e551dbef36/incidents/INC-2026-0025/evidence/2026-10-11-runtime-acceptance-22fb1ad)).

Not covered yet: sleep/resume and RDP transitions, DPI change, failed
recovery / allocation failure, and live-object counts for the release of old
resources. The incident stays in `verify` until those parts of the gate run.
