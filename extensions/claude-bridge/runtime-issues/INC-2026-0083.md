## Symptom, versions and evidence boundary

The owner reports a long conversation with many compacts and historical child
transcripts becoming hard to use: Chat can stop updating while Console still
works, indexes/history appear late, and reconnects may be necessary. Earlier
captures used client 1.0.75 with server 6.3.152; after the server update some
observations used client 1.0.75 with server 6.3.158. The later command-capacity
report used the matched 1.0.81 / 6.3.158 pair and belongs to INC-0082.

On 2026-10-29 the owner reports trimming the conversation to the latest compact
boundary and substantially better responsiveness for the following hours.
Client/server updates and workload changed in the same period. No controlled
before/after trace establishes which change caused the improvement. This is
not permission to truncate more transcripts or a supported data-loss remedy.
There is no established 200/300/600 MB or 100/150-agent failure threshold.

## Confirmed residual and what is already fixed

The published 1.0.81 / 6.3.158 source is
`132623e456e9d6c2bcf8c59cb9e38e8cc4677a18`. INC-0078 implementation PRs #495,
#499 and #500 are merged and ancestors of that published tag. They address
streaming/worker repair, replay/backpressure, durable ingestion, database
ownership and related retries/archive generations. Do not implement them again
or conclude that later symptoms mean those bounded fixes did nothing.

A separate residual remains: `session-ws.ts` calls `replayAll()` on reattach;
`jsonl-watcher.ts` replays the parent from the start and clears/recreates child
watchers. Initial discovery opens every historical child. Full segmentIndex is
published with replay completion. Streaming limits individual work batches,
but does not by itself limit total history required on each open/reattach.

This is **not** evidence of a continuous full replay while idle. Normal tailing
uses filesystem events and offset/size checks; retired-file rediscovery was a
distinct INC-0069 defect already fixed in #380. Deliberate reconnect/reset can
still replay everything once. Measure actual reconnect frequency separately.

## Controlled runtime baseline

An isolated Docker test ran the published server, native PTY and checkout-only
fake CLI without an Anthropic account or owner data. Synthetic main: 40,010
records / 109,276,481 bytes / 10 compact boundaries. Children: 282 files,
112,800 records / 488,624,502 bytes. Total: 597,900,983 bytes.

Initial resume, warm reattach with a 1.5-second receive pause and resume after
server restart all delivered the expected UUID sets and boundaries, preserving
conversation identity. Warm reattach kept the PTY; restart created a new PTY.
Each open transferred about 604.2 MB of protocol payload. Replay/index took
9.9–17.4 seconds in that test. A subsequent synthetic compact boundary updated
the index without reconnect. No OOM or unplanned server restart was reproduced.

Environment: Linux arm64 Docker Desktop, server 2 CPU / 3 GiB, protocol peer
2 CPU / 1 GiB. The peer parses/discards bodies and retains UUIDs; it does not
run Windows Chat, Markdown layout or native CEF queues. Disk cache was warm
from fixture generation. Timings are neither production estimates nor upper
bounds. The production host resources and concurrent workload were not measured.
Raw results and scripts are in the immutable private packet after registration.

## Proposed bounded deliverables and order

1. **Independent urgent repair:** INC-0082 command admission. Keep its result
   retention and active limits independent from loading architecture.
2. **Loading contract:** define attached/current-ready/index-loading/archive-
   loading states, generation ownership, byte/record/page budgets and host
   capability negotiation. A current view must not wait for all historic child
   bodies. Preserve the conversation ID and old-client compatibility explicitly.
3. **Current first, history on demand:** separate parent segment metadata and
   child catalog from transcript bodies; load bounded pages when selected.
   Resume from a verified cursor/fingerprint where possible; reset explicitly
   after replacement/shrink. Do not trust an old cursor for a new generation.
   End-to-end mirror/cursor use must be proven, not inferred from a server-only API.
4. **Shared-server scheduling:** per-session and global byte/work budgets,
   cancellation, fair progress for many owners, and priority for live input
   over historical replay. One individually paced watcher per child is not a
   proof of a bounded combined workload.
5. **Client working set:** measure retained models, successive Markdown cache
   entries, host/native delivery bytes, queue depth and event processing per
   turn. Bound/coalesce safe replaceable updates while preserving ordered tool
   outcomes and lifecycle events. Split server/state fixes from native changes.
6. **Recovery and storage:** distinguish storage failures from not-found; keep
   bounded versioned repair backups separately from canonical transcripts and
   durable archive tips. Do not infer turn resubmission from a last user row.
   Define interrupted-turn outcome; do not replay side effects automatically.

These are proposed implementation slices, not six accepted fixes or fabricated
child IDs. The maintainer can refine them after current-source review. Archive/
backup retention must preserve user history and recovery generations; it is
not permission for age-based deletion of canonical conversations.

## Acceptance and what does not require new owner logs

Start from the supplied scripts and current public modules. Compare before and
after under the same environment and fixture, then add a documented mixed load:
small active sessions, large idle/reopening sessions, 1/50/150/282 historical
children and bursts across approximately 20 logical owners. Choose recorded
CPU/memory/queue/storage limits and measurable thresholds before the run.
Do not present a single-user local result as a production capacity figure.

Server/protocol checks: exact record/segment counts or hashes; bounded memory
and bytes in flight; stale-generation cancellation; prompt cancellation; current
readiness independent of archive completion; fair progress and health latency;
no periodic full replay at idle; matching/mismatched cursor behavior; restart,
slow/paused consumer, missing files and storage faults; no identity substitution.

Regression checks: accepted compact/index, Agents report/idle, drawable window,
legacy/modern tool results, no duplicate side-effecting execution and owner
isolation. The earlier .75/.158 Task-owner compatibility probe is relevant to
negotiation: a CLI advertising Tasks does not establish host-client capability.
The owner now using .81 does not establish a compatibility fix for older hosts.

For a changed native queue/CEF/input contract, run the card's exact Windows gate
on the candidate: large parent plus a small control tab, pointer idle, switch,
scroll/reveal, Console hidden/visible, new current output and reconnect. Record
responsiveness, delivered outcomes and bounded queues; ordinary compiler CI is
not this gate. Server-only changes do not inherit an unrelated UI gate.
