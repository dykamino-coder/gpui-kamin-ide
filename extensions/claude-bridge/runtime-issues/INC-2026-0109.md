# INC-2026-0109 — One pixel inside a glyph quad differs between frames of a bit-identical scene (Windows DirectX renderer)

- **Status:** investigation
- **Registration author:** @dykamino-coder, lead-directed registration by Claude Code (2026-11-11); found while validating #757 (relayout cache).
- **Completion target:** a research result: the mechanism that makes one rendered frame differ from another frame of the same scene, and either a bounded renderer fix or a documented tolerance for exact-RGB gates.
- **Diagnostic PR:** this PR
- **Fix PR:** none
- **Next step:** research — reproduce on each adapter separately (integrated and discrete) with the scene-hash probe, and on WARP; then test the sampler and readback hypotheses below (owner: next maintainer run).
- **Private evidence:** PRIVATE_URL (differing and reference frames with coordinates, run manifest, checksums).
- **Dependencies:** none.
- **Acceptance:** automated: a repeated-frame harness (same scene rendered N times, exact RGB compare of the captured frames) with zero differing frames over at least 2400 frames on the affected machine, or an accepted written tolerance rule for RGB gates.
- **Acceptance rationale:** the symptom is a captured-frame difference of an unchanged scene; it is observable by the bench frame capture without a live UI.
- **Deployment observation owner:** none (no user-visible report; single transient pixel).

## Symptom

In the `engine_bench` relayout job on `p02_many_paragraphs` (window 800x600 and 801x600 alternating, scale 1.0)
one frame out of several hundred differs from the other frames of the same width in a single pixel (once in a
1x2 pixel pair). The pixel lies inside a glyph quad and takes the value a neighbouring texel would give. The place
is different every time, the difference lasts one frame, and the next frame of the same scene is equal to the
reference again.

## Confirmed facts

- Same rate on main and on a branch: 40 runs x 60 relayout frames each; main (`4e61a690` engine) 4 differing
  frames of 2400, branch `perf/relayout-cache` 5 of 2400. Earlier runs of main builds: 3 of 244 `p02` runs had one
  such frame.
- The scene is bit-identical: a probe hashing the `Scene` handed to the platform renderer (sprites with tiles and
  bounds, quads, underlines) gave equal hashes for the differing frame and its reference frames in all 40 probe
  runs. The difference is therefore produced below layout and paint.
- Glyph sprites are drawn with `t_sprite.Sample(s_sprite, ...)` and the sprite sampler is created with
  `D3D11_FILTER_MIN_MAG_MIP_LINEAR` (`vendor/gpui-windows/src/directx_renderer.rs`, `shaders.hlsl`).
- Frames are read back synchronously (`vendor/gpui-windows/src/directx_renderer/frame_capture.rs`).
- The machine has an integrated Intel and a discrete NVIDIA adapter.

## Hypotheses

- With a LINEAR sampler a texture coordinate that lands on a texel edge may round to either side, depending on
  driver state; a point-sampled or `Load`-based glyph path would be exact.
- A driver-level race on the integrated adapter (atlas upload still in flight when the draw samples it).
- A readback artifact (copy of the back buffer before the last draw is resolved).
- Possible link to the earlier observation that `main.exe` and `flip.exe` of the same tree gave different pixels,
  and to an earlier "p02 RGB mismatch on the integrated adapter" note on clean main.

## Expected outcome

The mechanism is named with a reproduction that isolates it (adapter, sampler or readback), followed by a bounded
fix PR or a recorded tolerance rule. No behaviour change is part of this registration.

## Missing evidence and blockers

- Which adapter rendered the differing frames was not recorded per run.
- No reproduction on WARP or on a single-adapter machine yet.
