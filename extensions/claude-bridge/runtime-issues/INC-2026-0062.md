# INC-2026-0062 — Bridge upstream TLS fails under corporate inspection

- **Status:** reported
- **Registration author:** @dykamino-coder, owner-directed registration by Codex
- **Diagnostic PR:** pending
- **Fix PR:** none
- **Next step:** change; Codex prepares outbound TLS policy, CA assembly, tests and deployment guidance; lead accepts and merges the fix.
- **Private evidence:** not required; only the owner's sanitized report (2026-10-11), no raw production logs or credentials were supplied.
- **Dependencies:** none
- **Acceptance:** automated merge gate plus Podman-only synthetic TLS-inspection reproduction; no Bridge server on the Windows host.
- **Deployment observation owner:** deployment owner, after normal release/deployment.

## Symptom

The owner reports production CLI sessions through image `open-claude-bridge:6.3.141`
returning `502 Bridge upstream error: fetch failed` with
`self-signed certificate in certificate chain (SELF_SIGNED_CERT_IN_CHAIN)`.
Direct host-console Claude CLI works. The container is started with `docker run`
in a corporate network using a Harbor registry mirror and TLS inspection.

## Confirmed facts

- The symptom and working host CLI are owner-reported, not independently reproduced in production.
- Source at `3f5fc0e` issues MITM upstream requests through undici. Without a custom CA it does not explicitly assemble the system trust store. A supplied custom `ca` replaces the default roots.
- Session setup overwrites `NODE_EXTRA_CA_CERTS` with the Bridge MITM CA, dropping the operator CA previously injected by settings.
- The owner states the host trust store contains the corporate root and the CLI-to-Bridge MITM hop works.

## Hypotheses

The inspecting network's root is absent from the server's effective trust roots.
The server rejects the upstream chain while the host CLI accepts it. A synthetic
Podman reproduction will verify the mechanism; production is unavailable.

## Expected outcome

Per the owner's final decision on 2026-10-11, Bridge server outbound HTTPS
certificate verification is **disabled by default**, with one clear startup
warning. `BRIDGE_TLS_VERIFY=1` explicitly enables verification using bundled and
system roots plus the operator's `CLAUDE_PROXY_CA_CERT`. CLI verification remains
separate and its CA bundle retains both the Bridge MITM CA and corporate roots.
Document the recommended verified mode, Docker CA mounts, and both test paths.

This decision supersedes the earlier secure-default and insecure-opt-in requests.
Risk: disabling verification lets an attacker on the network path impersonate
upstreams and read or change tokens, prompts and transcripts. The deployment
owner explicitly chose this default; verified mode is recommended.

## Missing evidence and blockers

No production access or raw evidence is required for registration. Fix acceptance
requires unit CA-assembly tests and Podman reproduction showing baseline 502,
default-mode success, verified rejection without the root and verified success
with it. Production rollout observation belongs to the deployment owner. Keep
this card open until the lead accepts and merges the Change PR; no release here.
