- **Registration author:** @dvpetrochenko (owner-directed source review)
- **Priority:** P1
- **Diagnostic PR:** [#140](https://github.com/dykamino-coder/gpui-kamin-ide/pull/140)
- **Fix PR:** none
- **Next step:** research and implement a durable old-session resume contract, then prepare a bounded Change/Fix PR; owner: maintainer when scheduled.
- **Private evidence:** [INC-2026-0054 at immutable private commit](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/adde685eba515b7753df0196f60374845f41b238/incidents/INC-2026-0054). Full session identifiers stay outside this public repository.
- **Dependencies:** none. A separate report about fresh transcripts missing from the statistics index after restart must not be treated as the cause of this resume failure.
- **Acceptance:** an idle conversation older than 30 days remains resumable without recovery from a backup; explicit removal makes it unavailable; controlled CLI expiry/restart, server resume and client-list tests, and an authorized deployment observation of effective retention and mounted storage before claiming the field cause.
- **Deployment observation owner:** operator with authorized access to the Bridge host; the maintainer has no access to that host.

## Symptom

The owner reports that an older conversation remains visible in KaminIDE but
cannot be reopened. A server agent reported that the original Claude Code
transcript file was absent although the Bridge database retained session and
usage metadata, and a timestamped repair backup existed. Those filesystem and
database observations are second-hand; no production host or raw log was read
during this registration.

## Checked source and upstream contract

Source checked at `56473066733d8a19573dcfa6f2bc29ef82720c29`:

- `server/src/core/pty/session-resume-helpers.ts` looks for the exact
  `<conversation-id>.jsonl` beneath `~/.claude/projects/<slug>/`. It does not
  resume from DuckDB rows or a `.jsonl.bak-*` copy.
- If the file is absent, `server/src/core/pty/session-core.ts` drops the
  requested ID and starts a fresh session. `session-ws.ts` sends
  `resumeNotFound`; the client displays a warning. Historical database rows
  therefore cannot by themselves make the conversation resumable.
- `server/src/core/pty/session-settings.ts` does not set `cleanupPeriodDays` in
  its generated project settings. A global or managed setting could still
  override the effective value on a particular host.
- [Claude Code's current storage documentation](https://code.claude.com/docs/en/claude-directory#cleaned-up-automatically)
  says project conversation transcripts are subject to `cleanupPeriodDays`,
  default 30 days. That makes age-based deletion a plausible explanation, but
  does not prove it occurred on this host or under its installed CLI version.
- Bridge transcript repair creates a timestamped `.bak` before rewriting a
  `.jsonl`; no automatic backup-based resume path or retention guarantee is
  established by this code.

## 2026-09-25 field-report supplement

A second owner-supplied screenshot quotes a server agent's follow-up. The agent
reports that the inspected user settings file did not specify
`cleanupPeriodDays`, that older project transcript files were absent, and that
the affected file's last indexed activity and project-directory modification
were roughly one retention window apart. The agent also reports recovering a
copy from a surviving backup. These observations make the documented CLI
cleanup a stronger **hypothesis**, but the screenshot does not contain the raw
settings, filesystem snapshots, CLI sweep log or deletion event. Directory
mtime and timing correlation cannot identify the deleting process by themselves.

The follow-up says Bridge makes an epoch-named `.jsonl.bak-*` on every session
open. Current source calls `repairJsonl` before resume, but that function
creates this backup **only when it actually changes the transcript**. Source
review did not locate the other backup suffixes described by the agent; their
producer needs deployment/version provenance. The presence of backups therefore
does not prove that every open created one. Current Claude Code documentation
lists live session `.jsonl` and subagent paths for age-based cleanup, but does
not establish the installed CLI version's exact treatment of Bridge backups.

## Hypotheses to distinguish

The original file could have been removed by Claude Code retention, an
operational cleanup, a different or missing mounted volume, or another storage
failure. A restart on its own does not identify the remover. Separately, an
unhealthy JSONL-to-DuckDB scanner could explain missing statistics rows for
newer chats, but would not remove an existing transcript file. Do not merge
these two diagnoses.

## Owner-requested retention contract (2026-09-25)

The owner wants conversations to remain available until an explicit deletion,
including after more than 30 days of inactivity. Scheduled Claude Code
transcript cleanup must not make a Bridge-listed conversation impossible to
resume. Preventing that scheduled loss removes the need to restore backups
**for this specific expiry cause**; it does not replace storage backups for
corruption, accidental deletion, or volume loss. An already deleted transcript
is not restored by changing the retention setting.

The documented `cleanupPeriodDays` setting is a positive number of days; its
default is 30, and `0` is invalid. The current documentation does not promise
an unlimited-retention value. A larger positive value can be evaluated as an
operator mitigation, but merely choosing a large number is not a permanent
product contract. The maintainer must account for the effective Claude Code
settings and version, transcript storage growth, privacy, and explicit removal
while preserving the ability to resume old sessions. Do not make an unbounded
retention claim based solely on a numeric CLI setting.

## Maintainer deliverable

1. Reproduce expiry of a disposable transcript and verify the actual
   server/client behavior when the session list still contains its ID.
2. Implement the owner-requested retention contract: an old conversation
   remains resumable until explicitly deleted, without relying on a repair
   backup after a 30-day sweep. Establish how this works across the effective
   Claude Code settings, version changes and restarts; specify transcript
   storage/privacy controls and a clear explicit-delete path. If durable
   archiving outside the CLI cleanup scope is chosen, test restoring it to a
   valid resume path before handing the session to Claude Code.
3. Specify and test a safe, explicit recovery path when a verified backup
   exists. Never overwrite a production transcript or restore a stale backup
   without a read-only snapshot and integrity checks.
4. In a separate Change/Fix PR, add meaningful synthetic tests for more than
   30 days of inactivity, restart, explicit deletion and missing/corrupt source
   files. Verify an exact Windows candidate for any client UX change.

## Missing deployment evidence

effective `cleanupPeriodDays` value without other settings or credentials; a
bounded `stat`/listing for the affected `.jsonl` and `.bak` files; the mounted
volume identity before and after the restart; and relevant Bridge/Claude
retention and resume logs, including a `retention_sweep` event if that CLI

then, the reported deletion date, exact remover and recoverable content remain
unconfirmed. Changing retention now cannot restore an already missing file.
