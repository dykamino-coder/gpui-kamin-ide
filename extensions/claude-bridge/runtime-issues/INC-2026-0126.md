# INC-2026-0126 — No main-thread headroom while about 200 chats open at once

- **Status:** investigation. The symptom is known from the Bridge load runs; the per-phase cost on the main thread is not yet split.
- **Registration author:** `kacc22`, Bridge executor, lead-directed (2026-11-19). Listed as a known limitation of 1.0.117 ([#1055](https://github.com/dykamino-coder/gpui-kamin-ide/pull/1055)).
- **Completion target:** during a burst of 200 chats opening, the KaminIDE main thread keeps headroom for input (typing and clicks answered without visible stalls).
- **Diagnostic PR:** this registration.
- **Fix PR:** none
- **Next step:** investigation. Measure main-thread time per phase (reattach, replay, render, layout) during the 200-chat burst on 1.0.117, name the largest one, then propose a bounded change. Owner: next Bridge executor.
- **Private evidence:** none yet.
- **Dependencies:** none. #1048 (1.0.117) already removed transcript duplicates and cut delivery p95 on the load stand from 3.7 s to 0.67 s; this card is about what is left on the main thread.
- **Acceptance:** a Windows runtime run of the 200-chat burst on the fix head with an input-latency measurement.
- **Acceptance rationale:** the load exists only with many real CEF views and the real host.
- **Deployment observation owner:** the executor of the fix.

## Symptom

When about 200 chats open at once, the KaminIDE main thread stays saturated for the whole burst, so input has no headroom until the burst ends.

## Confirmed facts

- Observed on the Bridge load stand during the #1048 work (lead's summary); not re-measured on 1.0.117, no numbers in this card yet.

## Unknown

- Which phase dominates and whether it scales with chat count or transcript size.
