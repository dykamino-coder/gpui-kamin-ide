# INC-2026-0111 — Two KaminIDE profiles share Bridge tab, MCP and hook-approval state through the home directory

- **Status:** confirmed (source paths and one live write are verified)
- **Registration author:** @dykamino-coder, lead-directed registration by Claude Code maintainer `kmaint` (2026-11-13), found during the live runs of batch `RC-2026-11-13-KAMIN-BRIDGE`.
- **Completion target:** accepted and published fix: Bridge's own state follows the KaminIDE profile (`globalStorageUri`), so a second profile started with its own `LOCALAPPDATA` reads and writes none of the first profile's Bridge state.
- **Diagnostic PR:** this registration PR
- **Fix PR:** none
- **Next step:** change — move the Bridge-owned files under `~/.claude/open-claude-bridge/` to `context.globalStorageUri`, with a one-time migration from the old path. The executor is assigned by the lead from the Codex queue. CLI-shared files stay where they are; see Scope.
- **Private evidence:** not published; the observation is a file timestamp on the owner's machine, and the file content is not needed.
- **Dependencies:** none. Related: live acceptance procedure of the batch (profile copies), BR-10 (hook approvals), BR-04 (tab restore).
- **Acceptance:** unit tests that each moved store resolves its path from the injected storage directory and migrates an existing old file once. Then a live run of two profile copies with distinct `LOCALAPPDATA` and the same `USERPROFILE`, checking that `~/.claude/open-claude-bridge/*` keeps its mtime and each profile keeps its own tabs.
- **Acceptance rationale:** path resolution and migration are provable in unit tests; isolation between two real instances needs one live run.
- **Deployment observation owner:** none

## Symptom

A KaminIDE instance started with `LOCALAPPDATA` pointing at a copy of the
profile still wrote `C:\Users\<user>\.claude\open-claude-bridge\tabs-state.json`.
This is the file of the user's real profile. On 2026-11-13 the last write was at
04:00:43 (+05:00), and no other KaminIDE instance was running. After the test
runs, the real profile's tab state holds the test instance's tabs and test sessions.

## Environment and versions

- KaminIDE 1.0.94 (installed), Windows 11.
- Test instance: `LOCALAPPDATA` set to a copy, `USERPROFILE`/`HOME` unchanged.

## Source

At `main` f7c32f4e the extension keeps its connection config and incident
diagnostics in `context.globalStorageUri` (`bridge-host.ts`). The following
Bridge-owned state is built from `os.homedir()` instead:

- `main/tabs-state-store.ts` — `~/.claude/open-claude-bridge/tabs-state.json`;
- `main/mcp/state-persistence.ts` — `open-claude-bridge/mcp-servers.json` and
  `open-claude-bridge/mcp-tool-schemas.json`;
- `main/ipc/plugins/handlers-install.ts` —
  `open-claude-bridge/plugin-hook-approvals.json`.

## Scope

In scope: files under `~/.claude/open-claude-bridge/` that only Bridge reads.

Out of scope: files Bridge shares with the Claude CLI by design.
`~/.claude/plugins/*` (`known-store.ts` calls `known_marketplaces.json` the
CLI's source of truth), `~/.claude/settings.json`, `~/.claude.json` and
`~/.claude/.credentials.json` stay in the home directory. Whether a profile
should get its own CLI home is a separate product decision. It is not this fix.

## Workaround for acceptance runs

Start test instances with `LOCALAPPDATA`, `USERPROFILE` and `HOME` all pointing
at the copy, and a minimal `.claude` without credentials. After the run, check
that the mtimes under the real `~/.claude/open-claude-bridge/` and
`~/.claude/plugins/` are unchanged.
