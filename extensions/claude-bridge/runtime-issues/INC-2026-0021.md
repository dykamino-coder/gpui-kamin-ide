## Symptom

On the accelerated CEF path, a timed-out or abandoned shared-texture mutex is
treated as acquired. The shell then copies the surface and releases the mutex
without a successful exclusive-access result. This can make graphics recovery
and frame delivery unreliable under contention or producer failure.

## Confirmed facts

Audited source: `a34ab4892058bcacc00de8d97ae951fb60551780`.

- `crates/shell/src/web/copy_frame.rs:115–129` skips copying only when
  `AcquireSync(0, 16).is_err()` is true. Otherwise it runs `CopyResource` and
  `ReleaseSync`, including after a positive non-success wait status.
- The shell selects `windows = 0.62` in `crates/shell/Cargo.toml:58`;
  `Cargo.lock` resolves 0.62.2. Its generated `IDXGIKeyedMutex::AcquireSync`
  converts the raw HRESULT into `Result<()>`. The resolved `windows-result`
  0.4.1 treats nonnegative values as success, losing the distinction from S_OK.
  Both inspected package archives matched the lockfile SHA-256 checksums.
- `WAIT_TIMEOUT` is 258 and `WAIT_ABANDONED` is 128. A source-checked branch
  model confirms that both proceed to copy/release; a negative E_FAIL correctly
  takes the existing retry path. No actual DXGI call was made in that model.
- Microsoft's [AcquireSync contract](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgikeyedmutex-acquiresync)
  explicitly requires separate handling of these wait statuses. An abandoned
  surface and mutex need recreation; a timeout does not grant access.

## Hypotheses

Actual frame corruption, device reset or crash frequency is not established.
This is a concrete synchronization defect, not a proven cause of the owner's
sleep/RDP crash or measured GPU load. Startup under RDP currently selects CEF
software frames (`web/process.rs:103–113`, `web/browsers.rs:324`), so this
accelerated-copy path may be inactive in the reported event. Those short paths
are relative to `crates/shell/src/`.

The existing negative-error retry and bounded 16 ms wait are real mitigations;
they do not handle positive wait statuses. Do not replace this analysis with a
claim that every frame lacks synchronization.

## Expected outcome

Preserve the actual wait result at the interop boundary. Copy and release only
after successful acquisition. A timeout must retain a valid prior frame or
schedule bounded retry; abandonment must invalidate and recreate the affected
resource through a controlled lifecycle path.

Automated acceptance covers S_OK, WAIT_TIMEOUT, WAIT_ABANDONED, negative HRESULT,
missing mutex and repeated failures, asserting copy/release counts and bounded
retry. A Windows accelerated-CEF gate exercises contention and producer/device
recreation, checks D3D diagnostics and verifies usable frames/input after recovery.
Also verify the software fallback. No Windows acceptance or functional fix is
included in this Diagnostic PR; INC-2026-0020 still needs field crash attribution.

## Implementation candidate (2026-10-09)

The interop boundary invokes the typed AcquireSync vtable entry and preserves
its raw HRESULT. Only exact S_OK reaches CopyResource and ReleaseSync. Timeout,
negative and unexpected positive statuses do neither; retries are capped at
three self-requested frames until a new producer frame or successful copy.
Only successfully initialized own textures enter the cache, so a first-frame
wait failure cannot publish undefined pixels. A prior valid matching texture
is retained on retry.

Abandonment or missing keyed mutex retires the affected main/popup resource
caches and closes the producer browser; the existing ensure-view path recreates
it from stored HTML on the requested UI frame. Reopening the same abandoned
shared handle is insufficient under the Microsoft contract. This lifecycle
change requires the original live CEF gate; no user acceptance is claimed.
Device/context ownership remains a separate INC-0022 deliverable. Producer recreation is capped at three attempts until a successful copy; a fresh invalid producer callback does not reset this separate budget. Main and popup caches retire together.

A new regression runs actual D3D11 WARP resources and the actual copy module
without GUI/CEF. It preserves real WAIT_TIMEOUT=258, rejects an uninitialized
first busy frame and reuses a valid prior frame after contention. That test
fails against origin/main's copy module at the first-busy-frame assertion and
passes with the fix. Additional actual-module fixtures verify S_OK, timeout,
abandonment, negative/unexpected HRESULT, missing mutex and bounded retry.
Isolated Windows harness: `cargo test --offline -j 2` passes 5/5;
`cargo clippy --offline --all-targets -j 2 -- -D warnings` passes. Its only
replacements are inert UI repaint/browser/cache lifecycle boundaries; DXGI and
the production copy/mutex code are real. These results are not accelerated CEF
or software-fallback runtime acceptance. Fixtures are synthetic; no new private
runtime evidence is published.

Full shell checks/CI are tracked in the fix PR. Windows accelerated CEF runtime
gate remains required and unrun (contention, producer/device recreation,
D3D diagnostics, usable frames/input and software fallback). Status remains
open, release versions are unchanged, and vendor/html sources are untouched.
