## Symptom and scope

A long-running remote tool can finish on the KaminIDE host while its WebSocket to Bridge is closed. In the current source, the result is discarded locally and the server continues waiting until its timeout. This is a conditional source-level defect, not proof that the reported Agent Teams delays or a particular field disconnect were caused by this path. Agent Teams mailbox delivery is tracked separately by INC-2026-0039 and INC-2026-0056.

## Confirmed source facts

Source baseline: `origin/main` at `964788e`.

- `extension/src/main/ws/connection-manager.ts` exposes a `send` method returning `void`; it sends only when `ws.readyState === OPEN` and otherwise returns without an outcome. `respondMcp` and `denyMcp` delete the pending request and publish local completion/denial immediately after calling it.
- `extension/src/main/ws/mcp-call-pipeline.ts` also calls that `void` sender after `executeTool` finishes, then deletes `pendingMcpCalls` and publishes `completed`. Its error path likewise sends once and deletes the request. A closed socket at that point loses the result with no retry state.
- `server/src/core/pty/session-mcp-call.ts` marks the initial `mcp:call` as delivered when `sendToClient` accepts it. On reattach, `resendUndeliveredMcpCalls` skips delivered requests because the surviving client may still be executing them. The server cannot infer from this bit whether the later response reached it. Heavy tools have a 1,800,000 ms timeout; interactive calls have no ordinary tool timer.
- INC-2026-0011's fix corrected the initial request's `delivered` bit on transport rejection. It does not acknowledge or retry the client-to-server response.

## Maintainer investigation and expected outcome

Pin the client and server versions and trace one `requestId` through request acceptance, local execution, result send, disconnect, reattach and server settlement. Distinguish transport enqueue from server acknowledgement. Reproduce a disconnect before completion and one between result enqueue and acknowledgement. Define a bounded replay or explicit failure contract that preserves the result without re-executing a side-effecting tool. Include session destruction, timeout, duplicate response and multi-tab ownership in the tests. If the existing protocol cannot safely guarantee completion, surface an honest recoverable failure instead of `completed`.

The current field report lacks a correlated client/server WebSocket trace for a particular tool request. That trace and a Windows runtime check are needed to attribute the user's freeze or a specific 30-minute wait to this mechanism; they are not prerequisites for this diagnostic registration. This card remains open after merge and does not request a release.


## Prepared fix — 2026-10-09

A new test against unchanged public pipeline first failed: after the tool finished
without server acknowledgement, its pending entry had already disappeared.
The fixed pipeline retains the pending call and publishes completion only after
an authenticated session-scoped acknowledgement. Closed/replaced sockets retry
the serialized outcome, not execution. Success, execution error and user denial
share response delivery. Old sockets cannot settle another tab's request.

The per-connection outbox caps retention at 64 responses, 16 MiB total, 4 MiB
per frame and 120 seconds after completion, retrying once per second. Terminal
session teardown cancels it; attaching a different server session rejects stale
outcomes. Capacity, acknowledgement deadline and server-expired request failures
produce a visible host warning instead of a false completed state. There is no
persistent crash recovery and no claim about the historical field freeze.

Server settlement accepts the current authenticated socket only and checks the
request's session. It settles each promise once, acknowledges duplicate results
using an ID-only history bounded to 4096 entries and 120 seconds, and rejects
unknown/expired/destroyed requests. This history never retains tool payloads.
Old clients remain supported by optional response session IDs. The new client
requires the matching acknowledgement server; an older server will eventually
produce an explicit acknowledgement-timeout warning, not silent completion.

Automated fixtures cover closed socket, lost ack after enqueue, duplicate
execution prevention while pending, success/error/denial, wrong session, timeout,
teardown, session replacement and byte/count limits. Native Windows acceptance
remains outstanding: interrupt a long tool's socket before completion and between
response enqueue and ack, reattach, verify one server completion and no repeated
side effect; repeat with two tabs and a denial. Maintainer owns that gate.
