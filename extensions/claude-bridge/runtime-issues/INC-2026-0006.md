## Symptom

Locate Selected File cannot reveal a file outside a directory's first 100 rendered
entries even when its complete listing is already cached. Instead it repeatedly
reselects the target and schedules another attempt. The ordinary action can
therefore create continuing background work until unrelated state changes.

## Confirmed facts

Source revision: `a34ab4892058bcacc00de8d97ae951fb60551780`.
Short `state/`, `ui/` and `web/` paths below are relative to `crates/shell/src/`.

- `crates/shell/src/ui/file_tree/model.rs:65` sets the default cap to 100 entries.
  `flat_row_index` at lines 117–148 searches only the rendered prefix.
- `state/events/tree_listing.rs:40–46` expands ancestors and fetches missing
  listings. It never increases their child_cap.
- A target outside that prefix reaches lines 77–85, which unconditionally spawn
  a thread, sleep 120 ms and post LocateSelectedFile again. There is no attempt
  budget, deadline, cancellation generation or distinction between data still
  loading and a target outside the rendered prefix.
- Each attempt clears/reinserts selection and advances flash at lines 52–58.
  `state/tree_store.rs:23–34,56–60` notifies the tree for this mutation.
- A deterministic model with 101 cached files returns no row for file 101 over 500
  attempts at cap 100; increasing the cap to 300 returns row 101. Source assertions
  confirmed the unconditional retry and absence of a cap adjustment.

A concrete normal-workload trigger is opening the 101st alphabetically sorted file
in a 101-file directory and using Locate. A deleted target can also remain absent,
but that additional failure mode is unnecessary to establish the cap defect.

Each sleeping thread finishes after posting; this is repeated thread creation and
notifications, not proof that all past threads leak simultaneously. File 100 or
earlier is found, and manually selecting Show more can allow a later attempt to
succeed. Changing editor target/workspace can also stop a chain. None provides a
bounded policy for an unsuccessful Locate action.

## Hypotheses

The visible impact and CPU cost depend on tree size and repeated user actions.
Multiple clicks can start independent chains. No measured CPU, native failure
frequency or resource-exhaustion threshold is asserted.

## Expected outcome

Resolve Locate against the full cached listing, reveal the required capped
ancestors/target, and terminate or cancel retries with a defined outcome.
Automated fixtures cover nested caps, missing file, listing error, repeated clicks,
workspace/editor switch and stale retry events. Failed attempts must leave no
continuing selection mutations or polling.

The Windows gate verifies reveal, centering and highlight for targets beyond the
cap, plus adjacent Show more, keyboard navigation and selection behavior. It must
also show that a terminally absent target stops retrying. Deterministic source
models do not replace the native path-handling and visual acceptance gate.

## Windows runtime acceptance (2026-10-11)

Post-merge acceptance of fix PR #155 on current `main` (`6f09980`) in an isolated Windows KaminIDE
(separate desktop, own probe port and profile; Bridge server, when needed, in Podman with the
credential-free fake CLI), with the defect reproduced first on a local before-fix variant.
Folder session with a 150-file directory; f140 opened and Locate Selected File clicked once. On main f140 is revealed, scrolled into view and highlighted within 4 s; with d7da964 reverted it is never revealed within 24 s (beyond the 100-row cap). The bounded-retry part is covered by the merged automated tests (idle CPU of the debug build is not discriminating).
