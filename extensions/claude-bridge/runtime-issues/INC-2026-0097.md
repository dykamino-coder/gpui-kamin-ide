## Symptom

A session runs through the workspace host without a window in a Linux
container. Asked which tools it has, the agent lists PowerShell among them and
says that the tools run on the user's machine through Bridge. The host is a
Linux container without PowerShell, and it is not the user's machine.

## Confirmed facts

- Server source: the built-in tool list is a constant
  (`server/src/core/pty/mcp-tools-defs.ts`, `MCP_TOOLS`). `tools/list`
  (`server/src/core/pty/mcp-http-handler.ts`) returns the whole constant for
  every session, whatever host is connected. The PowerShell description says
  the command runs on the user's Windows host; the WebFetch description says
  the user's machine.
- Server source: the MCP `instructions` text (`mcpInstructions`) and the
  default session `CLAUDE.md` (`BRIDGE_DEFAULT_CLAUDE_MD`, written by
  `session-settings.ts`) are constants too. They say that the project, editor,
  shell and network are on the user's own machine and name Bash and PowerShell
  together.
- Protocol: `session:create` and `session:resume` carry `externalTools`,
  `basePrompt` and `protocolVersion`. Nothing in them tells the server which
  built-in tools the host can execute or what platform it is.
- Workspace host source: `workspace/src/session-context.ts` appends a note to
  the base prompt that reinterprets the server's wording for a container. The
  server texts above still reach the CLI unchanged, so the two contradict each
  other.
- A PowerShell call on a Linux client host today: `powerShellExecute`
  (`extension/src/main/mcp/tools/shell.ts`) resolves the executable through
  `findPowerShellExecutable` (`extension/src/main/utils/command-runtime.ts`).
  That looks for `pwsh` in `PATH`. Without it, on a host that is not Windows,
  it throws `PowerShell (pwsh) is not installed or is not available in PATH`,
  and the call returns that text as a tool error. With `pwsh` installed the
  call works. So the tool is advertised and fails only when called.

## Hypotheses

- Other built-in tools may be advertised without an executor on a reduced host
  (preview, LSP, notebook tools). Not audited tool by tool yet; the fix does
  that audit for the two existing hosts.

## Expected outcome

- The client host declares, when it creates, resumes or reattaches a session:
  the built-in tools it can execute, its platform and a label for the place
  where tools run.
- The server keeps the schemas and descriptions. `tools/list`, the MCP
  `instructions` and the session `CLAUDE.md` contain only what was declared and
  name the declared place, with no fixed reference to a Windows host or to the
  user's machine.
- A call of a built-in tool that the host did not declare is rejected by the
  server with a clear error and does not reach the host.
- A client without a declaration (an older KaminIDE) gets the full list and the
  present texts. KaminIDE on Windows declares its real set; its behavior does
  not change.
- Tests: a Linux host without PowerShell, a Windows host, a client without a
  declaration, a reduced host without a shell.

## Verification so far

- 2026-11-11, own stand, not a released image: a Bridge server container running the server sources of the fix branch and a workspace host container built from commit `9e3ed7a5` (Linux, bash and git present, no `pwsh`). After a session was created through the host, `tools/list` held 24 of the 25 built-in tools without PowerShell, neither `tools/list` nor the MCP `instructions` nor the session `CLAUDE.md` mentioned PowerShell or the user's machine, and they named "the workspace host (Linux)". A `tools/call` of PowerShell returned HTTP 400, code `-32602`, with the reason that the host did not declare it.
- That server had no Claude sign-in, so the agent itself was not asked. This is the remaining gate.
