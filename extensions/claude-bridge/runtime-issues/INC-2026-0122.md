# INC-2026-0122 — Closing the KaminIDE window leaves the process, a CEF renderer and the hosts running

- **Status:** verify. The fix [#999](https://github.com/dykamino-coder/gpui-kamin-ide/pull/999) is merged (`b5778a11`, 2026-11-17) and was first published in KaminIDE 1.0.113. The installed 1.0.116 contains it too. Acceptance on a published release is not yet done.
- **Registration author:** `kacc9`, Bridge executor, lead-directed (2026-11-16).
- **Completion target:** an accepted fix. After the main window closes, by any path, every process of that KaminIDE instance exits within a bounded time, and the next launch starts normally.
- **Diagnostic PR:** [#992](https://github.com/dykamino-coder/gpui-kamin-ide/pull/992)
- **Fix PR:** [#999](https://github.com/dykamino-coder/gpui-kamin-ide/pull/999) (`kacc10`)
- **Next step:** a live acceptance on the installed published release (1.0.113 or later), owned by the Bridge acceptance executor.
  - Run 10 WM_CLOSE closes and 10 title bar button closes with CPU under 80%. Every process of the instance must exit within 5 s, and the next start must open normally.
  - The slow `CefShutdown` under full CPU load is excluded: it is tracked in [INC-2026-0123](INC-2026-0123.md).
  - The 16 WM_CLOSE closes of 1.0.116 and of a #1043 candidate on 2026-11-19 ran under load. INC-2026-0123 records them; they are not this card's acceptance.
- **Private evidence:** not required. The reproduction is the public command sequence below. The diagnostic logs of the two runs stay outside the repository and hold nothing the card needs.
- **Dependencies:** none.
- **Acceptance:** Windows runtime on the exact fix head. For WM_CLOSE (as sent by Alt+F4, the taskbar's «Close window» and Task Manager's «End task») and for the title bar close button, all processes of the instance must be gone within 5 s. A relaunch must then open its window without the «previous instance is still exiting» recovery.
- **Acceptance rationale:** the defect is the lifetime of real OS processes after a real window close. Only a run of the built application on Windows shows it; unit tests cannot.
- **Deployment observation owner:** none. The local KaminIDE installation is the acceptance stand.

## Symptom

KaminIDE 1.0.110 on Windows: after the main window closes, its process and some of its child processes keep running without a window.

## Confirmed facts

- **WM_CLOSE path.** The installed KaminIDE 1.0.110 and a separate copy of the same build were started with `--do-not-de-elevate`. WM_CLOSE was posted to the main `Zed::Window`.
  - The window was destroyed within 31 ms.
  - The root process, the GPU process and both `kaminhost.exe` processes were still alive 30 s later (installed copy) and over 2 min later (separate copy).
- **Title bar close button.** It was pressed with a posted mouse click in the separate copy, which goes through `CzEvent::GracefulQuit` and `remove_window` in a frame.
  - The window was gone.
  - After 30 s the root, one CEF renderer and both `kaminhost.exe` were alive. The root used no CPU, and its diagnostics log stopped at the click.
  - Both close paths therefore hang after the window is gone.
- **Where the code goes after the window closes.** After the gpui run loop returns, `crates/shell/src/main.rs` calls `layout_store::flush_now()` and `web::shutdown()`.
  - `web::shutdown()` (`crates/shell/src/web/process.rs`) calls `cef::shutdown()` directly.
  - CEF runs with `multi_threaded_message_loop: 1`.
  - Browsers are closed only per view (`web/browsers.rs::close`). No path closes the remaining browsers, or waits for them to close, before `cef::shutdown()`.
- **Why the stop is after the run loop.** The diagnostics ticker runs on the gpui foreground executor and keeps printing while gpui waits in `finish_shutdown` (that loop still dispatches messages). The ticker stopped. So the process has left the gpui run loop.
- **Why updates do not show it.** The installer stops the instance's processes itself (`crates/installer/src/steps.rs`, `kill_in`).
- During the update of the installed copy, its forced stop left a Chromium «Something went wrong when opening your profile» dialog on the next start. It did not recur on the following start.

## Hypotheses

- `cef::shutdown()` blocks because browsers are still open. This is a known requirement of CEF's multi-threaded message loop: all browsers must be closed before `CefShutdown`.
- A relaunch while the hung instance is alive goes through the "previous instance is still exiting" recovery of #413, or is forwarded to the windowless instance. This needs a run.

## Expected outcome

Closing the window, by WM_CLOSE or by the title bar button, ends the instance: the root, the CEF processes and both hosts exit within 5 s. A relaunch then opens normally.

## Cause — proven 2026-11-16 (`kacc10`)

A copy of 1.0.111 built with full debug info was closed with WM_CLOSE and hung. Its main thread, read with a non-invasive debugger, was in the gpui-windows run loop's `finish_shutdown`, waiting in `MsgWaitForMultipleObjectsEx`. The loop drains `live_windows`, and its value was 1: one window object was never released.

- **What held it.** Every window registers an OLE drop target (`RegisterDragDrop`), and the target owns a reference to the window. The reference is released only by `RevokeDragDrop`, which works only while the HWND exists.
- **Why WM_CLOSE leaks it.** WM_CLOSE from outside the app (Alt+F4, the taskbar, Task Manager, `PostMessage`) reaches `DefWindowProc`, which destroys the HWND at once. The deferred revoke in `WindowsWindow::drop` then runs on a dead HWND and fails. The window object stays alive, and the drain waits forever.
- **The title bar button.** It removes the window through gpui, which revokes in time. In the reproduction on the unfixed build it exited in 1.7 to 3.3 s; one run with two Bridge sessions took 104 s, with the main thread inside `CefShutdown`.
- **The exit tail.** On every path, `web::shutdown` called `CefShutdown` with all browsers still open. CEF then closed them itself and waited for their processes. With the drain fixed, this was the remaining spread: `CefShutdown` took 0.26 to 4.4 s.
- **Toasts.** gpui quits only when no window is left, so an open toast kept the process alive until its 8 s auto-dismiss. A toast that arrived after quit began opened a window that nothing closed.

## Fix ([#999](https://github.com/dykamino-coder/gpui-kamin-ide/pull/999))

- **gpui-windows.** The window revokes its drop target in `WM_DESTROY`, while the HWND still exists, once. The drain in `finish_shutdown` gives up after 5 s and writes the number of windows still alive to the log.
- **Shell.** Before `CefShutdown`, exit closes every browser and waits up to 2 s for CEF to report each one closed. `diag.log` records each phase: the end of the window loop, the browser close and `CefShutdown`. gpui and platform errors (`log::error!`) now reach `diag.log`; before, the shell had no logger and they were lost.
- **Toasts.** When the last non-toast window closes, the open toasts close with it. Once quit begins, no new toast opens.
## Runtime result on the fix (2026-11-16)

These are 60 cycles of a separate copy, 10 for each of X and WM_CLOSE, each plain, with a toast and with two Bridge sessions. Each cycle was timed until the last process of the instance exited.

- **CPU under 80%:** 51 of 53 cycles exited within 3 s. The median was 0.45 s.
- **CPU at 80–100%, from other builds on the machine:** 6 of 7 cycles took 9–65 s.
- **Where the slow time went:** all of it inside `CefShutdown`, after every browser had closed in under 50 ms.
- **Profile:** the next start opened without the profile dialog.

The slow `CefShutdown` under load is tracked as its own follow-up with the captured stack. Acceptance of this card needs the published release.
## Reproduction

1. Start KaminIDE on Windows and wait for the main window.
2. Post WM_CLOSE (`0x0010`) to its top-level window of class `Zed::Window` (for example with `PostMessage` from PowerShell).
3. List the processes whose image is under the KaminIDE install directory: the root, the GPU process and both `kaminhost.exe` remain.
