# INC-2026-0073 — Claude chat and Bridge Console stay black after the CEF watchdog switches to software

- **Status:** confirmed — the mixed render mode is confirmed in source and in the owner's diagnostics; why the accelerated frames are black is still a hypothesis.
- **Registration author:** Claude, owner-directed registration, 2026-10-20.
- **Priority:** P1 — the main surface of the application (chat) is unusable until restart, and the restart can hit the same state again.
- **Completion target:** after the frame watchdog switches CEF to the software profile, no live view stays on shared textures, and every view draws its page. The implementer prepares a Change/Fix PR; the lead merges it.
- **Diagnostic PR:** pending (author registration).
- **Fix PR:** none.
- **Next step:** change. A watchdog that moves every live shared-texture view to the software profile when it switches, plus detection of accelerated frames that arrive but read back blank. Owner: implementer (Claude), then the lead for review and merge.
- **Private evidence:** not required. The input is the lead's sanitized reading of the owner's diagnostics log for KaminIDE 1.0.78, summarised below. No raw log lines, paths or screenshots are published or needed for this registration.
- **Dependencies:** none.
- **Acceptance:** automated merge gate — unit tests of the pure watchdog decision (which views to recreate, attempt limit, no recreate loop). Plus a Windows runtime check on a debug build: emulate the watchdog switch and observe that every view ends up in the software profile and draws.
- **Acceptance rationale:** the decision of which browsers to recreate is a pure function and can be tested exactly. Whether a recreated view actually draws depends on CEF and D3D11, so it needs a live run; the runtime check uses a profile copy driven by kamin-probe.
- **Windows runtime merge gate:** required for the functional fix — the scenario above on the exact candidate.
- **Deployment observation owner:** owner. After a release with the fix, start KaminIDE without `KAMIN_CEF_FORCE_SW` and confirm that the chat and Console draw.

## Symptom

On the owner's Windows laptop (KaminIDE 1.0.78), the Claude chat panel
(`claudeBridgeChat`) and the Bridge Console were completely black. The page
behind them was alive: the cursor changed shape over links and text, and CEF
kept delivering frames. It happened on two consecutive starts.

The owner's workaround is the environment variable `KAMIN_CEF_FORCE_SW=1`. It
puts every view in the software profile from the start, and then everything
draws. It is a workaround, not a fix.

## Confirmed facts

Source audited at `origin/main` `273497b` (KaminIDE 1.0.78).

1. **The software switch is process-wide, but the recreate is per view.**
   `respawn_stalled()` in `crates/shell/src/web/mod.rs` runs once a second.
   A view is stalled when it is visible, its browser was requested at least
   12 s ago, and it has neither a shared-texture frame nor a software frame.
   For each stalled view it calls `set_sw_mode(true)` and closes only that
   browser. `browsers::open` reads `sw_mode()` only when it creates a browser
   (`shared_texture_enabled: 0` or `1`). Browsers that are already live keep
   shared textures.
2. **The process switch is not applied.** The Chromium switch
   `disable-gpu-compositing` is added in `process.rs` only when
   `KAMIN_CEF_FORCE_SW` is set. After the watchdog switch, accelerated and
   software browsers share one CEF process.
3. **An accelerated frame always wins in the view element.** `element.rs`
   draws the shared-texture branch whenever `shared_texture::texture_for`
   returns a texture, and falls back to software frames only otherwise.
   `texture_for` copies the stored shared texture again on every window paint.
   The stored texture is the last `on_accelerated_paint` buffer. It is never
   refreshed while the page is static.
4. **The watchdog leaves the old frame state.** Unlike `reap_hidden`,
   `respawn_stalled` does not forget the view's shared-texture, copy or
   software frame state. Nothing stops a late accelerated frame from the
   closing browser from being stored for the view id.
5. **Owner's diagnostics (lead's reading, two starts).**
   - At start all four Bridge views (Console, Tools usage, Agents, Chat) were
     created with `cef_software=false`.
   - DXGI listed one adapter, Intel Iris Xe, `software=false`. The window
     renderer was not software. The machine is a laptop that also runs NVIDIA
     software, so hybrid graphics is likely, but the CEF GPU-process adapter is
     not in the log.
   - Tools usage and Agents never received a frame (neither accelerated nor
     software). Chat and Console received accelerated frames in the first
     2–3 s. After about 12 s the watchdog switched to software and recreated
     only Tools usage and Agents.
   - Second start: after the switch, the per-second frame line shows four view
     paints per window frame. There are no lines about a failed shared-texture
     open and no "no GPU texture and no software frame" warning. Chat and Console
     have no software frames, so they were painted from the accelerated copy.
     That copy was black on screen.
   - First start: the switch also recreated Console. Chat stayed accelerated
     and, per the owner, drew normally.

## Hypotheses

- **H1 — stale shared buffer.** Chat's last accelerated frame arrived at about
  2.2 s. Every window paint since then copies the same Chromium buffer. If
  Chromium recycles or clears that buffer (pool reuse, or GPU-process work for
  the recreated browsers), the copy turns black while the page stays static.
  This would explain why the first start drew and the second did not.
- **H2 — cross-adapter sharing.** On a hybrid laptop, the CEF GPU process may
  render on another adapter than the Intel device that GPUI uses. The shared
  handle opens, but its contents are not valid. This would also explain the
  silent Tools usage and Agents views.
- **H3 — never-delivered views.** Tools usage and Agents may have been silent
  for an unrelated reason, for example a first frame dropped before the D3D
  device was known. The watchdog then turned a per-view stall into a
  process-wide mode change.

None of these is proven. The fix below does not depend on which one is true.

## Expected outcome

- When the watchdog switches to software for any reason, every live browser
  created with shared textures is recreated in the software profile. That
  includes visible, hidden and never-reaped views such as the chat. Their old
  frame state is dropped, and accelerated frames that arrive late from a
  closed browser are ignored.
- A view whose accelerated frames are copied but read back blank counts as
  broken, the same as a stalled one.
- The attempt limit stays, and recreating cannot loop. Each browser migrates
  to software at most once, and stall respawns keep their limit of two.
- The chat reopens through the normal path (`ensure_html_view`, HTML store,
  view-state notification) and its conversation is restored.

## Missing evidence and blockers

None for the change. The underlying cause of the black frames (H1/H2) stays
open. Telling them apart needs a run on hardware that reproduces the issue,
with the new blank-frame counter enabled. That run is post-merge observation
and does not block the fix. The Windows runtime gate for the fix is not
claimed by this registration.
