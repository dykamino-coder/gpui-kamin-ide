## Symptom

During a running turn in Chat, the extension host process restarts (respawn).
Afterwards:

- Chat shows the turn as running for good, even after the CLI is idle;
- replies of messages that were already in the CLI native queue are not shown
  (they appear after an app restart, so the CLI did process them);
- a new message appears as `USER Queued` with `Cancel`, `Send now` and
  `Interrupt and send`, but never reaches the server;
- the tab still reports `connected`.

This matches the owner's report in INC-2026-0114 (queued messages never
delivered, `Send now` without effect), so it is one confirmed way to reach
that symptom.

## Environment and versions

- KaminIDE 1.0.95 (installed) and the #852 client candidate (1.0.95 exe with
  the #852 Chat bundle), each on a profile copy.
- Bridge server: the #852 tree on the acceptance stand.
- Driven in-process only (kamin-probe and the Chat debug API); the respawn was
  a kill of the app's own extension host child process by PID.

## Confirmed facts

- After the respawn, Chat received no submission or connection events; the
  server session was idle and its input count did not change when a new
  message was sent.
- Chat invokes that go through the extension host (`getConnectionState`,
  `forceSync`) did not return; a local call (`getVersion`) did.
- The new extension host opened its own connections to the server.
- Same result with and without the #852 Chat bundle.

## Cause

Established in source on 2026-11-13; live confirmation is the #863 Windows gate.

- The reproduction killed the kamin-host **parent** (the `kaminhost.exe`
  whose parent is the app), not the `--role=exthost` child. The gate owner
  confirmed this. The sidecar then starts a new kamin-host with a new
  endpoint. Its extension host is the first child of that parent, so
  `kamin:exthost:respawned` is never sent.
- The shell resets its per-view resolve guard only on that event. On the
  new connection every resolve of Chat, Plan and Console was skipped as
  already requested, and identical HTML from the new host was dropped. The
  new extension never resolved the Chat view or attached it to `BridgeHost`,
  so `Webviews.deliverMessage` dropped every message from the page. That
  explains the hanging invokes, missing events, permanent `working`, queued
  messages that never reach the server, and `resolve_tries=0` with no second
  resolve.
- On the same path, the old WS client's retry chain also connected to the
  new host. That left two clients on one host, so events were dispatched
  twice.
- The child-only respawn (BR-04, #832) is a different path. #863 checks it
  again in its live scenario.
