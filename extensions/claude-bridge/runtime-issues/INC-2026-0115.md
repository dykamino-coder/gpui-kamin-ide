# INC-2026-0115 — After an extension host respawn, Chat stops working and new messages stay "Queued"

- **Status:** confirmed (live on KaminIDE 1.0.95 and on the #852 client candidate); cause not yet established
- **Registration author:** @dykamino-coder, lead-directed registration by Claude Code maintainer `kmaint2` (2026-11-13), found during the Windows gate of #852 (INC-2026-0114), batch `RC-2026-11-13-KAMIN-BRIDGE`.
- **Completion target:** accepted and published fix. After the extension host respawns, Chat rebinds by itself: it receives submission and activity events again, its invokes return, and a message sent after the respawn is delivered or shows why it cannot be.
- **Diagnostic PR:** this registration.
- **Fix PR:** none yet; the lead gives the investigation and fix to the Codex `cxinc` worker, planned for 1.0.96.
- **Next step:** investigation. Find why the Chat webview keeps talking to the dead extension host channel after the respawn (BR-04 recovery path, #832), then change with a regression that respawns the host and checks events, an invoke round trip and one delivered message.
- **Private evidence:** [respawn runs](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/733772326d998a6f156b354a8cb8f3fd09e7fe77/incidents/INC-2026-0115/evidence/2026-11-13-respawn-chat-dead) (app captures of a profile copy; private only).
- **Dependencies:** related to BR-04 (webview recovery after respawn, #832) and INC-2026-0114 (same visible symptom).
- **Acceptance:** automated: a test that respawns the extension host under a live Chat binding and observes events, an invoke reply and a delivered submission afterwards. Then a live Windows run: messages queued during a long turn, a host respawn, then a new message; every message is delivered or shows a reason, and Chat leaves `working` when the turn ends.
- **Acceptance rationale:** the defect lives between the webview and the new extension host; only a real respawn shows that the binding comes back.
- **Windows runtime merge gate:** required; owner `kmaint2`.
- **Deployment observation owner:** owner (production use).

## Symptom

During a running turn in Chat, the extension host process restarts (respawn).
Afterwards:

- Chat shows the turn as running for good, even after the CLI is idle;
- replies of messages that were already in the CLI native queue are not shown
  (they appear after an app restart, so the CLI did process them);
- a new message appears as `USER Queued` with `Cancel`, `Send now` and
  `Interrupt and send`, but never reaches the server;
- the tab still reports `connected`.

This matches the owner's report in INC-2026-0114 (queued messages never
delivered, `Send now` without effect), so it is one confirmed way to reach
that symptom.

## Environment and versions

- KaminIDE 1.0.95 (installed) and the #852 client candidate (1.0.95 exe with
  the #852 Chat bundle), each on a profile copy.
- Bridge server: the #852 tree on the acceptance stand.
- Driven in-process only (kamin-probe and the Chat debug API); the respawn was
  a kill of the app's own extension host child process by PID.

## Confirmed facts

- After the respawn, Chat received no submission or connection events; the
  server session was idle and its input count did not change when a new
  message was sent.
- Chat invokes that go through the extension host (`getConnectionState`,
  `forceSync`) did not return; a local call (`getVersion`) did.
- The new extension host opened its own connections to the server.
- Same result with and without the #852 Chat bundle.

## Not checked

- Whether the webview is re-resolved after the respawn in this build; the
  app's view diagnostics show the Chat view alive with `resolve_tries=0`.
- Whether the #832 recovery runs and only Chat's channel stays stale, or
  recovery does not run at all.
- Agents and Console views after the same respawn.
