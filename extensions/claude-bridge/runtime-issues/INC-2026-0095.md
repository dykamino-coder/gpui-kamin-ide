# INC-2026-0095 — CLI mods never reach the Bridge server's CLI, and mod UI has no client channel

- **Status:** reported
- **Registration author:** studiohost. Found during the lead-assigned live matrix of the embedded workspace (headless host with `@kaminide/bridge-browser-client`).
- **Completion target:** a research result: whether and how Bridge delivers CLI mods (plugins whose `hooks/hooks.json` names a hooks module) to the CLI it runs, and which mod output an embedding or KaminIDE client can receive. The result includes a bounded change plan. Implementation is a later task.
- **Diagnostic PR:** [#722](https://github.com/dykamino-coder/gpui-kamin-ide/pull/722)
- **Fix PR:** none
- **Next step:** research. List what the user-data sync uploads per plugin, and check whether the server CLI loads a hooks module when its files are present (trust settings, PTY surface). Then decide on the client channel for `ui.render` / `$.ui.status` output. Owner: next maintainer run.
- **Private evidence:** not required. The facts below reproduce from public source and a synthetic test mod. The live run logs stay outside the repository.
- **Dependencies:** none.
- **Acceptance:** live. A test mod installed through Bridge loads in the session's CLI, which can be seen in its hook effect or the CLI debug log. The decided client channel, or its documented absence, is verified through `/bridge`.
- **Acceptance rationale:** loading depends on the real CLI build and the server sync, and unit tests of the sync alone cannot show that the CLI runs the module.
- **Deployment observation owner:** KaminIDE owner, after an implementation ships.

## Symptom

A minimal mod (`hooks/hooks.json` with `{ "modules": ["./register.tsx"] }`, a
`ui.render` hook on `AbovePrompt` and `$.ui.status` in `session.start`) passes
`claude plugin validate` on the Bridge server's CLI 2.1.312. It was installed
through `plugins:install` from a local marketplace in an embedded workspace.
In a new session nothing of it appeared, neither in the transcript nor in the
raw terminal stream the client receives (`pty-output`). Plugin monitors
installed the same way worked.

## Confirmed facts

- On the Bridge server the synced plugin directory of the mod contains only
  `.claude-plugin/plugin.json`, and the synced `plugins.json` records
  `"hooks": {}` for it. The hooks module files are not uploaded.
- The sync (`extension/src/main/sync/plugin-snapshot.ts`) uploads the manifest
  and the text of skills, commands and agents. It turns event hooks into
  proxied hooks. It has no handling for hooks modules.
- No Bridge source refers to hooks modules or `ui.render`.
- Bridge runs the CLI in a PTY on the server. Any mod UI drawn by the CLI's
  terminal surface could reach a client only inside `session:output` →
  `pty-output` bytes. No structured event exists.
- Plugin monitors are not affected: the workspace host starts them itself
  (`extension/src/main/plugin-monitors.ts`) and pushes `monitor:*` events.

## Hypotheses

- Copying the plugin's `hooks/` module files (and declared `types`) in the sync
  may be enough for the CLI to load the mod. The CLI may still refuse a module
  from settings it does not trust.
- A structured client channel for mod UI may need a CLI surface other than the
  terminal, which Bridge does not have today.

## Expected outcome

A documented decision: whether mods are delivered to the session CLI, which
mod effects (hooks, status line, panes) reach clients and through which
channel, and the tests that prove it. No behavior change is part of this
registration.

## Missing evidence and blockers

None for the research step.
