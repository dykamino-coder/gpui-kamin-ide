## Symptom

A `/resume <session id>` typed into the chat is executed by the CLI, but its
item stays in the Message Queue panel as PENDING ("Cleared once the CLI picks
up the message"). Each further `/resume` adds one more stuck item.

## Environment and versions

- KaminIDE 1.0.92 on Windows 11 (a copy of the owner profile), Bridge server
  image 6.3.169 in the acceptance container, Claude Code CLI 2.1.322, model
  `claude-opus-5-5`. Not re-run on 1.0.93 / 6.3.170.
- The chat was driven through CDP (`KAMIN_CEF_CDP`) without taking over the
  screen. The release exe has no `kamin-probe`; whether release acceptance
  should have such a tool is an open acceptance-tooling question, not a defect.
## Reproduction steps

1. Open a Claude Bridge chat session and run one turn, so that there is a
   session id to return to. Send `/clear`.
2. Send `/resume <id of the first session>`.
3. Wait. The panel shows "Message Queue / 1 PENDING / #1 /resume <id>".
4. Send a prompt that uses a tool, wait for the answer, then send another.

Observed: both turns are answered and are written to the transcript of the
resumed session; the CLI process runs with `--resume <id>`. The panel still
shows "1 PENDING" with the `/resume` item after both turns.

5. Send `/clear` and then the same `/resume <id>` again.

Observed: the panel shows "2 PENDING" with two identical `/resume` items.
They were still there about a minute later and after one more answered turn.

## Confirmed facts

- Seen in one run on Windows; the counts 1 and then 2 are from the step log.
- The command itself works: the resumed transcript receives the following
  turns, and the server log has no "Session destroyed" for the period.
- Ordinary prompts sent the same way did not stay in the queue.

## Hypotheses

- A queue item is cleared when the CLI transcript records the same user
  message; `/resume` switches the transcript and is never recorded as a user
  row there, so nothing matches. Not checked in source.

## Expected outcome

The queue item of an executed `/resume` disappears; no item stays PENDING
after the CLI has acted on it.

## Missing evidence and blockers

- How long the items live (reload of the chat, session reopen) was not tested.
- Whether other local commands (`/clear`, `/effort`) can stick the same
  way: `/clear` did not in this run; others were not tried.
