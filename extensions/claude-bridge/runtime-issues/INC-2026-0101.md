## Symptom

A `/resume <session id>` typed into the chat is executed by the CLI, but its
item stays in the Message Queue panel as PENDING ("Cleared once the CLI picks
up the message"). Each further `/resume` adds one more stuck item.

## Environment and versions

- KaminIDE 1.0.92 on Windows 11 (a copy of the owner profile), Bridge server
  image 6.3.169 in the acceptance container, Claude Code CLI 2.1.322, model
  `claude-opus-5-5`. Not re-run on 1.0.93 / 6.3.170.
- The chat was driven through CDP (`KAMIN_CEF_CDP`) without taking over the
  screen. The release exe has no `kamin-probe`; whether release acceptance
  should have such a tool is an open acceptance-tooling question, not a defect.
## Reproduction steps

1. Open a Claude Bridge chat session and run one turn, so that there is a
   session id to return to. Send `/clear`.
2. Send `/resume <id of the first session>`.
3. Wait. The panel shows "Message Queue / 1 PENDING / #1 /resume <id>".
4. Send a prompt that uses a tool, wait for the answer, then send another.

Observed: both turns are answered and are written to the transcript of the
resumed session; the CLI process runs with `--resume <id>`. The panel still
shows "1 PENDING" with the `/resume` item after both turns.

5. Send `/clear` and then the same `/resume <id>` again.

Observed: the panel shows "2 PENDING" with two identical `/resume` items.
They were still there about a minute later and after one more answered turn.

## Confirmed facts

- Seen in one run on Windows; the counts 1 and then 2 are from the step log.
- The command itself works: the resumed transcript receives the following
  turns, and the server log has no "Session destroyed" for the period.
- Ordinary prompts sent the same way did not stay in the queue.

## Hypotheses

- A queue item is cleared when the CLI transcript records the same user
  message; `/resume` switches the transcript and is never recorded as a user
  row there, so nothing matches. Not checked in source.

## Expected outcome

The queue item of an executed `/resume` disappears; no item stays PENDING
after the CLI has acted on it.

## Missing evidence and blockers

- How long the items live (reload of the chat, session reopen) was not tested.
- Whether other local commands (`/clear`, `/effort`) can stick the same
  way: `/clear` did not in this run; others were not tried.

## Source-trace follow-up — 2026-11-13 (cxstats)

Source baseline: `32109f31cd9a4940726d216e5deae03aef1220d5`, compared with
`origin/main` `848ac4618d81dad519958060fccb7200489bc5d9`. This is a trace of
production routing, not a new CLI reproduction or a queue fix.

- `pty/session-cli-control.ts::submit` returns false for slash commands before
  entering addressed native submissions. A healthy native mod therefore does
  not itself give `/resume` an addressed submission receipt.
- `webview/shared/submission-queue.ts::matchSubmissionQueue` accepts user text,
  queued-command attachments, and system content containing `<command-name>`.
  A standalone empty `<local-command-stdout>` row is not a candidate. Command
  candidates are compared as normalized raw text, not parsed into a command
  name, arguments and submission identity. Even a nonempty local-command row
  needs its exact emitted shape checked before it can be called an acknowledgement.
- `webview/src/signals/queue.ts` applies that matcher to its legacy local
  mirror; host-owned items are reconciled by the host. A local mirror timeout
  is cleanup, not proof that a particular command completed. A future receipt
  must settle the owner of the item, including after reattach, rather than
  only hiding one page's queue display.

**Next artifact:** queue executor retains the actual command row/receipt shape
with a synthetic submission id and route. The regression matrix needs two
identical resumes, success versus cancellation, an unrelated local command,
and reattach, for both queue owners. A transcript identity switch (0102) alone
must not acknowledge an arbitrary queue item. The existing automated gate is
unchanged; no paid provider request is needed to investigate this boundary.

## Fix — 2026-11-17 (kacc13)

Source base: `0faa1bcd` (KaminIDE 1.0.113 / Bridge 6.3.190). Change PR: [#1022](https://github.com/dykamino-coder/gpui-kamin-ide/pull/1022).

**Observed row shapes (CLI 2.1.322, stub model, no model turn).** `/clear` writes a
meta `<local-command-caveat>` user row, a user row with
`<command-name>/clear</command-name>` and a *system* row with an empty
`<local-command-stdout>`. `/model sonnet` writes the caveat, a user row with
`<command-name>/model</command-name>` and `<command-args>sonnet</command-args>`,
and a *user* row with its `<local-command-stdout>`. An inline `/resume <id>`
writes no row; its only report is `SessionStart` with `source: resume` and
`session_id: <id>`.

**Root cause.** Two independent gaps. (1) The resumed transcript has no row
for `/resume`, and its positions are below the old watermark, so no row could
ever confirm the item, in either queue owner. (2) The matcher compared a typed
command as raw text against `<command-name>` markup, which never matches
(`/model sonnet` stuck the same way), and short items such as `/clear` fell back
to position order, where the empty command-output row consumed them.

**Fix.**
- Server: a terminal-delivered `/resume` (`/continue`), `/clear` (`/reset`,
  `/new`) or `/compact` with a submission id is tracked per session. The
  matching `SessionStart` (same source; for `/resume <uuid>` the same
  `session_id`) settles the oldest such item with a correlated receipt
  `{ id, state: 'fallback', committed: true }`; one event settles one item.
  Completed receipts are resent on reattach.
- Desktop webview and browser host: a committed fallback receipt removes the
  item (desktop) or marks it consumed (browser host, persisted), also when it
  is first seen after a reload.
- Shared matcher: a typed slash command is confirmed only by a row recording
  the same command name and arguments; command-output rows are never
  candidates, and slash commands never use position order.

**Checks.** New tests fail on the base and pass with the fix: server
`terminal-command-receipts.test.ts`, webview `queue.test.ts` and
`submissions.test.ts`, workspace `presentation.test.ts`. Live, on a disposable
container of the published 6.3.190 image with the branch server sources and a
dummy key: `/clear`, `/clear`, `/resume <seeded id>` (pause 10 s and 0 s), then
`/model sonnet`. The base server sent no completion receipt; the branch server
sent a committed receipt for each `/clear` and for `/resume` (about 0.3 s after
sending), and the view ended on the resumed transcript with its history. The
captured frames, replayed through the real desktop queue and browser host
code, leave no pending item with the fix; with the base client code `/resume`
and `/model sonnet` stay pending in both owners. Raw frames stay in the private
diagnostics folder.

**Remaining.** A `/resume` cancelled in the CLI picker emits no event: the
desktop item expires after the 10-minute TTL, the browser host item needs
Dismiss. Publication and a check in the released build are open.
