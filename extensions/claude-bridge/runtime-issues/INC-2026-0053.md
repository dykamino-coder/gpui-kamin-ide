## Symptom and scope

The KaminIDE model picker offers explicit Opus 5.5 and Opus 5 IDs and sends a
model-change request for the active tab. The code implements a restart for an
empty conversation and an in-place `/model <id>` command for a conversation
with a CLI ID. The in-place path has two source-confirmed state defects:

1. The server reports `session:model-changed` and updates `session.model`
   immediately after writing the command to PTY stdin. It does not wait for the
   CLI to accept or apply the model. `writeInputToSession` silently returns when
   the PTY is not running, so the success notification is not even conditional
   on a write. A rejected or queued `/model` can therefore be shown as already
   active. Whether and when the pinned CLI applies this command while streaming
   still requires live verification.
2. The extension forwards that in-place notification as `session-restarted`.
   The webview handles every `session-restarted` by setting `needsClear`; its
   next PTY-output handler clears the Console buffer. A hot switch did not
   restart the PTY, so this discards live Console scrollback unnecessarily.

A third source-level persistence gap affects a switch followed by a disconnect
or full restart **before the next real assistant response**. The fresh
`session:resume` request carries no selected model. `createSession` recovers its
model from the last assistant row in JSONL; that row still has the *previous*
model. It then writes the previous model into `settings.local.json` and passes
it as `--model`, which takes precedence over Claude Code's restored model.
Thus the picker can report the new selection in the live tab and revert to the
old model on the next spawn. Reattachment to an already-running PTY is a
different path and should retain its in-memory `session.model`.

The observed rejection does not prove that every model switch fails. The
empty-conversation restart path and new-session default are separate and
already have focused argument tests.

## Field observation (2026-09-24)

On KaminIDE 1.0.55, a user selected Fable 5 from an existing Opus 5 session.
Claude Code showed a `Switch model?` confirmation in Console, but the chat
input picker already displayed Fable 5 before the user answered. The user
selected `No, go back`. Claude Code reported that it kept Opus 5, while the
input picker still displayed Fable 5. It returned to Opus 5 only after a
disconnect and reconnect. This confirms the premature-success UI symptom;
the screenshots do not establish whether accepting the prompt persists across
a later CLI respawn.

The confirmation appeared in Console, while the main Bridge chat did not
present an actionable question. A user with Console hidden can therefore miss
the prompt and leave the switch pending. The chat later displayed a local
command result, which is not a substitute for the pending choice.

### Confirmed switch lost after reconnect (2026-09-24)

The same user then opened an older conversation in KaminIDE 1.0.55 and selected
Fable 5 from the Opus 5 picker. This time Claude Code 2.1.236 reported
`Set model to Fable 5`. Its `/status` screen showed `claude-fable-5` before
disconnect. After `Disconnect → Connect` in the same conversation, `/status`
showed `claude-opus-5`, and the chat input picker also showed Opus 5. The old
assistant message claiming Fable 5 was still visible in the chat, so that
message must not be used as evidence of the current model. The two `/status`
screens establish the actual before/after CLI selection without exposing the
conversation, account details or session identifier in this public card.

The reconnect result is consistent with a new CLI spawn on the older Bridge
6.3.132 code path: its `session:resume` request carries no selected model and
`createSession` rewrites the per-session `.claude/settings.local.json` with the
server default Opus 5, then passes Opus 5 through `--model`. The deployed server
image tag was not captured, so this source explanation remains an inference.
The 6.3.134 transcript-model restore path added by #132 may behave differently
after an assistant response; it still has the before-next-response gap described
above. The `/status` screenshots were supplied in the user conversation and
were not copied into the public repository.

Claude Code's `/model <id>` also saves a user default in `~/.claude/settings.json`
([model configuration](https://code.claude.com/docs/en/model-config)). In the
Bridge image, every CLI uses `HOME=/home/bridge`; this path is in the persistent
container volume and is distinct from both Windows client settings and the
generated per-session `settings.local.json`. Bridge currently passes explicit
`--model` on fresh sessions, which outranks that saved user default. The
maintainer should still verify that a switch in one Bridge token cannot change
another token's effective model through shared Claude Code state.

## Source evidence

- `webview/src/components/dropdown/ModelDropdown.tsx:10-43` lists explicit
  model IDs and sends `bridge.changeModel(tabId, id)`.
- `server/src/core/pty/session-ws.ts:575-592` sends `/model` and immediately
  changes server/UI state; `server/src/core/pty/session-io.ts:113-116` can drop
  input for a non-running PTY without reporting failure.
- `extension/src/main/ws/handle-server-message.ts:399-407` maps the in-place
  event to `session-restarted`; `webview/src/hooks/useBridgeListeners.ts:303-312`
  marks the terminal for clearing, and lines 234-243 clear it on next output.
- `server/src/core/pty/session-ws.ts:406-420` omits model from a fresh resume;
  `session-core.ts:170-177` and `session-resume-helpers.ts:372-405` select the
  last assistant model; `session-settings.ts:182-194` and
  `session-env.ts:198-211` write/pass that model to Claude Code.
- `server/src/core/pty/session-env.model.test.ts` covers new-session and
  transcript-resume arguments, but not in-place switch acknowledgement,
  Console preservation or the before-next-response resume transition.

## Expected outcome

- In each tab, the displayed selected model matches the model the CLI will
  use for the next request. A pending, rejected, unavailable or delayed switch
  is reported honestly; no silent model substitution is introduced.
- A model-change confirmation is actionable in the main Bridge chat when the
  Console is hidden. Rejecting it restores the original model in the picker
  without requiring disconnect/reconnect; accepting it updates only after
  CLI confirmation. Avoid a second concurrent prompt when Console is open.
- An in-place switch preserves the Console buffer. An actual PTY restart may
  clear it at the appropriate new-output boundary.
- A confirmed switch survives disconnect, app restart and server PTY restart
  even when no assistant response has yet recorded the new model in JSONL.
  Existing Opus 5 sessions stay on Opus 5 unless the user explicitly changes
  them; fresh sessions keep the Opus 5.5 default.
- A model change in one token does not change another token's effective model
  or rely on Claude Code's container-wide saved user default.
- Tests cover an active and empty conversation, idle and streaming requests,
  rapid consecutive selections, switch confirmation and rejection with Console
  visible/hidden, next-response verification, reconnect to a live PTY, full
  respawn, multiple tabs and Console scrollback.
  Verify behavior against the pinned CLI and exact Windows candidate when a
  test environment is available.

## Missing evidence and blockers

There is now a real `/status` before/after result for 1.0.55 and Claude Code
2.1.236, but no authenticated reproduction on the newer 1.0.57/6.3.134 flow.
The maintainer should capture a synthetic conversation's requested model,
CLI-confirmed active model and first subsequent assistant `message.model`
across switch and resume, without prompts or tokens. Test both reconnect to
a live PTY and a fresh CLI spawn, before and after the next assistant response.
