## Symptom

Logging out of the dashboard can restart its background WebSocket connection.
A quick logout/login can leave callbacks and retries from the previous connection
interfering with the current connection and its displayed connectivity state.

## Confirmed facts

Audited source: `a34ab4892058bcacc00de8d97ae951fb60551780`.
Paths below are relative to `extensions/claude-bridge/server/src/ui/src/`.

- `App.tsx:24–30` connects while authenticated and intentionally disconnects
  during effect cleanup. `signals/auth.ts:85–96` makes logout a normal trigger.
- `services/ws-client.ts:16–19` cancels only an already scheduled timer and
  closes the socket. Its `onclose` handler remains installed; lines 30 and
  38–40 schedule another connection when the asynchronous close event arrives.
- No stopped flag or connection generation rejects that callback. `connect`
  also leaves older scheduled retries and socket callbacks valid.
- An actual-source VM test with an asynchronous fake close event created a
  second socket after `disconnect()`. Source/caller review independently
  confirmed the ordering. No real network connection was opened by the test.
- Server authorization is a separate guard. This finding does not establish
  an authentication bypass or any observed data exposure.

## Hypotheses

The frequency of duplicate sockets and background retries in deployed browsers
has not been measured. A missing heartbeat or general Bridge reconnect failure
is not claimed; BR-05 and BR-24 concern different client/transport boundaries.

## Expected outcome

Give the dashboard connection an explicit lifecycle owner. An intentional stop
must cancel retries and invalidate all callbacks from prior sockets; a genuine
unexpected close may still reconnect. Keep at most one current connection and
one retry associated with it.

Required tests cover delayed close after disconnect, stop while retry is pending,
logout/login before old close, old open/message/error callbacks, repeated connect,
and ordinary reconnect. An isolated dashboard gate must show that logout stops
background connection attempts and subsequent login receives one current stream.
Native Windows UI and authenticated production data are not needed for the
automated contract; browser runtime acceptance remains outstanding.

This research card authorizes no functional fix or release in the present batch.

## Local maintainer preparation — 2026-10-09

Under owner instructions permitting fix, tests, push and PR (no merge/release), the current
source at `a0a21dc` still reproduces the lifecycle defect. No upstream result
or closed status is claimed.

The local change invalidates old socket callbacks on intentional stop or
replacement, cancels pending retries, and permits one retry only for the current
connection. Socket identity also rejects late callbacks after ordinary reconnect.
Six synthetic tests exercise delayed close, retry cancellation, logout/login
ordering, stale open/message/error callbacks, repeated connect and constructor
failure. Five fail against the unchanged source; all six pass with the change.

An isolated Chrome test with a real loopback WebSocket verifies that intentional
stop opens no new connection after the retry interval, subsequent connect has
one current stream, and unexpected close reconnects once. This checks the socket
service contract; authenticated dashboard logout/login through App UI was not
run. Production credentials and user data were not used. The incident remains
open pending maintainer acceptance and the remaining dashboard UI scenario.
