## Symptom

При близких replay/resync Agents может сохранить старый или пустой snapshot
после завершения новой загрузки. Следующие live entries продолжают поступать,
но остаются в staging вместо обновления дерева. Для дефекта достаточно
правильной доставки всех сообщений; потеря wake или transport frame не нужна.

## Confirmed facts

1. `extensions/claude-bridge/webview/src/hooks/useBridgeListeners.ts:391–395`
   создаёт новую generation при replay start. Completion на строках 400–426
   задерживает переход на 50 ms; callback сначала ставит `tabJsonlLive=true`
   на строке 415 и лишь затем проверяет generation через publish на строке 418.
2. `extensions/claude-bridge/webview/src/signals/agent-replay.ts:42–44`
   корректно отвергает старую generation. Однако уже изменённый live flag
   заставляет handler следующего completion пропустить обработку на
   `useBridgeListeners.ts:400`. Новая generation остаётся staged, а строка 349
   направляет туда последующие batches вместо live parser.
3. Actual-source synthetic ordering `G1 start → G1 complete → G2 start →
   delayed G1 callback → G2 complete` оставил live=true и G2 staged; G2
   completion не создал publish timer, следующий live entry тоже остался
   staged. Stale callback дополнительно вызвал `markAllAgentsExited`.
4. Повторные replay requests разрешены в
   `extensions/claude-bridge/extension/src/main/ipc/sessions.ts:199–223`.
   `extensions/claude-bridge/extension/src/main/ws/connection-manager.ts:707/722`
   повторно отправляет start/completion. Правильное flush ordering предыдущего
   continuation в `extensions/claude-bridge/extension/src/main/ws/jsonl-batcher.ts:91–105`
   не отменяет отложенный renderer callback. Его timer также не очищается
   при cleanup hook (`useBridgeListeners.ts:800–801`).

## Hypotheses

Windows frequency и видимое время зависания не измерены. Это integration
остаток BR-26: существующая helper generation защита работает, но не охватывает
более ранние side effects caller. Более поздний replay/reset/close может
восстановить состояние; вечное зависание всего приложения не заявлено.
BR-31 является отдельным pump defect и не устраняет этот ordering даже при
идеальной доставке. Реальный размер возможного staging growth ещё не измерен.

## Expected outcome

Bounded Change/Fix PR должен сделать completion единым generation-scoped
переходом для live/progress/tree/cleanup. Stale callback после нового replay,
tab close или listener restart не меняет состояние. Добавить тест на actual
status-listener boundary, а не только прямой вызов publish helper.

Automated acceptance: указанная ordering, оба completion timers в очереди,
close/reconnect до callback и live agent update после G2. Staging после
завершения пуст, snapshot опубликован один раз, старая generation не архивирует
агентов нового состояния. Windows CEF gate повторяет reveal/resync и быстрые
session switches с работающими teammates; rows/badges остаются согласованными
и live updates продолжаются без repaint workaround. Исследование не выполняло
этот UI gate и не закрывает BR-25/31.
