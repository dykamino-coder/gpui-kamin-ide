# INC-2026-0005 — Session-switch cover does not finish its timeout fade

- **Status:** confirmed (source-level; not fixed)
- **Priority:** P2
- **Diagnostic PR:** this incident's enclosing Diagnostic PR (indexed in the research report)
- **Fix PR:** none
- **Private evidence:** [INC-2026-0005](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/01ba06fd8ac90a9fae31d40e18ccd49e29950492/incidents/INC-2026-0005)

- **Acceptance:** automated deadline/state tests + Windows CEF runtime merge gate
- **Corporate observation owner:** none

## Symptom

If a session switch receives no readiness acknowledgment, its opaque loading
cover can remain indefinitely instead of ending after the documented 2.5-second
fallback. The ordinary success path can work. Missing acknowledgment is the
trigger here; this incident does not claim to explain why that acknowledgment
was lost or to fix the BR-31 delivery pump.

## Confirmed facts

Source revision: `a34ab4892058bcacc00de8d97ae951fb60551780`.
Short `state/`, `ui/` and `web/` paths below are relative to `crates/shell/src/`.

- `crates/shell/src/state/events/sessions.rs:139` arms the cover with no cleared
  timestamp. Readiness acknowledgment persists a timestamp at lines 76–78 or
  225–229.
- `state/contributed_webview.rs:72–89` computes timeout using
  `self.chat_cover.and_then` by value. After 2500 ms it creates a local
  `Instant::now()` but never stores that timestamp back into the cover state.
- On every subsequent render, the local timestamp is new. The elapsed fade time
  at lines 84–85 returns to approximately zero and opacity remains approximately 1.
  No other writer commits the fallback transition.
- The 30 CoverTick events scheduled at `state/events/sessions.rs:206–215` request
  more renders but do not update that state.
- A deterministic translation of this branch returned opacity 1 at 2500, 3000,
  10000 and 60000 ms without acknowledgment. With acknowledgment persisted at 3000 ms,
  it correctly returned no cover at 3200 ms. This is source-model evidence, not
  execution of Rust/GPUI or a Windows reproduction.

The cover's native repeat animations are present in
`ui/chat_switch_skeleton.rs:100,121,146`; a permanently mounted cover can continue
requesting frames. No CPU percentage or production failure frequency was measured.

## Hypotheses

Failed/disconnected activation or a delivery failure can withhold readiness.
Native runtime acceptance must establish the visible result and preserve session
identity when choosing the timeout outcome; blindly uncovering stale content is
not an acceptable substitute for a bounded loading state.

## Expected outcome

Make the timeout/fade transition durable and define a bounded outcome when
readiness never arrives. Pure state tests cover repeated renders, no readiness,
readiness before/after grace and deadline, another switch, and stale readiness
from a previous switch.

The Windows gate withholds acknowledgment in a disposable scenario and verifies
that the cover either ends coherently or becomes an explicit error/retry state.
A successful switch must preserve existing grace and fade behavior, keyboard
focus and the correct session content. After loading ends, decorative activity
must stop requesting frames. Retain BR-31's separate event-delivery gate; this
cover test is not evidence that transport starvation has been corrected.
