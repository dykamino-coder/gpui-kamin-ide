## Symptom

При backpressure соединения Bridge запрос `AskUserQuestion` может не попасть
на клиент, хотя сервер считает его доставленным. Пользователь не получает
вопрос, а серверный pending request остаётся незавершённым после освобождения
буфера и повторного подключения. Приоритет P1: потеря управляющего запроса
останавливает выполнение текущего инструмента. Частота в production не измерена.

## Confirmed facts

Source snapshot: `a34ab4892058bcacc00de8d97ae951fb60551780`.

- `server/src/core/pty/mcp-tools-defs.ts:286` публикует `AskUserQuestion`;
  обычный `tools/call` проходит через `mcp-http-handler.ts:454–480` и
  `session-core.ts:985–992` в `sendMcpCall`. Все пути относительны
  `extensions/claude-bridge/`.
- `server/src/core/pty/session-io.ts:90–108` возвращает `false`, когда
  `bufferedAmount` превышает 16 MiB либо отправка/сериализация завершается
  ошибкой. Состояние сокета при переполнении может оставаться `OPEN`.
- `session-mcp-call.ts:63–83` не ставит timeout интерактивному запросу,
  вычисляет `delivered` исключительно по `OPEN` и игнорирует результат
  `sendToClient`. `resendUndeliveredMcpCalls` в том же файле, строки 95–105,
  пропускает такой request и повторяет ошибку предварительного `delivered=true`
  при собственной отправке.
- Actual-source synthetic harness исполнил неизменённые функции с инертным
  сокетом: при cap rejection отправлено ноль frames, сохранены
  `delivered=true`, `timer=null`. После сброса backpressure и вызова resend
  осталось ноль frames и один незавершённый pending request. Независимый
  cross-review повторил результат.
- Retry основного JSONL watcher относится к его frames и не исправляет MCP
  delivery state. SSE cancellation очищает heartbeat, но не этот request.
  Restart/destroy/shutdown очищают pending; reaper сохраняет абсолютный предел
  жизни session 24 часа. Это не бесконечная жизнь процесса и не запрет пользователю
  прервать или перезапустить session.

## Hypotheses

Не измерены production частота, длительность backpressure и фактическая нагрузка.
`EnterPlanMode`/`ExitPlanMode` также присутствуют в interactive timeout set, но
их штатная доступность как Bridge tools этим artifact не подтверждается.

Synthetic validation проверяет delivery contract; настоящий Linux PTY,
authenticated CLI и Windows question widget не запускались. Потеря подтверждена
на серверной границе до получения request клиентом, без предположения о CEF.

## Expected outcome

Отдельный Change/Fix PR должен связывать delivery state с успешной постановкой
в transport и определять bounded retry либо явное завершение при отказе.
Повторная попытка не должна повторно выполнять уже доставленный инструмент с
побочными эффектами. Functional fix в этом Diagnostic PR отсутствует.

Automated gate покрывает first-send rejection, resend rejection, исключение
send, disconnect до/после enqueue, повторный reattach и интерактивный запрос без
обычного tool timeout. Disposable Linux gate подтверждает обработку slow-client
на реальном transport. Если PR заявляет восстановление UI, нужен Windows gate:
вопрос появляется один раз, ответ завершает нужный request, соседняя session
продолжает работать.

BR-24 и BR-31 относятся к host→CEF invoke/pump и не являются исправлением
этого server→client MCP пути. Не дублировать их implementation scope.

## Windows runtime acceptance (2026-10-11)

Post-merge acceptance of fix PR #153 on current `main` (`ec6e9a1`) in an isolated Windows KaminIDE
(separate desktop, own probe port and profile; Bridge server, when needed, in Podman with the
credential-free fake CLI), with the defect reproduced first on a local before-fix variant.
In-container proxy stalls the server→client direction while replays push the server socket past the 16 MiB send cap; a host-tool MCP call issued then is rejected by the cap; the transport is dropped and the client reattaches. On main the call is resent and executes once; with 969c799 reverted the call is never resent and the tool never runs. The fake CLI issues a Bash tool call (same sendMcpCall/delivered/resend path) rather than AskUserQuestion.
Evidence: [INC-2026-0011 runtime acceptance](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/afa842e04f473d00c3550eec7d8ccd4d5d7ce591/incidents/INC-2026-0011).
