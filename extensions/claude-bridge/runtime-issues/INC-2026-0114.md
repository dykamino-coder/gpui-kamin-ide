## Symptom

Usually, messages typed in Chat while a turn is running are queued and
delivered, and `Send now` works. Rarely, queued messages stay in the state
`USER Queued` with the buttons `Cancel`, `Send now` and `Interrupt and send`
and are never delivered:

- the Bridge Console of the same session shows no queued input, and the turn
  keeps running (in the reported case a long turn of almost three hours under
  `/goal`);
- `Send now` has no visible effect;
- only `Cancel` works.

## Environment and versions

- Production Bridge server and the owner's KaminIDE client (versions not
  captured in the report).
- One screenshot; no logs, no session id, no time of the queueing.

## Confirmed facts (source, `main` `87dbcb1d`)

- The badge comes from `webview/src/components/jsonl-viewer/SubmissionBadge.tsx`. `Queued` with `Send now` means the server state `queued`, which is Bridge's own queue before delivery, not the CLI's native queue (that state is labelled differently and has no `Send now`).
- `server/src/core/pty/cli-submissions.ts`: `Send now` (`push`) only calls `drain()`. `drain()` also runs every 100 ms while the session is running.
- `drain()` returns without changing the item or showing a warning when another submission is marked as being dispatched, or when the session input snapshot reports an active input kind, queued native submissions or pending maintenance. Only a dirty terminal draft produces a visible warning.
- The "being dispatched" mark is cleared by a read receipt, by a fallback, by the delivery handshake callback, or by `uncertain()`.

## Hypotheses (not established)

- A lost event or race leaves the "being dispatched" mark or an input snapshot flag set, so every later `drain()` returns silently: a read receipt or handshake callback that never arrives, a client reconnect, an extension host respawn, or a session rebind during delivery.
- The client shows a stale `queued` row from a replay while the server item is already gone or in another state.

## Not checked

- Server logs of the reported session; whether the client had reconnected or the extension host respawned before the messages were queued.
- Whether the first queued message was ever in `Sending`.
