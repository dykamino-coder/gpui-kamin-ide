## Symptom and evidence boundary

After moving to another Windows 11 computer, KaminIDE 1.0.55 opens, displays
its restored chat/project list and disappears after a few seconds. The owner
reports that no warning appears and the application is absent from Task
Manager. Failures began before copying the old plugin directory and user
settings file. Some session/layout state had already been transferred; the
complete migration sequence and whether the CEF cache was copied are unknown.

## Confirmed facts

- All four crash logs identify application version 1.0.55 and process role
  `main`, with an exception in `libcef.dll` 2.462–2.662 seconds after the
  corresponding main-start record. They record exception code `0x80000003`,
  Microsoft's [STATUS_BREAKPOINT](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55).
  This classifies the exception, not the underlying fatal assertion or cause.
- Each log contains the same module sequence across 24 reported stack entries,
  including 17 `libcef.dll` entries. Raw addresses are retained privately;
  no DLL load-base verification, symbolization or exact CHECK attribution has
  been performed. Do not treat a different absolute address as a different bug.
- The four host incident files each contain only `host-log-start`; none records
  an extension-host exit. Current host output reaches successful activation of
  the bundled Bridge extension and six webview-provider resolutions. This does
  not establish successful page rendering, server connection or session resume.
- `diag.log` contains seven boot markers and 779 lines, including software-paint
  telemetry from some runs. Its metrics have no wall-clock timestamps/PIDs,
  so those samples cannot be assigned reliably to the four timed crashes.
  The last two boot sections each have one metric row with zero CEF frames.
  There is no renderer-death counter in the supplied diagnostic log.
- The layout JSON parses and restores Chat and Console panel selections. It
  does not establish which sessions were active or prove a layout defect.

Source countercheck baseline: `db4708663269d461bdf46112e5cedb8e47d34210`.
`crates/shell/src/main.rs` installs the native exception handler with role
`main`; `crates/crash/src/lib.rs` records that process's exception. This is
not the renderer-termination callback in `crates/shell/src/web/browsers.rs`.
`crates/shell/src/web/process.rs` initializes the native CEF runtime and its
persistent cache, configures the subprocess helper and selects software mode
for an RDP startup. These are investigation entry points, not proven causes.
Relevant exception/startup source is unchanged from release-source commit
`d9321a173bcf61ea7493a5d10eb82c1244ed1dee`; the installed artifact hashes and
CEF version are still unverified.

## Confirmed launch trigger — shortcut working directory

**Supplement author:** @dvpetrochenko. **Evidence:** a private bounded packet
contains the owner-provided September 18 launch captures, exact hashes and the
comparison matrix. The private link above is pinned to the immutable merge
commit containing this supplement.

The controlled comparison was performed on the same Windows 11 host with
KaminIDE 1.0.55, a clean application profile, no Bridge token, no restored
sessions and no copied user plugins. It establishes the following boundary:

- the installer's automatic post-install launch remained usable;
- the installer-created Start Menu shortcut failed in 2.387–2.653 seconds on
  repeated attempts, including after replacing the CEF profile with a fresh
  one. The failures are main-process `0x80000003` exceptions in `libcef.dll`
  with the same 24-entry module sequence retained in the first packet;
- complete installed-file hash manifests taken before a failing shortcut
  launch and after it were byte-identical, with SHA-256
  `7355abb33358fe06aa78f5adea87db8f8c5c84550083125bbdc62f3c4c0cdb2b`;
- process sampling found no remaining KaminIDE process after the failure and
  showed all nine processes from a normal run exit within the sampled close
  window. A stale-process requirement is therefore excluded for this host;
- direct execution of the same binary with the installation directory as the
  process working directory ran for 47.459 seconds and exited normally with
  code 0 after the owner closed it;
- a separate Start Menu shortcut with the same target and no arguments, but
  with `WorkingDirectory` set to the installation directory, remained usable
  and closed normally. The original Desktop and Start Menu shortcuts both had
  an empty `WorkingDirectory`.

The source countercheck on `origin/main` matches the observation.
`crates/installer/src/steps.rs::write_shortcuts` sets only `TargetPath` before
calling `Save()` for both links. It does not set `WorkingDirectory`.
`relaunch_app` starts the same executable directly, which gives the installer
launch a different current-directory context from the generated shortcuts.

This confirms a missing-shortcut-working-directory trigger for the reported
machine. The internal CEF assertion remains unsymbolized, so the evidence does
not establish that every Windows host or every empty-current-directory launch
must fail. Maintainer implementation may set `WorkingDirectory` on both links,
remove the application's current-directory dependency, or do both. It must
also repair already-created links during upgrade rather than fixing only new
installations.

The exact-candidate gate must cover installer autolaunch, at least three
successive Start Menu launches and at least three successive Desktop launches,
each with a normal close and no native exception. It must then restore the
owner's existing layout, sessions and plugin configuration and verify project
grouping, conversation bindings, Chat history and Console operation. This task
was originally to stay open until that manual verification completed. The
owner's later CI-only acceptance and its explicit limitation are recorded in
the resolution section.

## Fix implementation

PR [#117](https://github.com/dykamino-coder/gpui-kamin-ide/pull/117) changes
the installer shortcut generator to set both `TargetPath` and
`WorkingDirectory` for Desktop and Start Menu links. Installation already
recreates both links on every upgrade, so the same path repairs existing 1.0.55
shortcuts. The generator also escapes single quotes in installation paths.

Regression coverage checks the generated command on every platform. On Windows
it additionally creates a real temporary `.lnk` through `WScript.Shell`, reads
the stored target and working-directory properties back, and removes the test
directory. The fix and coordinated release are merged and verified in
`origin/main`; the CI-only runtime acceptance limitation is recorded in the
resolution section above.
