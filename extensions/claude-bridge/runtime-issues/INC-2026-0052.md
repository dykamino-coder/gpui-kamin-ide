## Symptom and evidence boundary

After moving to another Windows 11 computer, KaminIDE 1.0.55 opens, displays
its restored chat/project list and disappears after a few seconds. The owner
reports that no warning appears and the application is absent from Task
Manager. Failures began before copying the old plugin directory and user
settings file. Some session/layout state had already been transferred; the
complete migration sequence and whether the CEF cache was copied are unknown.

The supplied September 18 packet includes four crash-log generations, four
host incident-log generations, host output, a diagnostic log and layout state.
Private evidence retains every supplied log generation and a minimal derived
layout summary; raw layout identifiers/paths remain in the local private inbox.
This is bounded intake, not an implemented fix or Windows reproduction.

## Confirmed facts

- All four crash logs identify application version 1.0.55 and process role
  `main`, with an exception in `libcef.dll` 2.462–2.662 seconds after the
  corresponding main-start record. They record exception code `0x80000003`,
  Microsoft's [STATUS_BREAKPOINT](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55).
  This classifies the exception, not the underlying fatal assertion or cause.
- Each log contains the same module sequence across 24 reported stack entries,
  including 17 `libcef.dll` entries. Raw addresses are retained privately;
  no DLL load-base verification, symbolization or exact CHECK attribution has
  been performed. Do not treat a different absolute address as a different bug.
- The four host incident files each contain only `host-log-start`; none records
  an extension-host exit. Current host output reaches successful activation of
  the bundled Bridge extension and six webview-provider resolutions. This does
  not establish successful page rendering, server connection or session resume.
- `diag.log` contains seven boot markers and 779 lines, including software-paint
  telemetry from some runs. Its metrics have no wall-clock timestamps/PIDs,
  so those samples cannot be assigned reliably to the four timed crashes.
  The last two boot sections each have one metric row with zero CEF frames.
  There is no renderer-death counter in the supplied diagnostic log.
- The layout JSON parses and restores Chat and Console panel selections. It
  does not establish which sessions were active or prove a layout defect.

Source countercheck baseline: `db4708663269d461bdf46112e5cedb8e47d34210`.
`crates/shell/src/main.rs` installs the native exception handler with role
`main`; `crates/crash/src/lib.rs` records that process's exception. This is
not the renderer-termination callback in `crates/shell/src/web/browsers.rs`.
`crates/shell/src/web/process.rs` initializes the native CEF runtime and its
persistent cache, configures the subprocess helper and selects software mode
for an RDP startup. These are investigation entry points, not proven causes.
Relevant exception/startup source is unchanged from release-source commit
`d9321a173bcf61ea7493a5d10eb82c1244ed1dee`; the installed artifact hashes and
CEF version are still unverified.

## Relation to existing tasks and hypotheses

INC-2026-0020 concerns renderer termination after sleep/RDP return, with a
surviving shell; this case records a main-process exception shortly after
startup. A shared numeric exception code does not establish a duplicate.
INC-2026-0048 concerns session startup blocked during marketplace updates;
there is no corresponding marketplace error or proven causal link here.

An internal CEF fatal condition, profile/cache state, subprocess/runtime
compatibility, rendering environment, or restoration-triggered browser
lifecycle are candidate investigation branches only. Plugin-ID collisions,
GPU/driver failure, memory exhaustion and malformed sessions are not confirmed.
The owner timeline argues against the later plugin/settings copy as the
initial trigger; it does not exclude earlier local state or installed plugins.

## Owner follow-up — fresh local state also exits during startup

**Supplement author:** @dvpetrochenko. **Supplement PR:** pending.
**Evidence:** sanitized owner report in the ongoing September 18 intake;
no new files supplied for this attempt. The immutable packet above describes
the earlier four exceptions and must not be relabeled as this attempt's log.

The owner reports temporarily renaming all three recommended locations:
the native application data/cache root, the user `.claude` directory and the
user `.claude.json` file. The latter two had previously been copied from the
old computer in their entirety. The next launch displayed the default layout
and an empty chat list, then disappeared again within a few seconds. No token
entry or new-session action is described before this exit.

This observation weakens a restored-chat/custom-layout or copied-plugin-data
requirement for the visible symptom: it also occurs after those locations are
set aside. It does not prove that the new failure is the same `0x80000003`
libcef exception, nor establish Windows 11, GPU/driver, CEF profile or runtime
packaging as its cause. Renaming these directories is not a fresh OS account
or a clean installation; legacy migration sources, process environment,
installed binaries and RDP/local state were not independently checked.

Prioritize the freshly generated native crash/diag logs and existing CEF fatal
output from this attempt. Keep them as a separate capture and compare process
role, exception/module and stack signature with the retained four launches.
Do not require a new Bridge token or restore old user data merely to reproduce
an exit that already occurs before the owner can perform those actions.
Continue the native startup/runtime-environment branch of research if the
signature matches; investigate separately if it differs. Keep the task open
and preserve the renamed backup directories until diagnosis is complete.
