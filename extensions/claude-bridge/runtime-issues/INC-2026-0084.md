# INC-2026-0084 — Browser-depth paint test overflows the 8 MiB stack in the unoptimized agent profile

- **Status:** reported
- **Registration author:** @dykamino-coder, owner-directed registration by Claude Code (2026-10-30).
- **Completion target:** register the reproducible overflow and its bounded next step; no product fix or closure in this registration.
- **Diagnostic PR:** [#557](https://github.com/dykamino-coder/gpui-kamin-ide/pull/557).
- **Fix PR:** none.
- **Next step:** research — measure the per-level stack frame size of the deep paint path (inline, grid, math, table and multicol at depth 1026) at `opt-level = 0` and `opt-level = 2`, and decide between reducing the frames on that path and making the documented depth contract explicit per build profile. Owner: maintainer.
- **Private evidence:** not required. The facts below come from the public sources and a local control run on an exact `origin/main` commit; no user data is involved.
- **Dependencies:** follows [#430](https://github.com/dykamino-coder/gpui-kamin-ide/pull/430) (Gecko-depth documents on an 8 MiB stack). It is independent of the GPU adapter work that uncovered it.
- **Acceptance:** automated. The full `cargo html-test --features wpt-harness` suite completes on the 8 MiB stack, and `cargo test --workspace` still passes in CI. No WPT exact-RGB losses.
- **Acceptance rationale:** the failure is a deterministic stack overflow in a unit test, so a complete test run in both profiles proves the contract. It does not need a Windows runtime gate.
- **Deployment observation owner:** none.

## Symptom

`cargo html-test --features wpt-harness` stops with `STATUS_STACK_OVERFLOW` (exit `0xC00000FD`, `3221225725`) in
`depth_tests::special::inline_grid_math_table_and_multicol_paint_at_browser_depth_on_eight_mib`.
The process dies, so every test after it in the suite is not run. Agents therefore cannot get a complete local HTML suite result.

## Confirmed facts

- Reproduced on exact `origin/main` `636f3f5f` in a clean detached worktree. The test binary's PE stack reserve is 8,388,608 bytes. The source code was not modified.
- The same test overflows on a branch whose production `crates/html/src` is byte-identical to `origin/main`, so it is not caused by that branch.
- The test was added by #430 (`bb944577`). It paints documents nested 1026 levels deep for `inline`, `grid`, `math`, `table` and `multicol` inside `regression::on_eight_mib` (`crates/html/src/depth_tests/special.rs:59`).
- `cargo html-test` is defined in `.cargo/config.toml` as `test -p kamin-html --lib --profile agent`. The `agent` profile builds `kamin-html` with `opt-level = 0` (`Cargo.toml`, `[profile.agent]`).
- CI runs `cargo test --workspace` in the `dev`/`test` profile, where `kamin-html` has `opt-level = 2`. The Windows Rust tests pass there on `main`, so CI does not see this failure.
- In the same agent-profile run, other depth tests pass, for example `depth_tests::limit::beyond_box_limit_paints_the_remainder_and_keeps_the_whole_dom`.

## Hypotheses

- Unoptimized frames on the recursive paint path for these five layout kinds are large enough that 1026 levels exceed 8 MiB. With optimization the frames fit. This is not measured yet.
- Debug (`opt-level = 0`) builds of the product may hit the same limit on documents of that depth. Release builds are not affected as far as is known. This is not verified.

## Expected outcome

- Choose between two outcomes and record the decision:
  1. reduce the frames on the deep paint path, by boxing large locals or moving work out of the recursion, so the test passes at `opt-level = 0`;
  2. state the depth contract per build profile explicitly, so the test matches the profile it runs in.
- Silently skipping the test is not acceptable, and neither is raising the stack size.
- Completion means a full `cargo html-test --features wpt-harness` run on 8 MiB and green CI.

## Missing evidence and blockers

- Per-level frame sizes at `opt-level = 0` and `opt-level = 2` for each of the five kinds. Owner: maintainer.
- Whether a debug product build overflows on the same documents. Owner: maintainer.
