# INC-2026-0107 — The `if` condition of a hook written for a native tool never holds in Bridge sessions

- **Status:** confirmed
- **Registration author:** @dykamino-coder, owner-directed registration by Claude Code (2026-11-11)
- **Completion target:** accepted and published fix: a hook with an `if` condition written for a native tool (`Bash(git *)`, `Edit(*.ts)`) runs in a Bridge session for the same tool calls as in plain Claude Code, once per call.
- **Diagnostic PR:** [#751](https://github.com/dykamino-coder/gpui-kamin-ide/pull/751)
- **Fix PR:** [#828](https://github.com/dykamino-coder/gpui-kamin-ide/pull/828) — bounded command/HTTP candidate; remaining argument conditions below stay open
- **Next step:** review the bounded command/HTTP candidate below and run the exact-candidate Windows gate; prompt/agent argument conditions remain open. Owner: the lead/maintainer for acceptance, then the executor for the remaining mechanism.
- **Private evidence:** not required — the card holds only counts from a test profile.
- **Dependencies:** none. Follow-up of INC-2026-0106 (#747), which fixed the matcher and left `if` unchanged.
- **Acceptance:** automated tests plus a live Windows gate on the exact candidate.
- **Acceptance rationale:** the condition is evaluated inside the real CLI, so only a live session proves that a translated condition holds, and holds once.
- **Deployment observation owner:** none

## Symptom

In a Bridge session a hook whose handler has `"if": "Bash(echo *)"` does not
run for a `Bash` call of `echo …`. The same hook with the condition
`mcp__user-tools__Bash` runs for every `Bash` call.

## Environment and versions

- KaminIDE client built from `main` at PR #743, Windows 11; Bridge server
  image 6.3.170 with the server files of PR #747 and Claude Code 2.1.322 in
  the container.

## Confirmed facts

- Bridge serves the file and shell tools as `mcp__user-tools__<Tool>` and
  denies the native ones (see INC-2026-0106).
- The server copies the `if` field of a hook handler to the CLI settings
  unchanged (`server/src/core/hooks/proxy-rewriter.ts`, `if: h.if`). #747
  translates only the matcher.
- Live check on 2026-11-11, test profile, one turn with two `Bash` calls
  (`echo …` and `pwd`), three `PreToolUse` hooks with the matcher `Bash`:
  - without `if`: 2 runs;
  - `if: "Bash(echo *)"`: 0 runs (plain Claude Code would run it once, for
    the `echo` call);
  - `if: "mcp__user-tools__Bash"`: 2 runs.
- By the Claude Code hooks reference `if` uses permission-rule syntax and is
  compared with the tool name and its arguments.
- The owner's current settings do not use `if`.

## Bounded candidate (owner-approved scope, 2026-11-13)

- Real CLI 2.1.322 offline probes confirm that an MCP argument condition
  never holds, including after translating its tool prefix. A bare MCP name
  does hold. The candidate maps bare native names for all handler types and
  evaluates command/HTTP argument conditions before Bridge dispatch.
- The filter runs before execution/audit and reserves `once` only on the first
  accepted call, including concurrent calls. Original HTTP status/body remain
  intact; async commands keep the command relay.
- Native/Bridge Bash matching agreed in 200 synthetic comparisons, including
  the predecessor counterexample: `Bash(git *)` does **not** accept
  `printf '$(pwd)'`. Active substitution retains the native matcher's
  conservative behavior. File rules agreed in 28 comparisons against native
  Read calls. These are sampled parity checks, not proof for every shell AST.
- A real CLI MCP session using the production rewriter/dispatcher delivered
  three unconditional calls, three bare-name calls, one `echo *` command call
  and one original HTTP call; the `git *` hook never ran. The fixture used a
  local synthetic model endpoint, no external service or owner credentials.
- A further 80 comparisons against CLI 2.1.322 found continuation handling
  differences. The candidate now follows the native matcher's fallback for
  backslash-newline inside a word and omits a standalone continuation without
  adding an empty argument. Twelve regression cases cover these distinctions;
  eight fail before this correction, and the 80-case matrix now agrees.
- Isolated Windows CLI 2.1.322 PowerShell probes found 36 differences in 240
  comparisons. The candidate corrects sampled comments, invocation operators,
  simple assignments, redirections and standalone line continuations, while
  retaining a newline escaped inside a word. Seven regression cases fail
  before this correction. Thirteen real-CLI cases (26 comparisons) now agree;
  CRLF word handling was checked directly against the PowerShell AST parser.
  The broader matrix still has 22 differences, so PowerShell parity is not
  complete. These probes use a separate test profile and a local synthetic
  model endpoint; they do not constitute the live KaminIDE candidate gate.

### Explicit remainder and acceptance

- Argument conditions on `prompt`, `agent` and `mcp_tool` handlers remain
  unchanged and still do not hold for replaced native tools. Bare-name
  conditions are translated. Completing argument conditions requires a
  CLI-side predicate that can inspect the MCP input and then continue the
  original LLM/MCP hook execution; routing an LLM hook as a command/HTTP hook
  would change its execution and result semantics.
- An isolated CLI 2.1.322 mod probe cannot implement this by renaming the tool
  in `classic.PreToolUse`: the engine rejects a changed `tool` in `next()`.
  The original MCP call still executes. This rules out that approach, not every
  possible CLI extension mechanism.
- Shell environment expansion is another confirmed parity gap, not covered by
  the original 200 comparisons. The native CLI expands variables from its own
  environment. For example, `Bash(echo $HOME)` rejects `echo "$HOME"`, whereas
  the current Bridge matcher accepts it as literal text. Correct matching needs
  the effective CLI environment, including settings overrides, rather than
  assuming the dispatcher's environment is identical. This remains a blocker
  to claiming complete command/HTTP parity.
- PowerShell nested expressions remain a confirmed parity gap. For example,
  native `PowerShell(Get-Process *)` rejects `Write-Output $(Get-Location)`;
  the current Bridge matcher accepts it. Native matching traverses PowerShell
  command ASTs, whereas the current approximation accepts unsupported nested
  expressions. Exact PowerShell matching and Windows file paths still need
  the required real Windows candidate gate. Home-rooted file rules require the
  client's home directory in the predicate context; the current session
  protocol does not provide it. Do not claim those cases accepted from unit
  coverage.
- Keep this incident open after the bounded candidate. The lead/maintainer
  must run native versus Bridge command/HTTP hooks for echo, pwd, quoted
  substitution, compound commands and Edit patterns on the exact candidate;
  confirm filtering, unchanged output/block decisions and once-only behavior.

## Expected outcome

- A hook with an `if` condition for a native tool runs for the Bridge tool
  call that the condition would accept, and only for it.
- A condition that already names the MCP tool, and a hook without `if`,
  behave as now and do not run twice.
