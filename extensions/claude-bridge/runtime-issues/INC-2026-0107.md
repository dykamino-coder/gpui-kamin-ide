## Symptom

In a Bridge session a hook whose handler has `"if": "Bash(echo *)"` does not
run for a `Bash` call of `echo …`. The same hook with the condition
`mcp__user-tools__Bash` runs for every `Bash` call.

## Environment and versions

- KaminIDE client built from `main` at PR #743, Windows 11; Bridge server
  image 6.3.170 with the server files of PR #747 and Claude Code 2.1.322 in
  the container.

## Confirmed facts

- Bridge serves the file and shell tools as `mcp__user-tools__<Tool>` and
  denies the native ones (see INC-2026-0106).
- The server copies the `if` field of a hook handler to the CLI settings
  unchanged (`server/src/core/hooks/proxy-rewriter.ts`, `if: h.if`). #747
  translates only the matcher.
- Live check on 2026-11-11, test profile, one turn with two `Bash` calls
  (`echo …` and `pwd`), three `PreToolUse` hooks with the matcher `Bash`:
  - without `if`: 2 runs;
  - `if: "Bash(echo *)"`: 0 runs (plain Claude Code would run it once, for
    the `echo` call);
  - `if: "mcp__user-tools__Bash"`: 2 runs.
- By the Claude Code hooks reference `if` uses permission-rule syntax and is
  compared with the tool name and its arguments.
- The owner's current settings do not use `if`.

## Bounded candidate (owner-approved scope, 2026-11-13)

- Real CLI 2.1.322 offline probes confirm that an MCP argument condition
  never holds, including after translating its tool prefix. A bare MCP name
  does hold. The candidate maps bare native names for all handler types and
  evaluates command/HTTP argument conditions before Bridge dispatch.
- The bounded #828 filter runs before execution/audit and reserves `once` on
  the first accepted call, including concurrent calls. That reservation differs
  from native settings-hook semantics and is corrected in #869 below.
  Original HTTP status/body remain intact; async commands keep the command relay.
- Native/Bridge Bash matching agreed in 200 synthetic comparisons, including
  the predecessor counterexample: `Bash(git *)` does **not** accept
  `printf '$(pwd)'`. Active substitution retains the native matcher's
  conservative behavior. File rules agreed in 28 comparisons against native
  Read calls. These are sampled parity checks, not proof for every shell AST.
- A real CLI MCP session using the production rewriter/dispatcher delivered
  three unconditional calls, three bare-name calls, one `echo *` command call
  and one original HTTP call; the `git *` hook never ran. The fixture used a
  local synthetic model endpoint, no external service or owner credentials.
- A further 80 comparisons against CLI 2.1.322 found continuation handling
  differences. The candidate now follows the native matcher's fallback for
  backslash-newline inside a word and omits a standalone continuation without
  adding an empty argument. Twelve regression cases cover these distinctions;
  eight fail before this correction, and the 80-case matrix now agrees.
- Isolated Windows CLI 2.1.322 PowerShell probes found 36 differences in 240
  comparisons. The candidate corrects sampled comments, invocation operators,
  simple assignments, redirections and standalone line continuations, while
  retaining a newline escaped inside a word. Seven regression cases fail
  before this correction. Thirteen real-CLI cases (26 comparisons) now agree;
  CRLF word handling was checked directly against the PowerShell AST parser.
  A subsequent correction traverses grouped pipelines and unquoted
  subexpressions, keeps their source text as outer command arguments, and
  distinguishes literal arrays from nested commands. All 240 comparisons
  now agree, along with another 120 comparisons covering nested pipelines,
  quoted parentheses and arrays. Of 35 new regression cases, 28 fail on the
  predecessor. These probes use a separate test profile and a local synthetic
  model endpoint; they do not constitute the live KaminIDE candidate gate or
  establish full PowerShell parity.

### Explicit remainder and acceptance

- Argument conditions on `prompt`, `agent` and `mcp_tool` handlers remain
  unchanged and still do not hold for replaced native tools. Bare-name
  conditions are translated. Completing argument conditions requires a
  CLI-side predicate that can inspect the MCP input and then continue the
  original LLM/MCP hook execution; routing an LLM hook as a command/HTTP hook
  would change its execution and result semantics.
- An isolated CLI 2.1.322 mod probe cannot implement this by renaming the tool
  in `classic.PreToolUse`: the engine rejects a changed `tool` in `next()`.
  The original MCP call still executes. This rules out that approach, not every
  possible CLI extension mechanism.
- A separate isolated Podman probe tests adding `tool_name: "Bash"` to the
  `classic.PreToolUse` continuation while leaving the reserved `tool` intact.
  For `echo fixture` and `pwd`, native runs the conditional hook once; baseline
  MCP and the payload-alias variant both run it zero times. All three run the
  unconditional hook twice, and both MCP variants retain two MCP-only matcher
  executions and the original MCP payload names. The alias therefore preserves
  compatibility but does not affect the native predicate. The fixture uses
  an isolated profile and a loopback synthetic API with container networking
  disabled; it is not the required live Windows candidate gate.
- A subsequent isolated Windows CLI 2.1.322 probe establishes a narrower
  working continuation: `classic.PostToolUse` accepts rewriting `tool_name`
  before `next()`. For each original prompt, agent and mcp_tool handler,
  native and rewritten MCP calls produce one conditional and two unconditional
  executions, versus zero conditional executions without the mod. Separate
  per-handler probes also preserve the original blocking results. This
  supersedes a general claim that no original-handler continuation was found;
  it does not resolve PreToolUse. The rewrite affects every settings hook:
  an MCP-only matcher stops matching and unconditional payloads receive the
  native name. It is not integrated into production because the existing
  MCP matcher/payload contract must also remain intact. These probes use a
  local synthetic model endpoint and isolated profiles, not the Windows gate.
- #869 now transports the CLI's startup home for Bash conditions,
  separately from the client's home used by file rules. Native CLI 2.1.322
  expands simple `$HOME` from its startup home; `settings.env.HOME` changes
  hook-child environments but not that matcher value. Other simple variables
  retain conservative native matching even when defined in settings or the
  inherited environment. Five matcher regression cases and a launch-context
  regression fail before the change. The production HTTP and command relay
  each agree with native in 35 comparisons, including different startup,
  settings and client homes. An additional 88-comparison HTTP matrix agrees
  for braced expansions, tilde and a HOME path suffix. These are sampled
  comparisons against a local synthetic API, not the live Windows gate.
- #869 also traverses command children of expandable PowerShell strings
  and scriptblock arguments, retaining the outer argument's source text.
  Both regression cases fail before the correction. All 24 comparisons for
  `Write-Output "prefix$(Get-Location)"` and
  `Write-Output { Get-Location }` now agree with the isolated Windows CLI
  2.1.322. This resolves those confirmed counterexamples; the approximation
  does not establish equivalence for every PowerShell AST construct. Exact
  PowerShell matching and Windows file paths still need the required Windows
  candidate gate. Home-rooted file rules require the client's home directory
  in the predicate context; #869 adds it as described below.
- #869 adds client home to the create/resume host declaration and uses
  the live session value for command/HTTP path conditions. Six new regression
  cases fail before the change and pass after it. An isolated Linux CLI
  comparison agrees for three sequential Read calls (three unconditional and
  two home-filtered executions on each side), with different CLI and client
  homes in Bridge. This is not the required Windows candidate gate or full
  native parity. The native fixture's `once: true` hook ran twice for two
  accepted calls, including a sequential retry. This agrees with the
  [documented scope of once](https://code.claude.com/docs/en/hooks#common-fields):
  it is honored only for skill hooks, not settings hooks. The successful home
  comparison excludes `once` and does not establish skill-hook parity.
- #869 also removes the server-side `once` reservation for declarations
  emitted through CLI settings. The CLI ignores `once` there; only skill
  frontmatter honors it. Seven new regression cases fail before this correction
  and pass after it, covering repeated and concurrent command calls and original
  HTTP responses with statuses 200, 403 and 500. An isolated CLI 2.1.322
  native/Bridge comparison makes three sequential Read calls, two accepted by
  a home rule. Before the correction Bridge executes each conditional command
  and HTTP hook once while native executes each twice; after it both sides
  execute each twice. This is a production rewriter/dispatcher probe against a
  local synthetic API, not the live Windows candidate gate. Skill-frontmatter
  hooks are not processed by this settings rewriter and remain outside this
  correction.
- Further Windows CLI 2.1.322 probes identify literal-token and command-name
  differences. #869 treats text after `--%` as literal until newline,
  skips block comments, preserves executable paths and removes module
  qualifiers for matching. Six of eleven regression cases fail on the prior
  code; the focused native comparison agrees in all 182 cases. Nested block
  comments deliberately follow the sampled CLI matcher, whose first-terminator
  behavior differs from the PowerShell AST parser.
- A subsequent correction resolves `$ht = @{key=(Get-Location)}` accepting
  unrelated rules: the matcher traverses hashtable values without treating
  literal keys as commands, including nested tables, arrays, scriptblocks and
  expandable strings. A table used as an argument retains its source text for
  the outer command's condition. Recognized empty ASTs reject command-specific
  conditions, while the universal `*` rule still accepts them, matching native.
  Of 43 regression cases, 23 fail on the predecessor. All 250 isolated Windows
  CLI 2.1.322 comparisons agree after the correction, as do the preceding
  192-case PowerShell matrix. These are sampled corrections, not proof of
  full PowerShell AST parity or the live Windows candidate gate.
- Keep this incident open after the bounded candidate. The lead/maintainer
  must run native versus Bridge command/HTTP hooks for echo, pwd, quoted
  substitution, compound commands and Edit patterns on the exact candidate;
  confirm filtering, unchanged output/block decisions and repeated execution
  of settings hooks (including `once: true`, which settings hooks ignore).
- A further sampled correction consumes simple PowerShell assignment syntax
  before parsing its right-hand command, independently of whitespace around
  `=`. It fixes missed commands in `$x=Write-Output fixture` and false matches
  for unrelated rules in `$x =(Get-Location)`, including invocation operators
  and subsequent statements. Twelve of nineteen new regression cases fail on
  the predecessor. All 114 targeted isolated Windows CLI 2.1.322 comparisons
  agree after the correction. Six additional neighboring comparisons exposed
  one counterexample: unquoted `Write-Output $x=fixture` incorrectly matched
  the same literal rule in Bridge, whereas native splits its variable and
  literal AST elements.
- The variable/literal argument correction resolves that counterexample,
  including a scoped variable and a literal containing another `=`. Quoted
  arguments, braced variables and literal prefixes keep one argument. Thirteen
  of 80 new regression cases fail on predecessor `d306ecc32`; all 80 pass after
  the correction, and the focused Windows suite passes all 258 tests. All 80
  new isolated CLI 2.1.322 comparisons and all 120 rerun assignment/neighboring
  comparisons agree. These remain sampled synthetic local-API checks, not
  complete PowerShell AST equivalence or the live Windows candidate gate.

- A further isolated Windows CLI 2.1.322 matrix exposes 12 differences in
  50 comparisons for scoped/braced variables and compound assignments.
  #869 consumes those assignment prefixes before extracting the
  right-hand command, including chained assignments and grouped pipelines.
  All 50 targeted and 128 neighboring comparisons agree after the correction.
  These local synthetic checks extend the sampled PowerShell coverage; they
  do not resolve original-handler continuation or satisfy the Windows gate.

- Further isolated Windows CLI 2.1.322 PostToolUse probes partition declarations:
  native argument conditions retain a native matcher, while unconditional and
  MCP-only hooks retain their MCP matcher. Calling `next` with the native name,
  then with the original MCP payload, preserves each original prompt, agent and
  mcp_tool blocking result in the controlled fixtures. Each conditional handler
  runs once for two calls (one accepted, one rejected); unconditional and MCP-only
  HTTP hooks each run twice with the original MCP name and arguments. These are
  local synthetic probes, not a production implementation or the Windows gate.
  A second downstream mod receives four PostToolUse events for those two tool

  Arbitrary combined results and conditional-handler payload restoration are
  not established by these fixtures.
- Skipping downstream mods with `next.to(e, 'core')` is not available to the

## Original-handler follow-up candidate (2026-11-14)

The follow-up keeps original prompt, agent and mcp_tool handlers in the CLI.
Bridge evaluates their native argument predicate against the original tool
payload and publishes the per-call decisions through its generated local
settings. A per-process flag identifies the owning session; only the merged
settings read folds that session's marker. Accepted original declarations lose
only `if`; rejected declarations are omitted for that call. Source-specific
reads, command/HTTP declarations, MCP-only conditions and unconditional
handlers retain their existing behavior.

The CLI module waits for the engine's watched-settings reload, then calls the
original continuation exactly once with the unchanged MCP envelope. It returns
the original result and restores the declarations before releasing the serial
gate. Marker-only reloads do not manufacture ConfigChange hooks; real user
edits still propagate. Concurrent tool events wait in the server's UDS request.
Disconnect, turn completion, replacement CLI instance and disposal release
stale work. Tools called by the native hook agent bypass this parent gate,
since that agent has its own hook lifecycle; this avoids a nested-tool deadlock.
Each overlapping tool.call retains its own identity record until completion,
including when separate hook agents reuse the same tool-use ID. One completed
call cannot remove another live agent's bypass identity.

The same follow-up supplies client home as the predicate cwd when no tab folder
is selected, including Read/Edit/Write/NotebookEdit with POSIX or Windows paths
and spaces. Bash startup-home context remains separate.

New automated tests reproduce missing behavior on #869: 16 fail and three pass
before the change. Candidate tests cover original handler fields and results,
MCP-only/unconditional compatibility, one downstream event, watched-settings
source identity, real versus marker-only configuration changes, queue cleanup,
abort and the next turn. Offline real-CLI probes use synthetic local model and
MCP endpoints, isolated profiles and no paid services. Their exact results are
recorded with the follow-up; they do not replace Windows KaminIDE acceptance.

## Expected outcome

- A hook with an `if` condition for a native tool runs for the Bridge tool
  call that the condition would accept, and only for it.
- A condition that already names the MCP tool, and a hook without `if`,
  behave as now and do not run twice.
