## Symptom

In a Bridge session with `prompt`, `agent` or `mcp_tool` hooks that carry a
native `if` condition, the conditions can stop applying after an `mcp_tool`
hook has fired. From then on the tool calls run and are not blocked by those
hooks, and the chat may show "hook skipped: threw Error: Bridge hook conditions
unavailable". Command and HTTP hooks are not affected. A new session applies
the conditions again. Shipped in KaminIDE 1.0.100 / server 6.3.177 and listed
in its known issues.

## Confirmed facts

- Release candidate 1.0.100 on Windows, isolated profile, server built from
  the same main. Five steps behaved as expected. In the sixth, an `mcp_tool`
  handler that calls a Bridge tool ran once and two "hook skipped" messages
  appeared, for PreToolUse and PostToolUse.
- After that, in the same session, an agent condition no longer blocked its
  call and the `mcp_tool` handler no longer ran (two repeats). A call without
  a conditional handler still ran with one command hook per event.
- The session's CLI process did not restart: it was the original process and
  still had the condition gate enabled in its environment.
- Source: `CliModTransport` drops the module's lease when no request arrives
  for more than 3 s (`expire()` clears the instance). The module sends
  `/hello` only on `session.start`, so every later `/hooks/prepare` is
  answered with 409. The module then throws, the engine skips the hook, and
  the CLI evaluates the native condition itself, which never holds for a
  Bridge tool.
- The same six steps passed in the gate of #917 on the same server build, so
  the fault is intermittent.

## Cause, reproduced 2026-11-14

- Pausing the test session's CLI process for 5 s on the acceptance stand
  reproduces the symptom every time: the server logs the lease expiry 3.4 s
  after the last request, the next `/hooks/prepare` is refused, the chat shows
  the same two "hook skipped" messages, and an agent condition no longer
  blocks.
- An `mcp_tool` handler is not the trigger. A request log of the module on an
  instrumented stand copy of the server (nine runs of the `mcp_tool` step, one
  with a handler that sleeps 5 s) shows no `tool.call` and no hook event for
  the handler's own tool call: it never enters the condition gate, and the
  module keeps polling while a handler runs. Six repeats of the failing pair
  of steps and the original order of six steps passed.
- What stalled the CLI for more than 3 s in the release gate is not known;
  that run was not instrumented, so its pause length was not recorded. The
  machine was running builds at the time.
- The 3 s lease window is unchanged. With the fix a stall only costs the
  calls made while it lasts.

## Fix

The module asks for its lease again (`/hello`) when a condition request is
refused, and repeats the request once. A call is left unguarded only if no
lease can be obtained. The server needs no change: it already accepts a new
`/hello` from the same module instance.

## Expected outcome

- After a lease loss the next condition request restores the lease and the
  condition applies again; calls are only left unguarded while no lease can
  be obtained.
- Tests for the lease contract in the module and in the transport, and the
  live gate named above, extended with forced CLI pauses of 5 s and 30 s.

## Missing evidence and blockers

None for the fix. The source of the original stall stays unknown.
