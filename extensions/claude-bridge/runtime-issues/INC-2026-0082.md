### Delivered behavior and limits

`McpTaskStore.create()` checks working tasks against execution limits first.
If retained count, per-owner history or bytes need space, it evicts the oldest
settled outcomes before admitting new work. This replaces the old refusal on
terminal-heavy history; it is more than an increase of the old 256-record cap.
Count/byte eviction does not evict working tasks. Existing TTL expiry remains
a separate lifecycle rule.

| Resource | Published .159 / .160 policy |
| --- | --- |
| Working tasks | 400 globally; 8 per MCP owner |
| Retained records, including working | 2048 globally; 256 per MCP owner |
| Stored record bytes | 128 MiB globally; 512 KiB per result; 64 KiB per input |
| Serialized store operation queue | 1024 operations; not an execution scheduler |
| Retention TTL | 24 hours from creation, subject to earlier settled-outcome eviction |

Owner means the durable endpoint identity described below, not necessarily a
person, PTY or session. The 400-task setting is sized for a stated roughly
50-session envelope; it is not evidence of measured production throughput.
Upgrading the Bridge server is required for this fix; a client-only upgrade
does not change server admission. A .158 store is within the new storage
bounds, so its old 256 records do not require manual deletion after upgrade.

## Symptom and scope

On KaminIDE 1.0.81 / Bridge 6.3.158, ordinary Bash/PowerShell calls report
`Task admission unavailable or capacity exceeded`. The server-side agent
reports 256 retained records, of which 250 are terminal and only six working,
across multiple owners. These production counts were not independently read
by the registration author. The same state is reproduced against published
source with synthetic tasks and no executed commands.

This is a new failure of durable command admission, not proof of the cause of
older Chat freezes, token expiry, transcript replay or CEF crashes.

## Historical confirmed source contract — .158

Published source `132623e456e9d6c2bcf8c59cb9e38e8cc4677a18` includes #501.
`McpTaskStore.create()` counts all stored states toward `retained=256` and
`perOwner=64`; separate working limits are 16 globally and four per owner.
An owner is the durable MCP endpoint identity derived from token/settings
context, not necessarily one live PTY or one human.

Settlement persists completed/failed/cancelled records without releasing their
retained-count admission slots. Expiry uses creation time plus 24 hours and
runs before store operations. A 256-record terminal-heavy store therefore
refuses a fresh owner even though the working limit is not reached. This is a
rolling retention window, not a calendar-day quota.

The HTTP handler maps every Task creation failure to the same 503/error text;
that text alone does not distinguish capacity, persistence or queue failure.
The reproduced count failure and other failure classes need separate tests.

A restarted store reloads the JSON files. **Restart with the same profile
volume does not clear the capacity failure.** Removing files behind a live
store is not a supported recovery: its memory state remains and later expiry
can fail. Do not delete user task data or restart production as acceptance.

At reviewed main `4b3396127`, #518 changes foreground response timing and #527
also admits explicit background commands through Tasks. Neither changes the
retained/owner count policy. In exact .158, `run_in_background:true` bypasses
this branch and uses legacy BashOutput/KillShell; that workaround does not
apply to the newer Tasks-capable background path and does not recover an
already-admitted operation.

## Original requested outcome and implementation decision — historical

Execution capacity and result retention are independent resources:

1. Terminal work releases its execution slot immediately; old successful
   commands must not constitute a daily allowance for new commands.
2. Keep active/admission concurrency and bounded waiting limits per endpoint
   and globally, with cross-owner fairness and explicit overload outcomes.
   Configure values from a documented load envelope; do not merely raise 256.
3. Retain retrievable outcomes separately with a bounded byte/storage policy
   and documented protocol TTL. Do not discard a result just because execution
   ended or an HTTP response was sent: the peer may have disconnected.
4. Persist execution identity and terminal outcomes across restart without
   automatically repeating an admitted side effect. Do not invent a result
   consumption ACK that the supported Claude CLI does not send.
5. Define expiry/cleanup, already-full-store migration and storage-pressure
   behavior before modifying admission. A finite storage limit may still
   require refusal; old terminal record count alone must not disable commands.

The maintainer chooses the bounded implementation. This card does not accept
an eviction protocol or a result-loss tradeoff in advance. The applicable
[Tasks extension contract](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html)
uses `tasks/get` and `ttlMs`; check it against the pinned supported CLI.

## Reproduction and acceptance

Available actual-source probe creates 250 completed tasks across 20 synthetic
owners and six working tasks. A new owner is refused; advancing the test clock
one minute and reopening the store both remain refused. Advancing past the
creation TTL frees entries. The temporary directory is removed after the test.
No Anthropic account, real shell execution or production profile is needed.

The original requested acceptance matrix (coverage and residual owners reconciled above):

- more than 256 sequential completed short calls across 20 owners, and more
  than 64 sequential calls by one owner, without hitting an execution limit;
- real active limits, bounded waiting and one owner's burst alongside another
  owner's short commands; no starvation or unbounded queues;
- foreground/background and modern/legacy routes, including current #527;
- result retrieval after transport loss, duplicate result/ACK, denial, cancel,
  PTY replacement and restart, with exactly one side-effecting execution;
- restart/migration over a full terminal-heavy store and TTL boundaries;
- storage-byte pressure, persistence failure and queue saturation as distinct,
  correlated outcomes; cleanup failure must not silently disable all owners.

Publish fixture sizes, concurrent owners, limits, timings and queue/storage
bounds. Do not advertise a production throughput estimate from a single-user
Docker test. The deployment owner later observes ordinary commands after the
previous retained threshold would have been exceeded.
