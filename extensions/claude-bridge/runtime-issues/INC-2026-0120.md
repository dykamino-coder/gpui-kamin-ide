## Symptom

The chat stays open while the Bridge server restarts. A message sent before the
tab has reconnected appears in the chat as "Queued" and is never answered.
"Send now" and Cancel do not deliver it, the CLI input box stays empty, and the
item disappears only when the local queue TTL expires. A message sent after the
tab reports `connected` is delivered normally.

## Confirmed facts

Runs on the published image 6.3.178 with KaminIDE 1.0.101 on an isolated
profile copy. One uniquely marked request was sent through the same path as the
Send button, after `podman restart` of the acceptance container:

| tab | send moment | outcome |
|---|---|---|
| existing | server down, tab `connecting` | dropped: "Queued", no answer, CLI input box empty |
| existing | after `connected` | delivered and answered |
| new | server down, tab `connecting` | dropped: same as the existing tab |
| new | server up, tab still `connecting` | delivered and answered |

The outcome depends on the socket state at send time, not on tab age. Without
a send, the tab reconnects and reaches prompt readiness normally (about 8 s
after the restart in these runs).

Source trace (main `19ea052a`):

- `extension/src/main/ws/connection-manager.ts`, `send()`: writes the frame
  only when `ws.readyState === WebSocket.OPEN`. Otherwise it returns without a
  signal to the caller. Frames other than `session:resume` are likewise
  dropped while `identityHold` is set. `submitText()` uses this path.
- `webview/src/lib/send-message.ts`: adds the message to the local visual queue
  whenever the tab is not prompt-ready, on the assumption that the message
  reaches the CLI either way.
- `webview/src/components/widgets/QueueWidget.tsx`: "Send now" only interrupts
  the current turn and deliberately does not re-send, so a dropped item can never
  be pushed through.

## Bounded proposed change

Do not discard `session:submitText` while the socket is closed or the identity
is held. Either keep a bounded FIFO of semantic submissions per tab and send it
after the resumed session is confirmed, or reject the submission explicitly so
that the webview restores the text to the composer instead of queueing it.
Preserve existing order, cancellation (Cancel removes the held item), tab close
and session-switch teardown. Raw PTY input is not buffered. A replay must not
duplicate a message the server already accepted.

## Acceptance

Automated: a ConnectionManager test that sends `submitText` while the socket is
CONNECTING/CLOSED and during identity hold, then completes the reconnect. It
must show exactly one delivered submission, or an explicit rejection that the
webview surfaces. The test must fail on the current code.

Windows gate on the exact candidate: keep the chat open across a server restart
of the permitted acceptance container. Send one uniquely marked multiline request
while the server is still down, then verify that it is delivered whole and
answered once, or returned visibly to the composer. Repeat with an existing tab
and a new tab. Do not inspect or alter the container's authentication volume or
CLI authentication directory.
