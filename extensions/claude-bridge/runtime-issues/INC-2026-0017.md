# INC-2026-0017 — Native loading animations bypass reduced-motion mode

- **Status:** confirmed (source-level policy gap; not fixed)
- **Priority:** P2
- **Diagnostic PR:** this incident's enclosing Diagnostic PR (indexed in the research report)
- **Fix PR:** none
- **Private evidence:** [INC-2026-0017](https://github.com/dykamino-coder/gpui-kamin-ide-priv-evidence/tree/1b8e9b43bd076efd16bdce6fb882ef39af0e2fdd/incidents/INC-2026-0017)
- **Dependencies:** none; coordinate cover lifecycle with INC-2026-0005
- **Acceptance:** automated animation/scheduler checks + Windows native runtime gate
- **Corporate observation owner:** none

## Symptom

Native loading panels continue decorative glow, logo float and sweep animations
when the existing native reduced-motion mode is enabled. These elements request
GPUI frames directly, so CEF-only animation suppression does not cover them.
Ordinary slow extension loading or session switching reaches this behavior; an
indefinitely stalled loader is not required.

## Confirmed facts

Source revision: `a34ab4892058bcacc00de8d97ae951fb60551780`.
Short `state/`, `ui/` and `web/` paths below are relative to `crates/shell/src/`.

- `crates/shell/src/win_integration.rs:154–178` defines an explicit
  `KAMIN_REDUCE_MOTION=1` override and RDP detection for continuous decorative
  native animations.
- Session status dots (`ui/sessions/status_dot.rs:54`), switching chips
  (`ui/tabs/chip_leading.rs:59`) and terminal caret (`state/term_grid.rs:131`)
  consult this mode.
- `ui/chat_switch_skeleton.rs:100–106,121–127,146–152` always installs three
  repeating animations. Native spinner builders in `ui/icon.rs:96–102,162–165`
  also repeat unconditionally. Their loader callers do not apply a mode guard.
- `vendor/gpui/src/elements/animation.rs:175–176` requests the next frame while
  an animation is active. `vendor/gpui/src/window.rs:1687–1689` schedules a
  notification independently of the CEF pump's repaint interval.
- CEF's reduced-motion CSS is injected into HTML pages by `web/gpu_mode.rs` and
  `web/scheme.rs`; it cannot change these Rust elements. Source inspection
  therefore proves that this override does not change their scheduling path.

No native frame-rate or CPU measurement was performed. This incident establishes
a bounded policy inconsistency, not the root cause of INC-2026-0001's field CPU
samples. A meaningful loading caption/progress indicator remains necessary;
reduced motion does not prohibit genuine progress updates.

## Hypotheses

Removing decorative repeat work should change frame scheduling during otherwise
stationary loading, but the CPU benefit requires supported Windows measurement.
`software_render()` and `reduce_motion()` are different policies: this report does
not assume every WARP system automatically enables native reduced motion.

## Expected outcome

Honor native reduced motion for decorative brand effects and explicitly define
its behavior for activity spinners. Preserve visible loading/progress/error/retry
information and normal-mode appearance.

Automated checks must verify that the explicit mode does not install repeating
decorative animation. Also verify retry and deadline progression without animated
frames: contributed_webview currently evaluates retry timing during rendering,
so merely removing animations could strand loading again. Use a bounded scheduler
where needed, without polling at display frequency.

Windows acceptance compares stationary loading under override 1/RDP and ordinary
mode, records animation requests/frames and CPU, and verifies real progress,
resolve retries, error/retry, session switching and keyboard/focus behavior. No
performance improvement may be claimed from source checks alone.
