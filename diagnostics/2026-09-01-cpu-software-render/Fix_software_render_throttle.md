# Правка «software render throttle» — контекст, решения, где смотреть в логах

PR: https://github.com/dykamino-coder/gpui-kamin-ide/pull/19
Ветка: `perf/software-render-throttle` → `main`, коммит `db02b8d`, 5 файлов, +152/−2.
Расследование велось по логам этой папки (сборка KaminIDE 1.0.53, машина `WSY92293`).

---

## 1. Симптом и что он на самом деле означал

Жалоба: «десктоп-приложение выедает весь CPU». Первоначально считалось, что жор идёт
**на простое**. По ходу разбора выяснилось, что это не так, и это важно для оценки
приоритета.

Замер (`cpu.txt`, 20 с, машина на 8 логических ядер):

| PID | процесс | тип | CPU% | CPU-сек / 20 с |
|---|---|---|---|---|
| 38392 | kaminide-gpui | **main** | **85,5** | **136,84** |
| 14852 | kaminide-gpui | gpu-process | 10,3 | 16,55 |
| 21232 | kaminide-gpui | renderer | 0,5 | 0,88 |
| 25784 | kaminide-gpui | renderer | 0,5 | 0,73 |
| 10148 | kaminhost | main | 0,1 | 0,14 |

136,84 CPU-сек за 20 секунд = **6,8 ядра из 8**. Ест наш Rust-шелл. Chromium-renderer'ы
и Node практически не работают — значит ни webview-код, ни extension host, ни Bridge
server к жору отношения не имеют.

Спусковой крючок нашёлся зондом (`anim.txt`): единственная работающая анимация во всём
приложении — **CSS-спиннер 19×19 в шапке чата** (`_spinner_1yjoq_35`, keyframes
`_spin_1yjoq_35`, то есть `ActivityIndicator` с `animation: spin 0.8s linear infinite`).

Прямое сравнение двух состояний на одной машине:

| состояние | анимаций в чате | кадров CEF/с | кадров окна/с | CPU main |
|---|---|---|---|---|
| спиннер крутится | 1 | 120–139 | 22–27 | **6,8 ядра** |
| спиннер снят | 0 | 0 | 0 | **0,28 ядра** |

Ключевое уточнение: спиннер показывается по условию `visible={!!(activity?.isWorking)}`
(`ActivityStrip.tsx`), то есть **ровно пока Claude работает**. Это основной рабочий режим
приложения, а не редкая ситуация. Формулировка «жор на простое» была неточной: приложение
съедает почти всю машину всё время активной работы в чате.

## 2. Почему встроенная диагностика не показывала виновника

Это была главная загадка разбора. Строка `[cef] за секунду` в момент жора объясняла
только ~0,8 ядра из 6,8:

| статья | мс/сек | ядер |
|---|---|---|
| сцена gpui (главный поток) | 613 | 0,61 |
| копия sw-кадров (~1,6 мс × 124) | ~198 | 0,20 |
| презент | 1,3–3,5 | ≈0 |
| **итого объяснено** | | **≈0,8** |
| **измерено в cpu.txt** | | **6,8** |

Шесть ядер не видел ни один счётчик. Разгадка в `modules.txt`: в главном процессе
загружен **`d3d10warp.dll`**, а аппаратных драйверов (`nvwgf*`, `igd*`, `amdx*`) нет
вообще. Машина — облачная виртуалка Yandex (`xeon-gold-6354`) в RDP-сессии, из видео
только `Microsoft Remote Display Adapter` (32 Гц) и `Microsoft Basic Display Adapter`
(SeaBIOS VBE) — см. `env.txt`.

То есть gpui рисует через **WARP**, программный растеризатор Direct3D. Он:

* многопоточный — растеризует на всех логических ядрах (в `threads.txt` девять потоков
  в состоянии Running/Ready по ~6 секунд из 10);
* работает **асинхронно после `Present`**. `Present` только ставит команды в очередь и
  возвращается за 1–5 мс — поэтому счётчики gpui показывают «презент 3,5 мс» и честно
  не видят настоящей работы.

Побочная поправка к первой сводке: колонка `StartAddr` в `threads.txt` одинакова
(`0x7FFCD3C7CC70`) у **всех** потоков процесса, включая заведомо разные. Это общий
стартовый thunk ntdll, а не признак пула воркеров — вывод «это пул» из неё не следует.
Сам факт девяти горячих потоков верен.

## 3. Причинная цепочка целиком

```
CSS-спиннер 19×19 в шапке чата (показан, пока Claude работает)
   ↓  Chromium перерисовывает вью ~60 раз/с (dirty всего 2–4%)
on_paint / on_accelerated_paint → repaint_requested()      ← безусловно, без фильтров
   ↓
насос (pump.rs) заказывает cx.notify() на RootView         ← перерисовка ВСЕГО окна
   ↓
gpui собирает сцену (~0,6 ядра) и зовёт Present
   ↓
d3d10warp.dll растеризует 1920×1080 на девяти потоках      ← ~6 ядер, мимо всех счётчиков
```

Один кадр окна обходится примерно в 40 мс процессорного времени. Поэтому насос, спящий
8 мс (то есть готовый заказывать до 125 кадров в секунду), физически выдавал только
22–27 — он упирался в потолок WARP, попутно занимая почти всю машину.

На машине **с** видеокартой та же цепочка стоит копейки. Именно поэтому проблему не
замечали раньше — она специфична для развёртывания на VM/RDP без GPU.

## 4. Что изменено и почему именно так

### Пункт 1. Явное определение программного рендера

Новый файл `crates/shell/src/web/gpu_mode.rs`.

Приложение раньше **не знало**, что рисует в софте. Существующий флаг `web::sw_mode()`
для этого не годится: он про общие текстуры CEF и включается эвристикой «вью 12 секунд
не отдаёт кадров».

Режим определяется один раз перечислением адаптеров DXGI. Программным считается адаптер
с вендором Microsoft (`VendorId 0x1414`) либо с именем, начинающимся на
«Microsoft Basic Render».

*Почему не по флагу `DXGI_ADAPTER_FLAG_SOFTWARE`:* вендор и имя однозначны для WARP и не
зависят от того, как объявлен тип флага в конкретной версии крейта `windows`, — а собрать
и проверить правку было нечем (см. раздел 7).

*Почему DXGI, а не устройство окна:* ответ нужен **до первого кадра**, иначе первая же
отдача страницы уйдёт с непогашенными анимациями, а чат больше не перезагружается
(он в списке `NEVER_REAP`). Устройство gpui появляется только на первом кадре.

### Пункт 2. Глушение бесконечных анимаций

`crates/shell/src/web/scheme.rs`, функция `html_reply`.

К каждой отдаваемой странице приклеивается блок:

```html
<style id="__kaminReducedMotion">*,*::before,*::after{animation-iteration-count:1!important}</style>
```

*Почему именно счётчик повторов, а не `animation: none`:* последнее оставило бы навсегда
невидимым всё, что появляется через `opacity: 0` + `forwards`. А так спиннер довернёт
свой круг и замрёт, разовые появления отработают как были.

*Почему шов именно здесь:* через `html_reply` идут **все** наши страницы — и чат, и вью
расширений; рядом тем же способом уже вставляется тема. Перезагрузка вью вставку потерять
не может.

### Пункт 3. Троттлинг заказов перерисовки

`crates/shell/src/web/pump.rs`: пауза насоса 8 мс → **100 мс** при программном рендере.

Это страховка, которая чинит не только спиннер, но и любой другой источник кадров —
стриминг ответа, вывод терминала, — где цена кадра ровно та же. Смысл в том, что при 8 мс
заказы копились быстрее, чем WARP успевал их отрабатывать.

**Размен, который надо понимать:** веб-содержимое при программном рендере обновляется
10 раз в секунду. Стриминг ответа и скролл станут заметно дискретнее. Альтернатива —
6,8 ядра и общая неотзывчивость машины. Ввод и события интерфейса идут своим путём и
не троттлятся.

Дополнительно в `crates/shell/Cargo.toml` явно добавлена фича `Win32_Graphics_Dxgi`
(раньше приезжала транзитивно из gpui). Состав зависимостей не изменился, `Cargo.lock`
не тронут, release-версии не менялись.

## 5. Куда смотреть в логах

### 5.1. В логах ЭТОЙ папки — где лежат доказательства

| факт | файл | что искать |
|---|---|---|
| ест главный процесс, а не Chromium/Node | `cpu.txt` | колонка `Type` = `main`, `CpuSecPer20s` 136,84 |
| рендер программный | `modules.txt` | строка `d3d10warp.dll`; отсутствие `nvwgf*`/`igd*`/`amdx*` |
| нет GPU, сессия RDP | `env.txt` | `SESSIONNAME = RDP-Tcp#1`, `Microsoft Basic Display Adapter` |
| девять горячих потоков | `threads.txt` | `State` = Running/Ready, `CpuSec10s` ≈ 6 |
| виновник — один спиннер | `anim.txt` | `[anim] claudeBridgeChat ... n=1 :: _spinner_1yjoq_35/_spin_1yjoq_35` |
| поток кадров и цена сцены | `cache-diag.log` | строки `[cef] за секунду` и `[sw]` |

Как читать строку `[cef] за секунду` — значимые поля по порядку:

* **`кадров N`** — сколько кадров прислал Chromium за секунду (суммарно по всем вью).
  В окне жора 120–139, медиана по всему логу — 2.
* **`кадров окна N`** — сколько раз перерисовалось наше окно. В окне жора 22–27.
  Это и есть то, что уходит в WARP.
* **`сцена N мс`** — время построения кадра на главном потоке за секунду (613 мс в жоре).
* **`презент N мс`** — 1,3–3,5 мс. Обманчиво маленькое: настоящая работа идёт **после**
  него, в потоках WARP, и в лог не попадает.
* **`переиграно вью N`** — во всех 6739 замерах ноль. Кэш элементов gpui не переигрывает
  ничего, каждый кадр собирается с нуля. Это отдельная проблема, здесь не чинилась.

Строка `[sw] кадров N: копия в среднем X мкс, dirty в среднем Y%` — путь без общих
текстур. `dirty 2–4%` при 120 кадрах в секунду означает: меняется крошечный кусочек
экрана, а перерисовывается всё окно целиком.

Полезные срезы, уже посчитанные по `cache-diag.log` (6739 секунд замеров):

```
секунд с потоком >=100 кадров/с : 1771 из 6739  (26% времени)
в эти секунды                    : кадров окна 21,3 · сцена 486 мс/с · презент 3,5 мс
последние 100 с (окно замера CPU): кадров 123,8 · окна 24,9 · сцена 613 мс/с
медиана по всему логу            : 2 кадра/с
```

Отдельно показателен блок 300–600 секунд: **кадров 56/с, а кадров окна 0**. Вью льют
кадры, когда окно вообще не рисуется — это подтверждает незакрытый `was_hidden` (см.
раздел 7).

### 5.2. В НОВЫХ логах — как убедиться, что правка сработала

Файл тот же: `%LOCALAPPDATA%\kaminide-gpui-dev\cache\diag.log`.

**Шаг 1. Режим определился.** При старте должны появиться строки:

```
[cef] адаптер 0: Microsoft Basic Render Driver — программный
[cef] рендер программный (WARP): кадры окна не чаще 100 мс, бесконечные анимации страниц гасим
```

Если их нет — детект посчитал адаптер аппаратным, и ничего из правки не включилось.
Тогда смотреть, какое имя и вендор у адаптера в `modules.txt`/`env.txt`, и форсировать
режим через `KAMIN_FORCE_SW_RENDER=1` (раздел 6).

**Шаг 2. Спиннер больше не льёт кадры.** Дать Claude поработать так, чтобы индикатор
в шапке чата появился. Ожидаемо:

* спиннер делает один оборот и замирает — это видно глазами;
* в `[cef] за секунду` поля `кадров` и `кадров окна` падают к нулю, а не держат 120/25.

**Шаг 3. CPU.** Снять `cpu.txt` тем же скриптом, что и раньше. Ожидаемо: `main` — доли
ядра вместо 6,8 (ориентир — 0,28 ядра, как было при снятом спиннере).

**Шаг 4. Контроль троттлинга.** Даже если какой-то источник кадров останется, поле
`кадров окна` не должно превышать ~10 в секунду (пауза 100 мс). Если превышает —
троттлинг не включился, то есть провалился шаг 1.

**Чего ожидать не надо.** Поле `переиграно вью` останется нулём — эта правка его не
касается. Строки `[sw]` останутся, если кадры идут: программный путь CEF не менялся.

## 6. Как форсировать и как откатить

Переменная окружения `KAMIN_FORCE_SW_RENDER`:

* `=1` — считать рендер программным принудительно. Нужна, чтобы проверить поведение
  правки на машине **с** видеокартой.
* `=0` — считать аппаратным, то есть **полный откат поведения** без пересборки: пауза
  насоса вернётся к 8 мс, блок глушения анимаций не будет вставляться.

Запуск с переменной (приложение перед этим закрыть полностью — оно single-instance):

```powershell
Get-Process kaminide-gpui -ErrorAction SilentlyContinue | Stop-Process
$env:KAMIN_FORCE_SW_RENDER = "0"
& "$env:LOCALAPPDATA\Programs\KaminIDE-GPUI\kaminide-gpui.exe"
```

## 7. Что НЕ сделано и что не проверено

**Не проверено.** На машине, где готовилась правка, нет ни Rust-тулчейна, ни Node —
`cargo fmt`, `cargo clippy`, `cargo test` **не запускались вообще**. Запущено только
`python scripts/check_event_routing.py` (зелёный, 200/200), `git diff --check` (чисто)
и правило 250 строк (новый файл 136 строк, число превышений не изменилось). Первый же
`cargo check` на машине с тулчейном закроет риск опечаток в вызовах DXGI-API.

PR помечен как **Windows runtime merge gate**: корректность зависит от CEF/webview
lifecycle и рендера, unit-тест этого не воспроизводит. Evidence снимается по разделу 5.2.

**Не сделано (отдельные задачи, найдены тем же разбором):**

1. **`was_hidden(1)` для скрытых вью.** `crates/shell/src/web/browsers.rs` вызывает
   `was_hidden(0)` один раз при создании браузера, и больше никогда. Chromium считает
   вью видимым вечно, не тротлит его таймеры и анимации. Зонд это подтвердил со стороны
   страницы: `claudeBridgeConsoleView` отвечает `vis=visible, hidden=false`, хотя на
   экране его нет (`anim.txt`). Это же закрывает пункт 0.2 мастер-плана (канал
   `kamin:webview:viewState`).
2. **`переиграно вью 0`.** Кэш элементов gpui не переигрывает ни одного вью — каждый кадр
   окна собирается с нуля (раскладка ~300 мс/с, taffy ~230 мс/с). Не первопричина
   текущего жора, но на машине с видеокартой станет главной статьёй расходов.
3. **`windowless_frame_rate`.** Остался 120 (60 под RDP). При работающем троттлинге
   насоса это уже не критично, но лишние кадры Chromium всё равно генерирует.

**Известное ограничение детекта.** Программный адаптер стороннего вендора (не Microsoft
и не с именем «Microsoft Basic Render») детект пропустит. На этот случай есть
`KAMIN_FORCE_SW_RENDER=1`.
