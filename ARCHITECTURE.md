# Как устроен gpui-kamin-ide

Страница для того, кто открыл репозиторий впервые. Дальше — только детали в
`//!`-заголовках самих файлов; каждый файл начинается с описания.

Общий процесс веток, change PR, проверок, версионирования и Windows-релиза
описан в `CONTRIBUTING.md`. Общие правила ИИ-агентов хранятся в `CLAUDE.md`;
`AGENTS.md` направляет к ним Codex и не дублирует их.

## Крейты

| крейт | зачем |
|---|---|
| `shell` | само приложение: окно, интерфейс, состояние, связь с хостом |
| `theme` | палитра и тема (светлая/тёмная), парсинг contributed-тем |
| `metrics` | числовые константы дизайна: отступы, радиусы, кегли |
| `model` | типы сессий, общие с сервером |
| `ws` | JSON-RPC поверх веб-сокета: кадры, эндпоинт |
| `probe` | протокол отладочного канала (сам канал — в `shell/src/probe`) |
| `sidecar` | запуск и присмотр за процессом `kamin-host` |

Всё, кроме `shell`, — маленькое и без зависимостей от интерфейса.

## Три слоя внутри `shell`

```
   host/            ←  что пришло снаружи (веб-сокет, JSON-RPC)
     ↓  ShellEvent
   state/           ←  что мы про это думаем (поля RootView) и как рисуем кадр
     ↓  вызовы функций
   ui/              ←  как это выглядит (чистые функции-компоненты)
```

Правило одно: **`ui/` ничего не знает про `state/`**. Компонент получает
готовые значения и канал событий `tx`, возвращает элемент. Общие мелочи, нужные
обоим (например, проверка имени файла), лежат отдельным листом — `file_names.rs`.

Проверить правило: `grep -rn "crate::state::" crates/shell/src/ui/` — должно
быть пусто.

## Путь события: от клика до пикселя

1. **Клик.** Компонент в `ui/` шлёт `ShellEvent` в канал: `tx.try_send(...)`.
2. **Доставка.** `state/events/dispatch.rs` — один `match`, который по варианту
   события выбирает домен-обработчик и больше ничего не делает.
3. **Изменение.** Обработчик (`state/events/*.rs`) правит поля `RootView` и
   зовёт `cx.notify()`.
4. **Кадр.** `state/frame/*` и `state/columns/*` собирают дерево элементов,
   дёргая компоненты из `ui/`.

События снаружи (от `kamin-host`) входят в тот же канал: `host/ws_events/*`
превращает сообщение веб-сокета в `ShellEvent`.

### Осторожно: молчаливая потеря события

У каждого `apply_*` последняя ветка — `_ => {}`. Если диспетчер отправит
событие модулю, где ветки нет, компилятор промолчит, а кнопка перестанет
работать. Поэтому связку проверяет скрипт:

```bash
python scripts/check_event_routing.py
```

Он падает, если событие маршрутизируется в никуда, обрабатывается в двух
местах или не маршрутизируется вовсе. Запускать после любой правки `dispatch.rs`
или переноса веток между модулями.

## Что где лежит

| папка | содержимое |
|---|---|
| `state/events/` | обработчики событий по доменам + `dispatch.rs` |
| `state/frame/`, `state/columns/` | сборка кадра: колонки, панели, сплиттеры |
| `state/model.rs` | поля `RootView`, сгруппированные в под-структуры |
| `ui/` | компоненты интерфейса; вложенные папки — по областям экрана |
| `overlay/` | отдельное прозрачное окно поверх главного: меню, модалки, тосты |
| `web/` | хостинг offscreen CEF (чат Bridge, браузер, вью расширений), delivery pump и recovery |
| `host/` | клиент `kamin-host`: запросы, разбор входящих событий |
| `probe/` | отладочный канал: снять метрики, кадр, послать клик |
| `term/` | терминал: PTY, профили шеллов, клавиши, цвета |
| `icon_theme/` | иконочные темы расширений (иначе — Catppuccin) |

`crates/html` (`kamin-html`) — отдельная реализация HTML/CSS для examples и
WPT runner; устройство — в следующем разделе. На runtime audit baseline
`d54de40` production `shell` зависит от CEF, а не от этого crate. Поэтому WPT
changes и Bridge runtime acceptance ведутся отдельно; текущая граница и
условия supersession описаны в
[RUNTIME_BACKLOG.md](extensions/claude-bridge/RUNTIME_BACKLOG.md#engine-boundary).

## Движок HTML/CSS: `crates/html`

`kamin-html` рисует статическую разметку (без скриптов) элементами GPUI:
своя раскладка по спецификациям CSS, проверяемая reftest-ами WPT
(`cargo run --example wptrun`). Публичный API — `Document` (разбор один раз,
`update` по новой разметке, `render(&RenderOpts)` каждый кадр); доменные папки
закрыты (`pub(crate)`) и образуют внутренний контракт между фазами.

### Слои

```
   dom/       html5ever → дерево Node/Element; обход с каскадом, починка
     ↓        дерева коробок (анонимные обёртки, таблицы, руби, shadow DOM)
   style/     разбор CSS и @-правил, селекторы, каскад → Computed
     ↓
   layout/    блочный поток, флоаты, таблицы, сетка, многоколоночник,
   text/      фрагментация, страницы, позиционирование; строчный поток,
     ↓        абзац, перенос, руби, вертикальное письмо
   paint/     Computed → стиль элемента GPUI (`paint/apply`), фон, рамки,
   svg/       декорации, эффекты, наложение; `<svg>` через resvg
   ─────
   render/    сборка: обходит узлы, зовёт фазы и возвращает элементы GPUI
```

Зависимости идут по конвейеру вперёд: фаза знает типы предыдущих
(`dom::Node` и `style::computed::Computed` читают все), а не последующих;
обход `dom/walk` вызывает каскад `style`, потому что стиль вешается на узел
при построении дерева. `layout` и `text` — одна ступень, `paint` и `svg` —
следующая: внутри каждой пары допустимы взаимные зависимости. `render` и
`hooks.rs` — адаптеры над фазами; они могут обращаться ко всем фазам.
Фазы не импортируют `render`. Алгоритмы `layout/float`
запрашивают построение детей через контракт `layout::build_contracts::ChildBuild`;
его реализацию предоставляет `render`. Поперечные папки:
`document/` (документ между кадрами, base URL, встроенные документы,
viewport), `interactive/` (прокрутка, липкие коробки, формы, выделение),
`animation/` (переходы, анимации, `offset-path`), `coverage/` (реестр
покрытия свойств; таблица в `docs/html-css-mapping.html` генерируется
`python scripts/css_coverage_table.py`).

Это правило **типов и импортов**, включая реэкспорты, полные пути вызовов,
тесты и отключённые `cfg`-ветви. В частности, `dom` не зависит от
`layout`/`text`/`paint`/`svg`, `style` — от `layout`/`text`/`paint`/`svg`,
а `layout`/`text` — от `paint`/`svg`. Запрос построения чужой фазы описывается
типом потребителя в `layout::build_contracts`, реализацию выбирает render.
Например, multicol передаёт `Layer::gap_rules` буфер и спецификацию из
`layout::multicol::gap_rules`, а painter создаётся адаптером render.
Состояние обхода дерева (`Deferred`, `Depth`) принадлежит `layout::cx`,
а не paint.

Проверка: `python scripts/check_layer_imports.py`. Точный остаток долга —
`scripts/layer_import_allowlist.json`: файл, Rust-путь, число обращений,
владелец и задача удаления у каждой записи. Маски запрещены, удалённая
зависимость делает запись устаревшей и ломает проверку. В CI `--base`
дополнительно запрещает новые записи и рост числа обращений: allowlist может
только уменьшаться. Проверка разбирает явные пути Rust, вложенные `use` и
относительные пути; комментарии и литералы не считаются импортами.

### Модель элемента и правило 1.D (ADR P-19)

Движок строит дерево `gpui::Element`: один элемент участвует и в раскладке,
и в отрисовке, подобно фрейму Gecko. `request_layout` передаёт ограничения
taffy, а `prepaint` получает реальную геометрию. Отдельного неизменяемого
дерева фрагментов, которое затем читает независимый painter, сейчас нет;
такое разделение фаз относится к будущему семантическому paint IR.

Реализация `gpui::Element`/`Hooks` в `layout` или `text` допустима, когда её
`prepaint` содержательно вычисляет геометрию: стопка колонок или страниц,
полосы флоатов, абзац, anchor-позиционирование. Реализация, у которой
содержательна только `paint`, принадлежит `paint` (например, художники таблиц
и отложенной покраски позиционированного содержимого). Само наличие
`AnyElement`, `Div` или `paint`-метода не определяет владельца алгоритма.

Роли и анонимные обёртки таблиц принадлежат `dom/table_boxes`, а измерение и
размещение этих коробок — `layout/table`. Для свёртки постоянных фоновых
цветов `style` получает доступность и цвет изображения через
`BackgroundImageValues`; загрузка и декодирование остаются в `paint`.
Состояние документа и раскладки передаётся явным контекстом или хранится в
`Document`; процессные кэши допустимы только для результатов, не зависящих от
документа (растры, шрифты). Правила vendor-копий — `docs/VENDORING.md`.

## Правила, которых держимся

* **Файл не длиннее 250 строк.** Проверка:
  `find crates -name '*.rs' -exec wc -l {} + | awk '$1>250'`.
* Размещение unit-тестов: [единая конвенция](CLAUDE.md#размещение-unit-тестов-rust)
  (inline; внешние дочерние модули при превышении лимита файла).
* **Ноль предупреждений.** `cargo clippy --workspace --all-targets`.
* **Каждый файл начинается с `//!`** — чем модуль владеет (фаза, вход и
  выход, инвариант), не «вынесено ради лимита строк». Заголовки и
  комментарии — по-русски; имена кода, спецификаций (`css-break-3 §4.1`),
  файлов Blink/Servo и тестов WPT остаются как есть.
* Комментарий объясняет **причину**, а не пересказывает код; в порте это часто
  ссылка на оригинал и замер («ревью ц.14», `SessionItem.module.css:176`).

## Запуск и проверка

```bash
cargo run                     # ровно ОДИН экземпляр: прежний сначала убить
python scripts/check_event_routing.py
cargo test
```

Отладочный канал слушает TCP 9333:

```bash
node scripts/probe.mjs '{"cmd":"metric","id":"status-bar"}'
node scripts/probe.mjs '{"cmd":"screenshot","path":"C:/tmp/frame.png"}'
```
