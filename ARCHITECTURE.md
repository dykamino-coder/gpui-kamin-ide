# Как устроен gpui-kamin-ide

Страница для того, кто открыл репозиторий впервые. Дальше — только детали в
`//!`-заголовках самих файлов; каждый файл начинается с описания.

## Крейты

| крейт | зачем |
|---|---|
| `shell` | само приложение: окно, интерфейс, состояние, связь с хостом |
| `theme` | палитра и тема (светлая/тёмная), парсинг contributed-тем |
| `metrics` | числовые константы дизайна: отступы, радиусы, кегли |
| `model` | типы сессий, общие с сервером |
| `ws` | JSON-RPC поверх веб-сокета: кадры, эндпоинт |
| `probe` | протокол отладочного канала (сам канал — в `shell/src/probe`) |
| `sidecar` | запуск и присмотр за процессом `kamin-host` |

Всё, кроме `shell`, — маленькое и без зависимостей от интерфейса.

## Три слоя внутри `shell`

```
   host/            ←  что пришло снаружи (веб-сокет, JSON-RPC)
     ↓  ShellEvent
   state/           ←  что мы про это думаем (поля RootView) и как рисуем кадр
     ↓  вызовы функций
   ui/              ←  как это выглядит (чистые функции-компоненты)
```

Правило одно: **`ui/` ничего не знает про `state/`**. Компонент получает
готовые значения и канал событий `tx`, возвращает элемент. Общие мелочи, нужные
обоим (например, проверка имени файла), лежат отдельным листом — `file_names.rs`.

Проверить правило: `grep -rn "crate::state::" crates/shell/src/ui/` — должно
быть пусто.

## Путь события: от клика до пикселя

1. **Клик.** Компонент в `ui/` шлёт `ShellEvent` в канал: `tx.try_send(...)`.
2. **Доставка.** `state/events/dispatch.rs` — один `match`, который по варианту
   события выбирает домен-обработчик и больше ничего не делает.
3. **Изменение.** Обработчик (`state/events/*.rs`) правит поля `RootView` и
   зовёт `cx.notify()`.
4. **Кадр.** `state/frame/*` и `state/columns/*` собирают дерево элементов,
   дёргая компоненты из `ui/`.

События снаружи (от `kamin-host`) входят в тот же канал: `host/ws_events/*`
превращает сообщение веб-сокета в `ShellEvent`.

### Осторожно: молчаливая потеря события

У каждого `apply_*` последняя ветка — `_ => {}`. Если диспетчер отправит
событие модулю, где ветки нет, компилятор промолчит, а кнопка перестанет
работать. Поэтому связку проверяет скрипт:

```bash
python scripts/check_event_routing.py
```

Он падает, если событие маршрутизируется в никуда, обрабатывается в двух
местах или не маршрутизируется вовсе. Запускать после любой правки `dispatch.rs`
или переноса веток между модулями.

## Что где лежит

| папка | содержимое |
|---|---|
| `state/events/` | обработчики событий по доменам + `dispatch.rs` |
| `state/frame/`, `state/columns/` | сборка кадра: колонки, панели, сплиттеры |
| `state/model.rs` | поля `RootView`, сгруппированные в под-структуры |
| `ui/` | компоненты интерфейса; вложенные папки — по областям экрана |
| `overlay/` | отдельное прозрачное окно поверх главного: меню, модалки, тосты |
| `wv/`, `wv_visual.rs` | хостинг WebView2 (чат Bridge, браузер, вью расширений) |
| `host/` | клиент `kamin-host`: запросы, разбор входящих событий |
| `probe/` | отладочный канал: снять метрики, кадр, послать клик |
| `term/` | терминал: PTY, профили шеллов, клавиши, цвета |
| `icon_theme/` | иконочные темы расширений (иначе — Catppuccin) |

## Правила, которых держимся

* **Файл не длиннее 250 строк.** Проверка:
  `find crates -name '*.rs' -exec wc -l {} + | awk '$1>250'`.
* **Ноль предупреждений.** `cargo clippy --workspace --all-targets`.
* **Каждый файл начинается с `//!`** — что внутри и почему именно так.
* Комментарий объясняет **причину**, а не пересказывает код; в порте это часто
  ссылка на оригинал и замер («ревью ц.14», `SessionItem.module.css:176`).

## Запуск и проверка

```bash
cargo run                     # ровно ОДИН экземпляр: прежний сначала убить
python scripts/check_event_routing.py
cargo test
```

Отладочный канал слушает TCP 9333:

```bash
node scripts/probe.mjs '{"cmd":"metric","id":"status-bar"}'
node scripts/probe.mjs '{"cmd":"screenshot","path":"C:/tmp/frame.png"}'
```
