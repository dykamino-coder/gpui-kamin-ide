# letter-spacing в vendored gpui (план, ц.31)

Закрывает СЕМЬ элементов парити разом: 11, 15, 18 (`.04em`), 23, 98 (`.08em`),
82 (`.06em`), 111/146 (`.02em`), 77 (`-0.02em`).

## Точка врезки найдена

`vendor/gpui/src/text_system/line_layout.rs:533 layout_line` уже содержит
пост-проход по глифам для `force_width`: он идёт по `layout.runs`, двигает
`glyph.position.x` и правит `layout.width`. Letter-spacing делается ровно там
же и той же механикой — значит хит-тест (`index_for_x`) и отрисовка получат
согласованные координаты автоматически, отдельной правки не потребуют.

## Шаги

1. `TextStyle` (`style.rs`): поле `letter_spacing: Pixels` (по умолчанию 0),
   плюс `Styled::letter_spacing()` в `styled.rs`. Поле НЕ помечать
   `#[refineable]` не нужно — оно внутри `TextStyleRefinement`, который
   сливается нашим патчем `refine_merge_text` (ц.25).
2. Протащить в `shape_line` / `layout_line` и в `CacheKeyRef` — иначе строка с
   другим трекингом возьмётся из кэша с прежними позициями.
3. Пост-проход: `glyph.position.x += spacing * i` по сквозному индексу глифа,
   `layout.width += spacing * n`. Последний глиф в CSS тоже получает трекинг
   (`letter-spacing` добавляется ПОСЛЕ каждого символа, включая последний).
4. Перенос строк: `wrap_line` считает ширины из того же layout — проверить,
   что перенос учитывает увеличенную ширину.
5. Пометить все правки маркером `KaminIDE patch`, обновить счётчики в
   `scripts/vendor_patches.py`.
6. Проверка: probe-замер ширины заголовка секции с `.08em` до и после; на
   строке из N символов ширина обязана вырасти на `N × 0.08 × font_size`.

## Риски

- кэш строк: без ключа получим «прилипшие» позиции при смене трекинга;
- `force_width` и letter-spacing вместе — порядок применения важен;
- моноширинные места (JetBrains Mono) трекинг НЕ должны получать: у оригинала
  `letter-spacing` стоит точечно на заголовках, а не глобально.

## Точный список правок (замерено ц.31)

Расширять СУЩЕСТВУЮЩИЕ сигнатуры нельзя — слишком широкий радиус:
`layout_line(` встречается 24 раза в `vendor/gpui/src`, `shape_line(` — 12 раз
в нашем коде и `gpui-component`. Поэтому:

1. Новые методы-обёртки, старые оставить как есть с трекингом 0:
   - `TextSystem::shape_line_spaced(text, font_size, runs, force_width, letter_spacing)`
   - `LineLayoutCache::layout_line_spaced(...)`
   Старые вызывают новые с `px(0.)` — ни один существующий вызов не трогаем.
2. `CacheKey` и `CacheKeyRef` получают поле `letter_spacing: Pixels`
   (обязательно, иначе строка с другим трекингом придёт из кэша со старыми
   позициями). Их `Hash`/`Eq` — производные, добавление поля достаточно.
3. Пост-проход рядом с существующим `force_width` (`line_layout.rs:568-578`):
   сквозной индекс глифа `i`, `glyph.position.x += letter_spacing * i`,
   в конце `layout.width += letter_spacing * n_glyphs`.
4. `TextStyle` (`style.rs`) — поле `letter_spacing: Pixels` (default 0) и
   `Styled::letter_spacing()` в `styled.rs`. Поле живёт внутри
   `TextStyleRefinement`, который наш патч `refine_merge_text` (ц.25) сливает
   поле-в-поле, так что hover не будет его стирать.
5. Прокинуть из стиля в шейпинг: `elements/text.rs` (StyledText/Label) —
   заменить вызовы `shape_line` на `shape_line_spaced(..., style.letter_spacing)`.
6. Маркеры `KaminIDE patch` + счётчики в `scripts/vendor_patches.py`
   (ожидается +1 файл `text_system/line_layout.rs`, +N маркеров).

## Проверка

`probe metric` ширины заголовка секции Customize (`.08em`, FS_XS = 11):
строка из N символов обязана вырасти ровно на `N × 0.88` px. Замер ДО правки
уже есть в досье 82: «NOTIFICATIONS» = 89.6 против 82.4 у оригинала, то есть
наша строка сейчас УЖЕ шире — значит после патча сверять надо не «стало
больше», а точное совпадение с 89.6.

## Сделано в ц.31 (компилируется, 14 файлов / 57 маркеров)

1. `line_layout.rs`: поле `letter_spacing` в `CacheKey` и `CacheKeyRef`,
   метод `layout_line_spaced`, проход по глифам рядом с `force_width`
   (`glyph.position.x += spacing * i`, `layout.width += spacing * n`).
   `layout_line` делегирует с нулём — существующие 24 вызова не тронуты.
2. `text_system.rs`: `TextSystem::layout_line_spaced` и `shape_line_spaced`;
   старые `layout_line`/`shape_line` делегируют с нулём — 12 вызовов в нашем
   коде и `gpui-component` не тронуты.

## Цепочка достроена (ц.31, вторая половина)

`shape_text_spaced` → `layout_wrapped_line_spaced` → `layout_line_spaced` →
проход по глифам. Всё компилируется, старые вызовы делегируют с нулём.

Ключевое решение: трекинг применяется ТОЛЬКО при `wrap_width == None`.
При переносе `compute_wrap_boundaries` считает границы по ширинам БЕЗ
трекинга, и строка порвалась бы не там. Все наши цели (заголовки секций,
подписи табов, чипы) — однострочные `nowrap`, так что ограничение не мешает.

## Остаток: ДВА шага

1. `TextStyle.letter_spacing: Pixels` (default 0) в `vendor/gpui/src/style.rs`
   + `Styled::letter_spacing()` в `styled.rs`. Поле живёт внутри
   `TextStyleRefinement`, который наш патч `refine_merge_text` (ц.25) сливает
   поле-в-поле — ховер его не сотрёт.
2. `vendor/gpui/src/elements/text.rs:395` — заменить `shape_text` на
   `shape_text_spaced(..., style.letter_spacing)`. Это ЕДИНСТВЕННОЕ место
   отрисовки обычного текста; `div.rs:1930` — отладочная подпись id, её
   трогать не надо.

Дальше — проставить `letter_spacing` в семи местах порта и сверить ширины.

## (устарело) почему это ещё НЕ видно на экране

Обычный текст (`div().child("…")`, `StyledText`) шейпится НЕ через
`shape_line`, а через `shape_text` (`elements/div.rs:1930`,
`elements/text.rs:395`) — многострочный путь с переносом. Он идёт в
`wrap_line`, где ширины считаются заново, и трекинг там намеренно оставлен
нулевым (иначе перенос строк разъедется).

Остаток работы:
1. `shape_text` получает параметр трекинга и передаёт его в `wrap_line`;
2. `wrap_line`/`LineWrapper` учитывают трекинг при подсчёте ширины кандидата
   переноса, иначе строка будет рваться не там;
3. `TextStyle.letter_spacing: Pixels` + `Styled::letter_spacing()`;
4. места отрисовки берут значение из стиля.

Шаг 2 — единственный неочевидный: `LineWrapper` меряет ширины через свой
кэш `font_id → advance`, туда трекинг тоже надо добавить, иначе перенос будет
считать по «узкому» тексту.


## Ц.32: трекинг доехал до экрана, но замер требует нового инструмента

Проставлен в шести местах: заголовки секций Customize (.06em), заголовок
списка сессий и титул хедера дерева (.08em), меню Layout и колонка тем
(.04em), подписи табов редактора (.02em), титул Welcome (-0.02em).

Три попытки замерить ширину по кадру дали 120.5, 307.8 и 93.6 px — каждый раз
полоса ловила СОСЕДНЮЮ строку. Контрольный A/B (трекинг обнулён, пересборка)
дал те же 93.6 — то есть измерялся вообще не тот текст.

Регион `probe_area("section-title")` тоже не помог: он меряет БОКС, а блочный
`.sectionTitle` растянут на всю колонку (1068.8 px). У оригинала он тоже
блочный — значит эталон 89.6 снят с ТЕКСТА, а не с бокса.

### Что нужно (следующий шаг)

Probe-команда `{"cmd":"shape","text":"…","font":"…","size":11,"weight":600,
"spacing":0.66}` → возвращает ширину строки от шейпера
(`window.text_system().shape_line`). Тогда ширина текста меряется точно, без
пиксельной охоты по кадру, и годится для ВСЕХ семи элементов сразу.

Без неё пункт `letter-spacing` в досье не закрывать: «стало шире» — не
доказательство совпадения с 89.6.
