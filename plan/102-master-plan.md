## Фаза 0 — доделки уже начатого (S, риск L). Батчить в один релиз.

**0.1 #84 mailbox-nudge (главный не видит отчётов субагентов).**
ТОПОЛОГИЯ: CLI крутится НА СЕРВЕРЕ (контейнер), SendMessage — нативный тул CLI
(НЕ MCP, no host round-trip — `session-env.ts:26-29`), пишет файл в
`~/.claude/teams/<team>/` НА СЕРВЕРЕ. Клиентские тулзы ни при чём. Отчёт
попадает в mailbox сервера + `subagents/agent-*.jsonl`, НЕ в JSONL главного;
главный CLI дренит mailbox только на своём ходу → «ни один аудитор не прислал».
Вся логика СЕРВЕРНАЯ, клиент только рисует бейдж:
1. Сервер (рядом с `jsonl-watcher`): файл-вотчер на `~/.claude/teams/<team>/`,
   считает непрочитанные (mtime/offset).
2. Сервер→клиент: новый WS-ивент `team:inbox {count, from[]}` (как `jsonl:status`)
   → клиент рисует «N reports waiting» в agent-панели.
3. Клиент→сервер: кнопка «poke» → WS `session:nudge-main` → СЕРВЕР пишет в
   главный PTY (enter) через `session-io.ts writeInput` → CLI дренит mailbox.
Клиент mailbox НЕ читает. Открытый вопрос стенда: дренит ли CLI mailbox на
любом ходу или нужен спец-сигнал — если нет, fallback: только бейдж без nudge,
юзер сам даёт ход. Проверить `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` + первым
прогоном 4-агентной команды.

**0.2 #87 канал видимости (память хоста).**
`kamin:webview:viewState(id,visible)` ПРИНИМАЕТСЯ (`exthost/api/webview.ts:337`

**0.3 #87 двойной stringify.**

## Фаза 2 — O(файла)→O(хвоста) на реаттаче и компакте (M, риск L).

Арх-win #4. `replayAll()` (`server/src/core/pty/jsonl-watcher.ts:865`)
ре-парсит ВЕСЬ файл на каждом WS-реаттаче (`session-ws.ts:393`) — 15-20с на
85MB, хотя `streamFrom(offset)` (`:338`) уже есть, и у клиента зеркало с `_pos`.

**План:** реаттач шлёт клиентский `mirrorPos` (последний `_pos` зеркала) в
`session:resume`; сервер при наличии → `streamFrom(mirrorPos)` вместо
`replayAll`; при рассинхроне fingerprint → фолбэк на полный replay.
Segment-index (`rebuildSegmentIndex:587`) — инкрементально: новая compact-граница
+ счётчики хвоста, без полного ре-ридстрима.
Риск L: реаттач-путь уже понимает fingerprint/`_pos`; фолбэк страхует.
Гейт: реаттач большой сессии (85MB) < 1с до первого контента; компакт не
блокирует.

## Фаза 3 — единый контракт транскрипта (L, риск M-H). СВЯЗКА, только со стендом.

Арх-wins #1+#2+#6 — синергичны, делать вместе. НИ ОДИН канал не удаляется.

**Факт (проверено):** общий ключ `message.id` (id ответа API, `msg_...`)
СУЩЕСТВУЕТ и уже используется как ключ сшивки:
- стрим: `entry-synthesizer.ts:203` `message.id = msg.id`, uuid `stream-${msg.id}`;
- каноника: CLI пишет тот же `msg.id` в каждую per-block строку хода;
- клиент мирит по нему: `webview/src/signals/jsonl.ts:132` `findByMsgIdFromTail`.

**Инвариант:** `message.id` — ЕДИНСТВЕННЫЙ ключ владения бабблом и порядка.
Стрим создаёт/двигает текст в бабле по `message.id` (+ стабильный `_pos` от
watcher как ключ порядка); каноническая строка того же id — тихий upsert, НЕ
«замена-клоббер». `_ord` удаляется целиком.

**3 явных edge-правила (вместо неявной машинерии):**
1. API-abort retry → новый `message.id` = новый баббл, старый стаб убить
   (сейчас размазано в `abortedStreamIds`).
2. Синтетические/error-стабы (`msg_err_<rnd>`, `entry-synthesizer.ts:327`) —
   свой домен id, рендерятся как есть, в сшивку не входят.
3. N канонических строк одного `message.id` (thinking/text/tool_use) сворачиваются
   в тот же баббл, что рисовал единственный стаб (рендер по `message.id`).

**Что удаляется/схлопывается (webview/src/signals/jsonl.ts):**
`sweepOrphanStubs`+`STUB_TTL` (300-367), `abortedStreamIds` (134-151),
`mergeAssistantEntry` (379) → тонкий upsert-by-id, дедуп по msgId. `order-entries.ts`
→ сортировка по одному ключу (`_pos`/ts). ~300-400 строк долой.

**#2 связка (тройной курсор):** один стабильный ключ `_pos` сквозняком;
зеркало = единственный серверный кэш, через который читает клиент; `_ord`
удалить (`seenOrdsByTab`, ре-тег в `prependJsonlEntries:712`,
`replaceWindowWithSegment:657`, ord-dup диаг). Закрывает класс #82/#70-C9/#78.

**#6 связка (OOM-машинерия):** клиентский стор = строго ограниченное ВЬЮ над
зеркалом (никогда не растёт; окно грузится из зеркала). Схлопывает
`STORE_WINDOW`/`trimTabToWindow`/`enforceTabCap`/`needsRefill`/`archivedViewByTab`
(`jsonl.ts:48-66`) в «загрузи окно из зеркала».

**Стенд-матрица (обязательна ДО мержа):** стриминг длинного ответа + Ctrl+C
interrupt в середине; API-abort retry; live `/compact` в момент стрима;
subagent-стрим; scroll-up за окно; реаттач после обрыва; huge-session (85MB).
Каждый — «баббл не пропал / не над промптом / не дублировался / контекст-бар
не прыгнул».
Делать поэтапно за флагом: сначала ввести единый upsert-by-id ПАРАЛЛЕЛЬНО
старой машинерии (feature-gate), сверить на стенде, потом снести старое.

## Порядок и гейты

```
Фаза 0 (доделки) ──► релиз ──► гейт: субагенты+память на стенде
Фаза 1 (сносим NSIS) ── ГЕЙТ: тест-матрица Rust-инсталлера зелёная
Фаза 2 (реаттач streamFrom) ──► гейт: 85MB реаттач <1с
Фаза 3 (единый контракт транскрипта, СВЯЗКА #1+#2+#6) ── за флагом ──► стенд-матрица ──► снос старого
Фаза 4 (единый персист layout)
Фаза 5 (виртуализация чата) — после #6
```

Фазы 0/1/2/4 независимы, можно параллелить. Фаза 3 — самая большая ценность
(снос класса багов + ~300-400 строк) и самый высокий риск: только со стендом,
только за флагом, только с прогоном всей стенд-матрицы до сноса старого кода.

Не начинать фазу 3 без: (а) зелёной фазы 2 (streamFrom уменьшает объём реплея,
на котором тестируется сшивка), (б) договорённости по стенду.
